## 1. 产品简介

**Harnex** 是以工作区为中心的 AI 智能体运行时。它提供普通会话和项目任务入口，支持模型调用、并行工具、子任务、会话检索、记忆与技能，并通过多种客户端呈现执行进度和结果。

### 1.1 你能用它做什么

- 在浏览器里流式聊天（原生 Anthropic Messages、原生 OpenAI Responses，以及实现标准 Chat/SSE/tool-calls 基线的 OpenAI-compatible 端点）
- **CLI / TUI**：在终端交互执行项目任务，或通过一次性请求接入脚本与 CI/CD；支持 SSH 远程工作区
- Agent 可使用 shell、文件读写编辑、glob/grep、网页抓取、子 Agent 委托、记忆、技能、历史搜索、Todo、计划与验证等工具；实际目录由当前工具集、配置与接入的 MCP 决定
- **MoA**：对难题并行跑多个模型，聚合最佳答案
- **子 Agent**：把子任务丢给独立小 Agent，主线上下文不被污染
- **Cron**：按 cron 表达式定时自动运行 Agent 任务（如每日早报）
- **跨会话记忆**：`MEMORY.md`/`USER.md` 自动注入，长期记住你
- **渐进式技能**：把任何最佳实践写成 `SKILL.md`，Agent 需要时自行读取

### 1.2 使用入口

| 入口 | 适用方式 |
| --- | --- |
| Web | 在浏览器中管理会话、项目、配置与自动化 |
| 桌面 | 使用原生窗口、本机目录选择和托盘管理 |
| CLI / TUI | 终端交互、SSH 项目任务和脚本中的一次性请求 |
| VS Code | 在编辑器内执行项目任务、读取选区与诊断、审阅文件差异 |

普通会话与项目 Agent 的范围见 §3.1，各入口的安装条件见 §2。

## 2. 快速开始

### 2.1 通过 npm 全局安装

TUI 适合在终端中保持交互会话，`-p` 一次性请求适合脚本和 CI，Web UI 提供图形化操作。各入口使用同一套运行、会话、技能与工具协议；同一 Runtime Domain 的客户端共享实时运行状态，跨域共享档案和配置的边界见详细设计 §3.21／§3.29。

```bash
# 1. 全局安装（构建产物随包发布；若直接克隆源码请走 §2.1 自行打包）
npm install -g harnex

# 2. 配置密钥
export OPENAI_API_KEY=sk-...

# 3. 常用命令
harnex             # 交互式启动菜单：Web UI / Terminal
harnex tui         # ★ 直接进入 native TUI
harnex serve        # 启动 Web UI + REST API（:18081），由 standalone-web Domain 托管
harnex stop         # 在任意终端干净停止后台 server
harnex status       # 查看是否在跑
harnex cli -p "总结 README.md"   # 一句话模式（脚本/CI 用，少用）
harnex --help       # 完整帮助
```

### 2.1.1 桌面图标 / 启动器

`npm install -g harnex` 安装完成后会**自动**在桌面创建一个 “Harnex” 图标，
双击即弹出 “Web UI / Terminal” 选择菜单。如果不希望自动创建（比如部署到服务器），
安装前设置环境变量 `HARNEX_NO_SHORTCUT=1` 即可；以下场景会自动跳过：

- 局部安装（非 `-g`）
- CI 环境（`CI` / `GITHUB_ACTIONS` / `GITLAB_CI` / `JENKINS_HOME` / `BUILDKITE`）
- Linux 上以 `root` 身份安装（容器 / 系统镜像）
- Linux 上无 `DISPLAY` / `WAYLAND_DISPLAY`（无图形界面的服务器）

任何时候都可以手动管理：

```bash
harnex                      # 命令行也是同一个交互式选择菜单
harnex shortcut              # 手动创建（或修复）桌面图标
harnex shortcut --uninstall  # 删除桌面图标
```

启动菜单提供三个选择：

- `[1] Web UI`：在浏览器打开工作台，默认地址为 `http://localhost:18081`。
- `[2] Terminal`：在当前终端启动 TUI。
- `[q] Quit`：退出启动菜单。

行为说明：
- **跨平台**：Windows 写 `Desktop\Harnex.lnk`（PowerShell COM 生成，自动渲染图标），
  macOS 写 `~/Applications/Harnex.command`，Linux 写 `~/Desktop/harnex.desktop`。
- **仅桌面**：根据用户反馈，**不再写入开始菜单 / 应用列表**。如需删除旧版本残留的开始菜单项，
  执行一次 `harnex shortcut --uninstall` 会一并清理。
- **Web UI 启动**：选 [1] 后启动器会**轮询 `/actuator/health`** 直到后端就绪再唤起浏览器，
  冷启动 JVM 不会再 `ERR_CONNECTION_REFUSED`。
- **跳过菜单**：`harnex launch --webui` / `--tui` 直接进入指定模式；
  `harnex shortcut --webui` 让桌面图标默认进 Web UI。
- **非 TTY 自动 Web UI**：一些 GUI 环境双击 `.command` / `.desktop` 不会分配真正的 TTY，
  此时启动器会自动选择 Web UI 而不是卡在等待输入。


> 🔑 **进程管理**：`harnex serve` 的 Owner lease 位于 `~/.harnex/runtime-domains/standalone-web/owner.json`，`harnex stop` 只停止该 Domain 的 Node+JVM 进程树，不影响 Web Supervisor、Tauri、VS Code 或 CLI Domain；Windows 自动用 `taskkill /T /F`，Unix 先 `SIGTERM` 后 5 秒升级到 `SIGKILL`。
> 🛑 **TUI 中断**：native TUI 中 **Ctrl-C** 只取消当前 Run，空闲时清空 Composer；Composer 为空时
> **Ctrl-D** 退出。standalone TUI 会 drain 自己拥有的 Runtime，attached TUI 退出不会影响 IDE Owner。
> 🧠 **摘要模型**：默认开启历史摘要压缩（防 token 撑爆），建议把 `HARNEX_SUMMARIZER_MODEL` 显式指向当前仍受厂商支持的廉价模型。详见 [§9 配置项参考](#9-配置项参考) 和 [docs/04_部署方案.md §4.3](04_部署方案.md)。
> 🖼️ **图片上传**：是否原生发图由全局 vision 开关和该 provider 下精确模型 ID 的 `input-modalities` 共同决定，不按模型名称猜测。未声明时会给模型可见的 `file_read`/OCR 降级提示；OCR 需安装 `tesseract`。详见 [§3.4.1](#34-附件与图片) 和 [docs/04_部署方案.md §4.5](04_部署方案.md)。
> ☕ **npm 依赖**：Node 18+、JRE/JDK 17+。macOS 会按 CPU 自动安装小型 native TUI 包；
> 桌面 DMG/NSIS 与 VS Code Runtime companion 自带 JRE，不需要系统 Java。

### 2.1.2 原生桌面安装包（Windows / macOS，零依赖）

面向**完全不想碰命令行 / 不想装 Node 或 JDK**的最终用户：Harnex 提供基于 Tauri 的
原生桌面薄壳（Windows NSIS；macOS 13+ DMG，签名状态见下文）。安装运行后自动在本机
空闲 loopback 端口拉起内置 Runtime，并从安装包可信资源加载完整 Vue SPA——**无需预装 JDK / Node / 浏览器配置**。

- **内置校验 Runtime Bundle（jlink JRE + 后端 jar + native CLI）**：用户机器零依赖；
- **复用系统 WebView**（Windows WebView2 / macOS WKWebView），薄壳不打包 Chromium；
- 与 Web 复用同一 SPA、API 和 Workspace Store；桌面 SPA 不由工作区 JVM 托管，因此切换时不重载窗口；
- 关闭窗口隐藏到系统托盘，Runtime 继续服务；托盘“退出 Harnex”才会 drain 并结束进程树
  （Windows 走 `taskkill /T /F`；macOS/Linux 终止独立 POSIX 进程组）。

**普通用户**：Windows 下载 setup.exe；Mac 按 CPU 下载 aarch64/x64 DMG，打开后把 Harnex.app 拖入
Applications。普通本地构建的 DMG 使用 ad-hoc 签名，未进行 Developer ID 签名或 Apple 公证；正式签名制品需单独通过签名、公证和 Gatekeeper 验收。以下载制品的发行说明为准，不能仅凭 `.dmg` 扩展名判断签名状态。Mac CLI 可在
App 内执行一次
`/Applications/Harnex.app/Contents/Resources/resources/bin/harnex path install`，建立
`~/.local/bin/harnex` 用户链接；若该目录不在 PATH，按提示加入 `~/.zprofile`。

若历史 Workspace 双击后进入 FAILED，可查看 `%USERPROFILE%\.harnex\runtime-domains\tauri-main\logs\desktop-shell.log`。
桌面包会严格校验内置 Runtime，同时把独立的 `resources/ui/` SPA 排除在 JVM Bundle 文件清单之外；
日志中的 `extra` / `missing` 会列出具体异常文件，而不再只显示笼统的文件集错误。
有历史项目时自动打开最近使用项目；首次无历史项目时直接显示空工作台，不自动弹选择框。点击左上
Workspace 后才打开系统目录选择，取消后仍保持空工作台。后续切换仍点击同一个 GUI 入口。
Mac 关闭红色按钮后可从 Dock/菜单栏重新显示；默认不注册 `⇧⌘H`，避免覆盖 Finder Home 快捷键。

**开发者构建安装包**（需 Rust + Tauri CLI v2 + JDK 17 含 `jlink`）：

```bash
npm run build:desktop:check    # 体检工具链（cargo / tauri-cli / jlink），不构建
npm run build:desktop          # Windows: NSIS；macOS: 当前 CPU 的 .app + .dmg
npm run build:desktop:updater  # 签名 updater artifact
npm run build:desktop:macos:release # Mac Developer ID + notarization + updater
npm run build:desktop:debug    # debug 构建（更快、体积大）
# 或经由统一构建入口：
node scripts/build/build.mjs --target desktop   # 等价于上面的 build:desktop
```

桌面外壳的环境变量开关（与 `bin/harnex.mjs` 对齐）：`HARNEX_PORT` / `SERVER_PORT`（显式端口；未设置时自动选择空闲端口）、
`HARNEX_DATA_DIR`（当前 workspace 运行数据目录，默认 `<workspace>/.harnex/data`）、
`HARNEX_USER_DATA_DIR`（用户数据目录，默认 `~/.harnex`）、`HARNEX_RUNTIME_DOMAIN_ID/DIR`（桌面 Domain）、`HARNEX_JAR`（覆盖 jar 路径）。Tauri 始终拥有自己的 Runtime，不提供任意 URL attach/no-spawn 模式。
更多细节见 [src-tauri/README.md](../src-tauri/README.md) 与 [docs/04_部署方案.md](04_部署方案.md)。

#### macOS 专项行为

- **架构**：Apple Silicon 与 Intel 分包，不通过 Rosetta 猜测另一架构的 JRE；下载与本机 CPU 匹配的 DMG。
- **命令环境**：Finder/Dock 启动会恢复登录 Shell 的 PATH，因此 Homebrew 下的 `git`、`node/npx`、
  `docker`、`ssh`、`tesseract` 可被 Runtime/MCP 发现。不会把 Shell 中其它变量整体导入应用。
- **密钥**：在桌面设置页新输入的 Provider API Key 写入 macOS Keychain；`agent-config.yml` 仅保存
  环境引用。历史明文配置继续工作，但主文件与 `.bak` 强制 owner-only 0600。该引用只由 Harnex.app
  拥有的 Runtime 解析；非桌面 launcher 会在启动前给出明确错误，避免空 key 静默鉴权失败。Node/native
  CLI 可附加桌面 Runtime；VS Code 拥有独立 Runtime，需要单独提供凭据。Keychain 命名空间不会被 MCP
  配置展开，并会从 Runtime 启动的 bash、Git、提取器及其它子进程环境剔除。
  密钥仍需短暂存在于 JVM 环境；同一 OS 用户观察该进程环境、以及用户点击“显示密钥”让明文进入受信
  Webview，是当前本地桌面架构的残余风险。
- **系统代理**：设置页代理地址填 `system` 才显式使用 macOS 系统/PAC 代理；留空仍按 YAML →
  `HTTPS_PROXY` 等环境变量 → 直连解析，绝不静默继承未知 JVM 代理。
- **文件权限**：第一次选择 Desktop、Documents、iCloud Drive 或外置卷时，按 macOS 提示授权；应用
  不申请 App Sandbox，因为核心能力需要启动内置 JVM 与用户批准的工作区命令。
- **退出**：红色按钮隐藏窗口；Dock reopen、菜单栏 Show 可恢复。Cmd-Q、菜单 Quit 或 SIGTERM 都会
  drain 后终止整个 JVM/MCP/tool 进程组。
- **更新**：启动后台检查，菜单栏可手动检查。缺少 HTTPS endpoint/公钥的开发构建显示更新通道未配置；
  正式包只安装 minisign 验证通过且具备 Developer ID/Apple 公证的更新。
- **诊断**：日志位于 `~/.harnex/runtime-domains/tauri-main/logs/`；发布包可用
  `codesign --verify --deep --strict /Applications/Harnex.app` 与 `spctl --assess` 验证。

### 2.1.3 VS Code 与原生 CLI（完全离线）

VS Code 版本由轻量 UI 扩展和目标平台 Runtime companion 组成。离线环境 Windows 运行
`install-vscode.ps1`，macOS 运行 `install-vscode.sh`；脚本先装 companion 再装 UI，目标机无需 Node/JDK。

每个 VS Code 窗口拥有独立 Runtime Domain。新建集成终端会自动获得当前窗口的 manifest 和 bundle 内 native CLI PATH：

```powershell
harnex doctor                         # 校验 bundle 与当前 IDE exact attach
harnex cli -p "解释当前选区相关代码"  # 复用 IDE JVM，不启动第二份 Runtime
harnex cli --run <id> --steer "先修复测试"
harnex cli --run <id> --follow-up "完成后再检查文档"
harnex stop --run <id>                # 只取消 Run
harnex runtime restart                # attached 模式会拒绝；请用 VS Code Restart Backend
```

外部终端可显式执行 `harnex --domain-manifest <domain.json> ...`；manifest 的 endpoint、双 PID、owner lease、root/workspace/instance、protocol 与 boot-token 任一不匹配都会失败，绝不扫描端口或退回 spawn。没有 manifest 的普通 `cli -p` 会启动临时 Command Domain，执行后关闭。

仓库开发者生成离线包：

```powershell
npm run build:runtime:companion
npm run build:offline
# 输出 dist/offline/<version>-<target>/：双 VSIX、portable/runtime、安装脚本、SHA256SUMS
```

**升级 / 卸载**：

```bash
harnex stop                          # 升级或卸载前先停掉 server
npm update -g harnex         # 升级到最新（或 npm i -g harnex@latest）
npm uninstall -g harnex      # 完全卸载

# 用户数据不会被自动删除（避免误清），按需手动清理：
rm -rf ~/.harnex             # ⚠️ 删用户配置/Auth/用户 Profile/Skill 状态/Supervisor registry
# workspace 会话、上传和索引位于各自 dataDir（默认 <workspace>/.harnex/data），需分别处理
```

### 2.2 本地 5 分钟启动（开发者）

```bash
# 1. 拉依赖
cd backend && mvn -DskipTests package -q
cd ../frontend && npm ci && npm run build

# 2. 使用内置 primary 时设置 OpenAI 密钥
export OPENAI_API_KEY=sk-...
# 也可启动后在设置页配置其他 Provider；仅设置 FALLBACK_API_KEY 不会启用默认禁用的 fallback

# 3. 启动后端
cd ../backend && mvn spring-boot:run

# 4. 启动前端（开发模式）
cd ../frontend && npm run dev           # http://localhost:18081
```

浏览器打开 `http://localhost:18081` 即可。前端默认走代理 → 后端 8088。

> 💡 **更省事**：仓库自带启动脚本 —— Windows 双击 `backend\dev-run.bat` + `frontend\dev-run.bat`，Linux/macOS 分别在终端运行 `./backend/dev-run.sh` 与 `./frontend/dev-run.sh`（首次可能需 `chmod +x`）。默认前台运行，Ctrl-C 停止；Linux/macOS 显式传 `--bg` 才后台启动并写 PID 文件。详见 [docs/04_部署方案.md §4.1–4.2](04_部署方案.md)。

> 本地用户级 GUI 默认 `HARNEX_AUTH_ENABLED=false`，归属当前 OS 用户，不显示登录或账户页面。
> 只有显式远程/API 部署设置为 `true` 时才启用后端账号、Session 和 Bearer 认证资源；默认 Web GUI
> 不提供交互登录页。

### 2.3 CLI / TUI 模式快速启动（源码路径）

```bash
cd Harnex

# 构建 native CLI + verified Runtime Bundle

# Windows 源码构建产物
```

### 2.5 Web Supervisor 与工作区域

```bash
harnex supervisor --port=18081
```

打开宿主显示的浏览器地址。首次进入默认“会话”，无需选择项目即可看到引导页和输入框；如果没有可用模型，先去设置页配置语言模型。左侧选择 Agent 后，通过项目选择器打开本机或 SSH 项目。

会话与 Agent 切换保留各自草稿和记录，不停止后台任务；Agent 内真正切换项目时先关闭当前项目。普通会话始终保存在用户目录的 personal 下，项目记录跟随各自 dataDir。共享个人 Runtime 和项目 Runtime 可以同时存在，浏览器多个标签页不会因此各自启动一份个人进程。

Web Supervisor 和桌面宿主启动时会后台预热个人 Runtime，同时恢复最近的项目，不依赖点击“会话”才启动。预热完成后的切换直接复用进程；冷启动尚未完成或正在恢复连接时，仍会短暂显示“正在连接会话服务”。

Web 的“本机目录”指运行 Supervisor 的机器，Windows 可选择所有可读盘符；Tauri 桌面使用原生目录选择器。启动失败时查看可读错误及“错误详情”，不要通过重复点击新对话来恢复界面。诊断页可查看实际存储路径与运行身份。

<a id="ssh-workspaces"></a>
### 2.6 打开 SSH 远程项目

1. 在「打开工作区」中选择「打开 SSH 远程项目」。已保存连接和 SSH config 的具体 Host 别名会自动列出，也可以输入 `user@hostname`、单独填写用户名，或粘贴简单的 `ssh` 连接命令。端口、连接名称和私钥路径位于高级配置；跳板机等设置继续由 OpenSSH config 处理。
2. 点击「连接」。优先复用 SSH config 和密钥代理；需要确认新主机指纹、输入密码或私钥口令时，应用内会显示认证卡片。主机指纹变化会拒绝连接。连接成功后才保存配置并显示远端主目录，无需先保存、再测试、再浏览。
3. 选择远端目录，可输入绝对路径或 `~/...`，也可使用面包屑、主目录、上一级和该主机的最近项目。连接测试和目录浏览只执行轻量 SSH 命令，不上传 Runtime，也不需要远端 Java。
4. 点击「打开此远端目录」后才准备运行环境：优先使用远端已有 Java 17+；缺少合适 Java 时，为 Linux x64/arm64 按需下载并校验 Eclipse Temurin 17 JRE，上传至远端用户私有目录。Runtime JAR 按 SHA-256 缓存于 `~/.harnex/runtime-cache/<sha256>.jar`，自带的 `rg` 放在同目录下的 `<sha256>/bin/rg`。不安装系统包，不复制整个项目。
5. 远端运行项目仍需 Linux、`setsid`（util-linux）、`sha256sum`；自动准备 JRE 还需 `tar`。代码搜索组件 `rg` 由 Runtime 自动准备，用户无需安装；Git 和构建工具按项目准备。网络受限时，可事先安装远端 Java 17+，或复用连接机器已校验的下载缓存。
6. 在远端工作区的设置中配置模型服务，复用远端已有配置或环境凭据。本机 Keychain 引用不会写入远端配置。

本机项目和 SSH 项目分别标明来源。远端路径只在远端解析；同名目录会同时显示主机和路径。Web 界面中的「本机」指运行 Harnex 的机器；页面辅助信息说明连接来源。SSH 配置、密钥代理、私钥选择和下载缓存都属于该机器，不属于浏览器所在电脑。桌面端可以直接选择本机私钥文件，路径支持 `~/`。

认证答案通过带随机凭据的 loopback askpass 通道传递，只保存在当前连接宿主的内存中；不会写进连接配置、命令参数、公开日志或工作区清单。一次性验证码不缓存。SSH config 变化会使原认证缓存失效。需要再次认证时，打开/关闭项目的前台连接过程仍可显示认证卡片；后台隧道只尝试复用会话，不弹出无人应答的提示，也不会重新提交任务。

SSH 连接支持密钥、密码、私钥口令和键盘交互验证码，认证信息在连接窗口内输入。路径输入或拖选文本时点击弹窗外部不会关闭 SSH 表单，关闭和取消使用明确按钮或 Esc。

再次打开已保存的 SSH 项目时直接重连，不先重复浏览目录、准备和登记项目。缓存完整时，Java、JAR 与 rg 的检查合并在一次 SSH 请求中完成；JAR 和 rg 仍核对完整 SHA-256，只有缺失、损坏或实际运行文件变化时才上传。缓存属于远端用户，可供多个项目复用；不同项目的运行状态仍然独立。

**连接服务器上已有的 Harnex**：在 Web／桌面的 SSH 连接成功后，选择“连接已有 Harnex 服务”，从列表选择正在运行的项目。此模式通过 SSH 隧道接入现有服务，不上传 JAR、不安装 Java、不启动另一套 Runtime。退出或切换项目只断开本机连接，服务的启停和升级由服务器管理。已有服务停止或身份变化时会明确报错，重新启动服务后再连接；不会自动改为部署新服务。

查找位置填写的是服务器的 **用户数据目录**，默认 `~/.harnex`：root 账号通常为 `/root/.harnex`，普通账号通常为 `/home/用户名/.harnex`，不是文件系统根目录的 `/.harnex`。`HARNEX_USER_DATA_DIR`／`--harnex.user-data-dir` 可覆盖此位置。Runtime 的程序、JAR、安装包可以位于 `/opt/harnex` 或其他目录；项目历史和状态通常位于 `<项目>/.harnex/data`，这三种位置各自独立。

新版独立 JAR／容器会在 `<用户数据目录>/runtime-domains/<运行域>/service.json` 发布不含凭据的接入信息；已有 CLI／Web／桌面宿主发布的兼容 `domain.json` 也可发现。SSH 用户须能读取对应受保护凭据，普通用户不能接入其他用户的私有服务。旧版独立 JAR 未发布信息时需先在服务器更新。Docker 要把用户数据卷暴露给 SSH 所在主机；若容器端口与宿主映射端口不同，在高级设置填写宿主端口。服务需能通过服务器的 IPv4 loopback HTTP 端口访问。自定义运行域目录应保留在所填用户数据目录的 `runtime-domains` 下，并为长期部署固定运行域 ID。

**托管服务的版本更新**：重连时读取正在运行的版本和 JAR 摘要，并与本机准备的构建比较。原服务仍在运行时继续复用，不自动打断任务；有更新会在“设置 → IM 客户端”的远端服务区域提示“空闲时更新并重启”。确认空闲的检查和关闭任务入口在服务端一起完成，有任务、暂停中的未结束任务或会话修改时拒绝升级，不取消工作。更新需要重新启动 JVM；若启动失败，保留错误并重新连接，不自动回滚。取消等待不能撤销已经开始的服务重启。旧服务不具备空闲升级能力时，界面提示先明确停止旧服务、再重连启动新版。接入已有服务的模式只显示运行版本，更新在服务器进行。

界面区分“检查缓存／复用文件”“连接或启动远端服务”和“建立工作区连接”。已有文件不代表 JVM 仍在运行：若上次停止了服务，下次仍需启动 JVM；需要更快重连时可选择“离开后保持远端运行”。开发模式下，即使版本号相同，重新打包后的 JAR 字节也可能改变，系统按实际文件摘要判断是否上传。重新登记同一个项目会保留原名称、最近使用时间及后台运行设置。

打开项目时，连接窗口只显示目标主机／目录和一个当前阶段，统一使用一个“取消”按钮；取消请求发出后显示“正在取消连接”，等待宿主结束，不再同时显示另一条“正在打开远端项目”。

Runtime 使用按摘要区分的不可变缓存，不原地覆盖其他服务可能正在使用的 JAR。新版在托管项目成功打开、升级或关闭后回收旧缓存：保留最近使用的两个构建、所有仍在使用的运行／控制构建，以及最近两小时准备过的构建；其余旧 JAR 和对应 `bin/rg` 一起清理，每次最多 32 个。清理只涉及 SSH 专用 `~/.harnex/runtime-cache`，不触碰项目数据、用户配置、JRE 或其他位置的独立安装。多项目同时使用不同版本时会保留多份；新准备文件的保护期结束后，在后续成功连接中继续回收。无法确认旧服务的构建身份、读取进程信息或取得清理锁时先保留文件，不冒险删除；旧客户端和服务需更新后才能完整参与这套机制。

移除连接配置保留最近项目历史，列表标记“连接已移除”，可重新配置原连接或单独移除最近记录。移除历史只修改本机目录索引，不删除远端项目文件；活动工作区仍需先关闭。

启动时，本机最近项目由宿主恢复，SSH 最近项目先打开认证窗口再恢复。自动恢复只尝试一次，失败后保留主界面及重试、选择其他项目入口，不自动循环重试。关闭或重连失败也会结束加载状态，同时保留尚未确认停止的 Runtime 身份。界面优先显示可读说明，原始错误和远端日志路径收在“错误详情”中。

连接、认证、目录浏览和准备过程可取消，Esc 保留当前草稿；迟到的结果不会继续打开项目。已经进入工作区切换后，取消只中断连接控制过程，不代表远端任务已停止；若远端 Runtime 已启动或关闭尚未确认，保留其身份并通过重新连接确认状态。

**离开后继续在手机 IM 中使用远端项目**：打开该 SSH 项目的 **设置 → IM 客户端**，勾选“离开后保持远端运行”。此后切换项目或退出桌面/Web 宿主只断开界面连接，服务器上的任务和机器人连接继续运行。也可点击“仅断开界面，保留远端运行”回到普通会话；项目列表显示“已留在远端 · 连接后确认状态”，再次打开后确认并接回原实例。要停止时，重新连接该项目，点击“停止远端服务…”并确认。关闭勾选仅改变下次离开的行为，不立即终止当前服务。

这个选项默认关闭，只针对桌面/Web 管理的 SSH 项目。服务器需持续开机、联网；重启服务器后需要重新连接，选项不安装系统开机服务。Linux 固定服务部署可继续使用 Docker Compose 的重启策略。远端项目分别保留自己的进程身份，同一主机可以保留其他项目；同一机器人仍只能由一个项目持有连接，保留 A 后打开 B 不会自动把机器人转交给 B。若要转交，在 A 断开机器人或明确停止 A 的服务后，再连接 B。

原生 CLI/TUI：

```text
harnex remote add devbox --host ops@server --port 22
harnex remote list
harnex remote discover
harnex remote test devbox
harnex tui --remote
harnex tui --remote devbox
harnex tui --remote devbox --workspace /srv/project
harnex cli --remote devbox --workspace /srv/project -p "检查项目" --permission-mode ask
```

`tui --remote` 显示远程主机选择；指定别名但省略工作区时显示远端目录选择。GUI 保存的名称、唯一主机地址和 SSH config 别名可直接用于 CLI，无需抄写 GUI 内部连接 ID；名称有歧义时会提示改用 ID。

可以加 `--identity-file <连接机器的路径>`（支持 `~/`）和 `--java <远端 Java 可执行文件>`。交互 TUI 在终端内处理指纹、密码和私钥口令；非 TTY 模式必须提供远端目录并具备可用的免交互认证，缺少 `--remote` 参数值会报错，不会退回本机执行。TUI 顶部标明 Local 或 SSH；命令执行环境及隔离策略在设置中查看和配置。

Runtime Bundle 包含 Linux x64/arm64 的静态 ripgrep 15.2.0；仅安装 CLI/JAR 时，由连接机器按官方发布地址和内置 SHA-256 清单自动下载。远端校验并复用缓存，启动时明确绑定 Runtime 自有 `rg`，不依赖项目或系统 PATH。

自动 JRE 来源为 [Adoptium API](https://github.com/adoptium/api.adoptium.net)。仅接受 Temurin 17 官方 GitHub 发布地址和有效 SHA-256 摘要；连接机器缓存位于用户数据目录的 `runtime-downloads/`，远端位于 `~/.harnex/jre-cache/`，不会修改系统 Java 或项目工具链。

源码运行需要先构建后端和原生 CLI：

```text
mvn -f backend/pom.xml -DskipTests package
npm run build:native-cli
```

Web Supervisor 与桌面端复用 `host-runtime` 连接实现；Web 由 Supervisor 所在机器发起连接，不是浏览器直接访问 SSH。启动前检查原生 CLI 的 SSH 协议能力，自动跳过旧版本候选；组件缺失或全部过旧时显示更新/安装提示，不能使用 Java REPL 回退实现远程连接。

远端项目默认在远端 `<项目>/.harnex/data` 保存记录，`.harnex/skills` 可跟随项目 Git 共享；远端用户配置、运行域和下载缓存位于远端用户 `.harnex`。本机已登记的显式 dataDir 优先，不自动搬迁历史。

在 SSH TUI 内按 F6 返回的是本机个人会话，远端 Agent 连接和任务保留。一次性 `cli --conversation --remote` 不支持；普通会话请使用本机 `--conversation`，远程项目使用 `--remote`。

## 3. 核心功能使用指南

### 3.1 普通会话与项目 Agent

左侧“会话”显示新对话、对话记录和搜索对话，不显示 workspace 切换。输入问题并发送即可；服务器确认接收后，问题立即出现在主区域并清空已发送草稿。失败保留输入，连接／历史加载失败提供重试入口。

左侧“Agent”显示新任务、任务记录、搜索任务和项目区域。先选择项目，再描述需要分析、修改或验收的任务。模型、权限、Plan 和 Goal 按实际任务选择，不需要额外选择“当前会话”或“当前 Agent”执行模式。

普通会话生成中再次发送会排队下一轮；Agent 运行中默认补充当前任务，也可选择完成后执行。前置未完成／失败会保留后续队列，待处理后再继续。停止按钮取消当前运行；关闭页面或切换视图只改变显示，不等于取消。

### 3.2 任务进度、调用与用量

Agent 的工具、子任务、审批和文件修改在消息与工作台中展示；需要用户决定时，就地回答问题、审阅计划或批准具体调用。普通任务遇到必需输入／本轮限额会显示“未完成”，可在下一轮继续；Goal 受阻或暂停后使用恢复入口，不会假装仍在生成。

Git 项目的 Agent 主会话顶部，在任务标题下方以轻量文字显示项目和当前分支；TUI 在现有顶部信息区显示 `git: 分支名`。这里反映工作目录的实际状态，查看历史任务不会恢复历史分支。在终端或 IDE 切换分支后，界面会自动刷新（前台每 5 秒，并在重新获得焦点时刷新）。显示为只读，不提供切换分支操作；非 Git 目录隐藏分支，游离 HEAD 显示短提交号。SSH 项目读取远端工作目录。

普通会话顶部的“调用 / 用量”可点击展开，再点一次收起。Agent 在工作台的对应页签查看，顶部不重复提供用量按钮。模型信息默认显示实际使用的模型与输入／输出；实际模型发生变化时才补充原选择，路由与重试详情放在调用记录中。

“调用”统计实际请求尝试，一次问题可能含重试、摘要、子任务或图片调用。“用量”从模型响应记录 Token 或图片数量，无需用户填写。费用由本地配置的单价估算，程序不会从模型接口自动获取价格，也不是供应商账单。没有单价／完整用量时显示未知或已知小计。当前没有独立倍率配置，中转倍率应折入输入、输出、缓存或图片的实际单价。

### 3.3 历史、编辑与继续

对话记录与任务记录按各自空间保存；新对话／新任务不删除旧记录。搜索可定位原文及保留的执行记录，长历史按页加载。编辑较早消息或重新回答保留原分支／回答；Agent 的重新执行可能再次修改项目，编辑历史本身不会撤销磁盘文件，恢复文件应使用工作台的恢复点。

从会话转交 Agent 时，选择需要带入的文字和资产并选项目，系统准备新任务草稿；不会把整个个人空间或未发送草稿自动交给项目，也不会仅因切换入口而执行任务。

### 3.4 附件与图片

把图片或文档加入当前输入；支持的图片／文件格式以当前模型能力为准。具有视觉能力的模型接收真实图片，无视觉能力时不能凭文件名判断画面；OCR 仅用于可提取文字，不等于视觉理解。

没有视觉能力的会话模型仍可把本轮图片的引用交给图片服务，执行用户要求的编辑或参考图生成；此时图片像素不会发送给会话模型，它不能据此描述画面。如果只是带着图片聊其他话题，也不会自动发起生图。

生图直接输入“生成一张……”；继续修改时也可直接描述要求，无需为了编辑而重复引用图片。语言模型结合当前输入、会话历史与图片引用，判断本轮是普通聊天、生图还是编辑，并在编辑调用中选择具体源图。上一轮有图或本轮附了图都只是上下文，不会自动触发编辑，也不会由程序强制选作源图；换话题可正常聊天，目标不明确时再通过对话澄清或引用图片。不需要进入单独生图页面；需要配置支持相应生成／编辑能力的图片模型，且自然语言入口的语言模型具备工具调用能力。图片模型负责绘图，语言模型负责理解要求与调用图片能力，两者可以来自不同服务。

会话所选语言模型（未选择时使用默认模型）先理解需求并决定是否调用 `image_generate`，图片服务再执行绘图。因此会话中的语言模型名称与输入／输出 Token 消耗仍然存在，图片卡片另行显示实际调用的生图型号。图片接口返回的用量单独记录；Responses 生图还会使用图片配置中的 `main-model`。

生成时显示模糊动画占位，状态自动更新，完成后显示图片，无需手动刷新。占位动画不是真实的中间预览。读取状态出错或结果未知时才提供刷新入口；刷新只查询状态，不会再次生成。图片可直接查看、下载或引用到后续消息。

生成的图片原文件会自动保存到当前空间的数据目录，并随会话历史保留；在同一台机器、同一数据目录重新启动后，无需先下载也能查看历史图片。“下载原文件”只是额外导出一份。浏览器缓存和程序重启不会改变图片归属；若原数据目录被删除或未随迁移复制，历史中的引用无法替代缺失的原文件。

图片结果卡保留原图与各次编辑结果。多图部分成功会保留已生成图片；网络中断导致结果未知时不会自动再次付费生成。保存失败可恢复已有结果；取消后仍可能收到已被上游接受的结果。下载可另存为本机文件；终端以文字和资产引用展示结果。

普通会话与 Agent 共用附件和结果查看器。上传、拖入或粘贴图片后，可以点击输入框中的缩略图查看；上传失败的文件保留在输入框，可重试或移除。失败文件尚未处理时不会被悄悄遗漏后发送。点击历史附件或生成的图片可放大、下载；“引用图片”将图片加入当前输入并保留已有草稿，具体用途由用户的文字要求决定。

#### 结果预览

项目文件树和搜索结果中的文件统一在弹窗查看，点击、Enter 或空格键均可打开，不再占用右侧栏。文本源码可查看、复制；HTML、图片／SVG、Markdown、PDF、音视频、JSON 和 CSV 按格式预览。回答中的 HTML／SVG 代码块提供“打开预览”；Mermaid 显示为图表，完成的 Markdown 回答支持公式。JSON 可折叠，CSV 按表格展示。

只有可渲染的内容显示“预览／源码”切换；纯文本或无法解析的内容直接显示源码。刷新图标紧跟文件名，关闭按钮独立位于右上角。下方工具栏分为查看模式和文件操作两组；窄屏下文件操作移到下一行。切到源码页签后自动聚焦源码区域，可直接按 `Ctrl+A`（macOS 为 `Command+A`）全选源码，不包含行号、弹窗工具栏或外层页面。

“变更”列表中的文件点击后在弹窗显示对应任务的差异，包括已删除文件；“恢复该文件”仍进入恢复确认流程。关闭弹窗后回到变更列表，整次任务的撤销操作保持不变。

本地项目文件的预览提供“打开所在目录”，不重复显示下载；SSH 项目文件提供下载到本机。会话中的附件、生图结果和内联 HTML 仍提供下载，用于保存独立文件。

HTML 预览运行完整文件及所在目录内的相对 CSS、JS、图片和数据资源，支持页面自身的按钮、计算、筛选和表单逻辑。预览操作不自动发送会话消息，不自动触发 Agent 工具。页面保持当前状态，修改源文件后可点击“重新载入”；重载会重置页面内的临时状态。普通会话中的 HTML 代码和上传文件不需要项目目录。

预览文件上限为 32 MiB，源码视图最多显示 2 MiB，CSV 最多展示前 500 行数据，超限时可通过所在目录或下载入口查看原文件。项目依赖资源仅限入口文件所在目录及其子目录，外部网络资源、父目录引用和隐藏文件不开放；React／Vue 源码需要项目开发服务，不能直接当作 HTML 运行。HTML 在隔离页面中执行，不能访问主界面或 Runtime API。浏览器预览链接最多有效 30 分钟，过期后在 Harnex 重新打开。

TUI 使用 `/preview 相对路径` 打开项目文件，例如 `/preview report/index.html`；使用 `/preview artifact:资产ID` 查看普通会话或 Agent 的附件。链接由当前 Runtime 提供，SSH 场景通过已有连接访问。VS Code 侧栏支持选择／粘贴图片、附件重试及浏览器预览；单个附件上限为 16 MiB，更多格式查看可使用 Web／桌面界面。

标准 MCP 的结构化数据、图片和嵌入文本资源会保存为可预览资产，工具历史保留稳定引用；私有 `_meta` 不作为公开结果展示。这不等于实现所有厂商的原生 UI 协议。

### 3.5 设置语言模型与图片模型

设置 → 模型分为“语言模型”和“图片模型”两个页签。语言模型供会话与 Agent 共用；提供商记录连接、密钥、协议 profile 和可选型号。图片模型配置独立的名称、协议、URL、API key 与型号，Responses 图片协议还需主模型。可以一次性导入已有提供商的连接值，保存后各自独立。

不需要用户查找“服务 ID”，界面使用名称和型号。图片尺寸／数量等由实际请求与服务能力决定，普通设置不要求逐项维护复杂能力表；计费信息是可选项。模型配置通常用于新任务；HTTP 代理、钥匙串凭据等关联变更可能需按界面提示重连。正在执行的任务使用已接受时冻结的配置。

语言模型连接测试会发起一次最小推理请求，可能计费；它不证明工具、多轮或图片能力都可用。刷新图片目录不执行生图。模型详细配置见 §9.1，图片 YAML 示例见 §9.2。

### 3.6 斜杠命令：`/plan` · `/goal` · `/skill`

普通 Agent 的聊天、编码和分析使用同一执行流程，不再选择 CHAT／CODING。普通任务因必需信息缺失或达到本轮限额停止时，界面显示“本轮未完成”并保存成果，补充后可发送下一轮。Goal 则保留目标运行，补充信息或调整预算后恢复。 在 Web／TUI／IDE 恢复时可使用当前界面接收后续具体审批，无需为了恢复而扩大任务权限。CLI 对未完成／受阻返回非零退出码，并保留可恢复 Goal。

WebUI 与 TUI 共用同一套斜杠命令（服务端统一解析，行为不漂移）。在输入框**以 `/` 开头**即弹出补全：↑↓ 选择、Tab/Enter 选中、Esc 关闭；输入 `/skill ` 后会二级补全技能名。TUI 下同样可用（见 §5.2），还可 `/help` 查看。

#### `/skill <name> [input]` —— 引用技能
- `/skill`（无参）：列出全部技能（名称 + 简介）。
- `/skill <name> <你的输入>`：把该技能的 `SKILL.md` 正文**预注入**到本轮，再带上你的输入执行。例如 `/skill web-research 调研 2025 年 LLM 推理优化进展`。省略输入则等价于"按上述技能执行"。

#### `/plan [task]` —— 先出计划、批准后再执行
强化版计划模式，适合重构 / 迁移 / 多文件或破坏性改动：
1. `/plan 重构鉴权模块`（或不带任务先 `/plan` 再描述）→ 进入 **plan 模式**：agent 只能用只读工具探索，写 / 执行工具被挡。
2. agent 探索完成后调用 `submit_plan` 提交计划 → WebUI 弹出**计划审批卡片**（渲染计划 markdown + 一个反馈输入框）。
3. 你选择：
   - **批准执行** → 退出 plan 模式，计划步骤自动写入待办清单（todo），agent 开始执行。
   - **打回修改** → 在反馈框写意见后打回，agent 留在 plan 模式按反馈修订并重新 `submit_plan`。
4. 若你想放弃计划模式，输入 `/plan cancel`（也支持 `/plan off` / `/plan exit` / `/plan stop` / `/plan clear`）。这只退出 plan 模式，不会执行计划。
> 普通交互任务的 Plan 需要你审阅；Goal 默认自主制定、调整并执行内部计划，不要求人员确认。已有 `/plan` 门槛或明确要求人工审阅时仍会等待。定时、网关和一次性脚本也显式采用自主计划策略；没有回复通道本身不代表批准。计划通过不会提高文件、命令或路径权限。计划文件仍保存到 `<dataDir>/agent/plans/<会话>/plan.md`，待审阅状态在重启后保留。

#### `/goal <objective> [+budget]` —— 自动续跑直到达成
让 agent **反复自我接力**完成一个目标，而不是只跑一轮：
- `/goal 把订单服务的单测覆盖率提到 80% +200k`：设定目标，可选 `+200k` / `+1.5m` 指定累计 token 预算。
- agent 每轮做完会自动**完成审计**（把"做完了"当未证实，逐条找证据核验），没达成就继续下一轮；对话滚动区下方的固定执行栏显示 **Goal/Todo 进度**（第 N/上限轮、已用 token、状态），流式思考出现或归档时不会把进度卡上下挪动。
- 终止方式：模型提交 `update_goal(complete)` 后由服务端验收；同一阻塞连续三个 Step 提交后进入阻塞；或触达用户显式设置的轮次、token、调用次数、费用或时间预算。默认不设置 Goal 总预算，Todo/文件变更统计不变只作提醒，不自动终止任务。
- 管理：`/goal` 查看当前状态与进度；`/goal pause` 暂停、`/goal resume` 恢复（恢复曾受阻的目标会重新计阻塞）、`/goal clear` 终止。
- 每轮是独立的持久 `GOAL_STEP`，不会用一个长期 while 持续占用 worker；Pause/Resume、Runtime 重启和
  Workspace 切换都保留同一个 `runId`。重开只恢复为可继续状态，**不会自动烧 token 或重放未知副作用**。
- 结构化 Goal 可配置 FILE_ASSERTION、TODO_COMPLETE、预配置 VERIFY_CHECK 和 USER_REVIEW。模型调用
  `update_goal(complete)` 只是提交完成申请；required criterion 未通过时服务端不会标记 COMPLETED。
- 固定执行栏显示 turns/model calls/tool calls/token/cost 与 criterion 结果。未配置可靠价格时不会显示
  `$0.0000` 假费用；使用 `costBudget` 时若当前 provider/model 缺少数值价格，启动会直接拒绝。
- 达到预算进入 `BUDGET_LIMITED`，不会伪装完成；PATCH Goal 提高预算后可继续同一 Run。无机器判据或
  USER_REVIEW 会进入 `READY_FOR_REVIEW`，用户可确认完成或提交反馈继续。
- Goal 总预算由 `harnex.goal.max-turns`、`harnex.goal.default-token-budget`、`harnex.goal.wall-clock-budget-ms` 配置，默认均为 `0`（不限）；已有 Goal 保存的预算继续生效，可将数值改为 `0` 取消限制。单步执行边界用于保存进度并续跑，不是 Goal 总轮次上限；计划审批等待上限由 `harnex.plan.review-timeout-ms`（默认 30 分钟）配置。

> **安全提示**：`/goal` 会自主连续消耗 token，务必善用 `+budget` 与 `max-turns`；目标文本按"不可信数据"处理，不会覆盖系统提示 / 工具权限。

## 4. 进阶功能

### 4.1 记忆系统（Core Memory）

Harnex 的长期记忆与项目上下文使用 **4 类 Markdown 文件**，分别保存项目约定、用户偏好、项目事实和经验。各文件的维护者、作用域与加载规则如下：

| 文件 | 谁写 | 路径 | 作用域 | 加载规则 |
|---|---|---|---|---|
| `AGENTS.md` | 人 | `<workspace>/AGENTS.md` + `~/.harnex/AGENTS.md` | 项目 + 全局 | **项目优先，全局兜底**（first-wins） |
| `USER.md` | 人 | `<dataDir>/memory/USER.md` + `~/.harnex/USER.md` | 项目 + 全局 | **项目优先，全局兜底**（first-wins） |
| `MEMORY.md` | agent | `<dataDir>/memory/MEMORY.md` | 仅项目 | 单一来源（绑 dataDir） |
| `LESSONS.md` | agent | `<dataDir>/memory/LESSONS.md` | 仅项目 | 单一来源（绑 dataDir） |

**分工边界**（一句话：人写偏好放全局，项目事实进项目，agent 自管的事实/失败留 dataDir）：

- **全局 `~/.harnex/USER.md`** —— 你这个人的偏好：语言、回复风格、commit 模板、安全红线。换项目不变。
- **全局 `~/.harnex/AGENTS.md`** —— 你这个人的工作流默认值：默认审批模式、跨项目通用约定。被 `harnex init` 当作种子复制到新项目。
- **项目 `<workspace>/AGENTS.md`** —— 这个项目的事实：技术栈、构建命令、测试基线、目录约定、雷区。**进 git，团队共享**。
- **项目 `USER.md`**（可选） —— 仅在某个项目需要覆盖全局偏好时手工创建（不会被自动创建，否则就永远屏蔽了全局兜底）。
- **项目 `MEMORY.md`** —— agent 自己沉淀的、这个项目里证实过的事实。
- **项目 `LESSONS.md`** —— agent 这个项目里踩过的坑（loop 异常 / max_iterations 触顶时也会自动追加一条）。

**加载行为**：

- 每条新对话首条 system message 会把 USER.md + MEMORY.md + LESSONS.md（来自 `CoreMemory`）和 AGENTS.md（来自 `WorkspaceContext`）**全部拼接**，外加 SKILL 摘要。
- 每个 .md **硬上限 3500 字符**（AGENTS.md 16 KB），超出在末尾追加 `[TRUNCATED — curate this file]` / `[...truncated at N/M bytes...]`。
- `memory_remember` 新增事实遵守 3500 字符注入上限，重复事实不重复保存，容量不足时保留既有事实并要求整理。可用 `replaces` 显式纠正一条同作用范围的旧事实；已有较长文件允许不增加长度的纠正。`LESSONS.md` 仍在达到 7000 字符后清理最早的教训条目。
- 全部用 `<core_memory>` / `<workspace_context>` / `<skills>` XML 标签包裹，闭合标签自动 neutralize，防 prompt injection。
- **跨进程并发安全**：`FileChannel.lock()` 保护，多 JVM 同时跑也不会丢字。

**首次设置（推荐流程）**：

```bash
# 1) 一次性：把你的个人偏好写到全局
harnex init --global              # 生成 ~/.harnex/{AGENTS,USER}.md 模板
$EDITOR ~/.harnex/USER.md       # 改成自己的语言/风格/红线
$EDITOR ~/.harnex/AGENTS.md     # 改成自己的工作流默认

# 2) 每个新项目：种子化项目 AGENTS.md
cd my-project
harnex init                       # 自动以 ~/.harnex/AGENTS.md 为种子复制一份
$EDITOR AGENTS.md                # 在尾部填项目栈/构建命令/测试基线/目录
git add AGENTS.md && git commit  # 提交给团队
```

种子化后的 `AGENTS.md` 顶部有 `<!-- seeded from ~/.harnex/AGENTS.md @ <date>; not auto-synced -->` 标记；**全局后续修改不会自动同步**到老项目（这是有意设计，agent 不应静默改用户已编辑过的文件）。

**agent 自管的写入**：

- `memory_remember` → 新增去重后的事实；可传 `replaces`（不含 `- ` 的完整旧事实）做原子替换，避免旧约定与新纠正并存。只替换同一任务/作用范围内的旧事实。
- `lesson_record` → LESSONS.md 追加带日期的 bullet。
- `memory_forget <substr>` → 删除匹配的第一条 bullet。
- `memory_list` → 返回 USER.md + MEMORY.md 内容（审计用）。

连续对话切回旧话题时，普通会话与 Agent 都可以按需从原始档案取回有关片段；不会为每轮对话增加一次记忆模型调用。召回内容附在触发它的用户轮次上，后续重建保持相同内容与位置，重复来源不重复注入。近期原文已足够时不增加召回正文。

项目 Agent 的 `session_search` 默认搜索当前会话有效分支，也可显式指定同一项目下的 `conversationId`。结果带原始消息/执行记录 ID 和命中偏移；用 `session_read` 指定 `messageId` 或 `executionRecordId` 读取原文，长内容通过 `nextOffset` 继续读取。未压缩的相同读取结果仍可见时会提示复用，压缩后允许重新读取；不会将另一分支或尚未完成步骤的工具结果当成当前事实。

当前会话的约束、参数和纠正可以使用 `session_fact` 登记，包含原文来源、版本和适用范围；`list` 返回完整引文并支持分页。需要替换旧记录时显式指定 `supersedes`，只影响当前分支和对应范围，不修改跨会话的 `MEMORY.md`。`memory_remember` 继续用于未来会话需要复用的偏好或项目知识。

普通会话不提供 `session_fact` 工具循环，但普通会话和 Agent 都可在已有摘要调用中顺带提取事实候选。后端只接受该次输入中能核验的 USER 原文；自动记录的 `registration=summary_candidate` 表示模型提取建议，不代表用户批准或语义判断完全正确。摘要关闭、失败或没有返回合格候选时保留提取缺口，仍可从历史原文回查，不会为每轮对话增加一次额外模型调用。开发者也可通过 `GET/POST /api/v1/conversations/{id}/facts` 查询或显式登记。
- AgentLoop 触顶 / 异常 finally 块会自动 `lesson_record` 一条诊断。

**人工修改**：可直接编辑并保存这些 .md 文件，存储内容无需重启即可读取。已有会话保留稳定的系统提示词前缀，不会每轮重新复制文件全文；需要核对当前记忆时使用 `memory_list`，需要当前项目规则时读取对应文件。AGENTS.md 改动可调用 `POST /api/v1/workspace/reload` 刷新工作区读取缓存，不能将其理解为已发送系统前缀会自动改写。

### 4.2 项目上下文：AGENTS.md

让 agent **每次 session 启动**就知道你这个项目的 README / 约定 / 注意事项，不用每次重复说。

发现优先级（**高→低**，第一个命中即停止）：

1. 配置项 `harnex.workspace.root` 指定的项目根下的 `AGENTS.md`
2. 环境变量 `HARNEX_WORKSPACE` 指定的目录下的 `AGENTS.md`
3. JVM 启动 cwd 下的 `./AGENTS.md`
4. 用户全局回退 `~/.harnex/AGENTS.md`

**容量**：≤ 16 KB（按行截断，超出会标记 `[...AGENTS.md truncated at N/M bytes...]`）。

**生成方式**：

- `harnex init` —— 在 cwd 写 `AGENTS.md`；若 `~/.harnex/AGENTS.md` 已存在，则**以全局为种子**复制并追加项目占位段，否则用内置模板。
- `harnex init --global` —— 一次性写 `~/.harnex/{AGENTS,USER}.md` 两个模板（已存在则跳过，`--force` 可覆盖）。
- `harnex init --force` —— 覆盖项目根已有 AGENTS.md。

**典型用法**（项目根目录的 `AGENTS.md`）：

```markdown
# 项目：Harnex

## 约定
- 所有后端代码在 backend/，前端在 frontend/。
```

### 4.2.1 工作区与文件访问分区

Harnex 始终围绕一个 project root 工作。project root 的来源按优先级为：

1. 桌面版“打开文件夹”写入的 `HARNEX_WORKSPACE`；
2. `agent-config.yml` 的 `harnex.workspace.root`；
3. 进程启动目录 `user.dir`。

文件类工具（`file_read` / `file_write` / `file_edit` / `bash` / `glob` / `grep`）都以这个 project root 为默认工作区。工程外路径按三色分区处理：

| 分区 | 范围 | 读 | 写 |
|------|------|----|----|
| 🟢 **GREEN** | 工程目录内 + 当前会话 uploads + 通过敏感/私有数据检查的系统临时目录 | 放行 | 不额外触发工程外审批，仍受普通工具权限约束 |
| 🟡 **YELLOW** | 其他工程目录外、非敏感路径 | 放行 | 默认逐次询问；也可配置为始终拒绝或跟随线程权限 |
| 🔴 **RED** | 命中敏感清单（`~/.ssh`、`*.pem`、`.env`、`.aws` 等） | 拒绝 | 拒绝 |

对应配置（默认值已覆盖常见机密，一般无需改）：

```yaml
harnex:
  workspace:
    root: D:/code/my-project      # 留空 = 进程启动目录 user.dir
    outside-write-policy: ask     # 普通工程外写入；系统临时目录例外。deny=拒绝；ask=逐次询问（默认）；allow=跟随线程权限
    # sensitive-globs: [...]      # RED 区清单，覆盖即整体替换（见 agent-config.example.yml）
```

> **注意**：工程**内**的同名机密（如仓库里的 `.env`）仍可被 agent 读取（GREEN），但默认禁止改写——那由 `.harnexignore` / `harnex.safety.protected-globs` 这层保护（见 [§4.5.1](#451-harnexignore-与编辑安全)）。RED 分区只在**工程外**生效。
>
> **无需维护路径白名单**：系统临时目录已有内置例外。其他工程外路径使用 `ask` 时，授权对象是当前这一次工具调用；工程外审批不会显示“始终允许”，服务端即使收到 whitelist choice 也只放行本次。它适合同步修改相邻仓库或用户临时指定的输出路径。设置页的“安全与权限 → 工程外写入”可切换三态，保存后用于新任务，当前任务保持原快照。无人值守任务无法回答询问，因此 `ask` 不会自动放行其他工程外写；确实需要时应显式选择 `allow`。
>
> **快照**：Harnex 不会把整棵工程树打成 tar 归档。它只保存会话状态和 AI 实际触碰文件的 before blob；新建文件记录为“回滚时删除”，删除/修改已有文件才保存原内容。工程长期版本管理仍交给你自己的 Git。



放置位置：`./.harnex/skills/<slug>/SKILL.md`（启动时扫描，深度 ≤ 3）。

每个 SKILL.md 用 YAML front-matter 声明元信息：

```markdown
---
name: web-research
description: Multi-source research with citation capture
when_to_use: Tasks needing > 3 web fetches
---

# How to: Web Research

1. 先用 `web_fetch` 拉一篇综述类页面...
```

- **进 prompt 的只是 header**（`name` + `description` + `when_to_use`）—— 200 个 skill 和 20 个 skill 在 token 上几乎无差。
- **完整 body 按需展开**：agent 调 `skill_read("web-research")` 才读全文。
- **运维**：放完文件后用 `POST /api/v1/skills/rescan` 重扫，或前端"设置 → 技能"页一键 rescan。
- **只读保护**：agent 只能经 `skill_read` 工具按名只读加载 skill，不能通过 `file_write` 写入（skillsDir 在工程根外时是 YELLOW，写入遵循 `outside-write-policy`；在工程根内时受 `PathProtection` 写保护）。

### 4.4 三类内容的优先级与覆盖关系

> 一句话：**三者全部叠加注入到 system，没有谁覆盖谁。** 区别在于"谁写"和"作用域"。

| 类型 | 谁写 | 作用域 | 适合内容 |
| --- | --- | --- | --- |
| `USER.md` | 用户为主 | Workspace Profile 优先、用户 Profile 兜底 | 个人偏好、习惯、关于我 |
| `MEMORY.md` | agent 为主 | 当前 Workspace，跨该项目的会话 | agent 学到的项目事实、约定的"硬记忆" |
| `LESSONS.md` | agent 自动 + `lesson_record` | 当前 Workspace，跨该项目的会话 | 失败教训、反模式 |
| `AGENTS.md` | 项目维护者 | 当前项目（按 `HARNEX_WORKSPACE` / cwd 决定） | 项目约定、本仓库特殊规则 |
| `SKILL.md` | 技能作者 | 用户 + Workspace；同名 Workspace 优先 | 可复用的标准化步骤化方法 |
| `ConversationThread.messages` | 用户 + agent | **当前 thread**（不跨会话） | 这一次对话的上下文 |

### 4.5 历史记录与全文搜索

- **用户档案完整持久化**：`<dataDir>/conversations` 保存消息、回合与分支，`indexes/conversations` 保存搜索；Agent 执行上下文另在 `agent/threads`。
- **侧边栏按页列出**：元数据按更新时间排序，正文仅按需加载。
- **搜索**：侧栏搜索 → `GET /api/v1/conversations/search?q=…&limit=20`，CJK + 拉丁双模分词。
- **工具历史详情**：折叠卡片使用摘要，展开时通过 `GET /api/v1/runs/{runId}/tools/{seq}` 按需加载实际参数与结果。详情单独持久保存，重启后仍可读取；摘要不计作完整输出的字符数。已有对话可从尚保留的执行记录恢复详情，记录缺失时会明确提示，不把摘要冒充完整结果。
- **快照与回滚**（FR-21）：每次写工具批次之前自动创建恢复点；每会话默认保留 50 个，旧恢复点按 LRU 清理。
  - UI/TUI：恢复点会显示涉及文件、增删行、`verified/partial/unverified` 覆盖度和 warning；Goal 模式额外提供“回到 Goal 开始前”。
  - 文件语义：新建文件回滚时删除；修改/删除已有文件时写回 before blob；超大文件、忽略目录、不可读文件会标记 skipped。
  - bash 语义：git 仓库下会用 git status 兜底捕获 tracked 变化和新 untracked 文件；简单 `rm -rf dir` / `rmdir dir` 会受限递归保护目录内普通文件；复杂 shell、变量、通配符、远端副作用只做 best-effort 并标记 partial/unverified。
  - REST：`GET /api/v1/agent/conversations/{tid}/snapshots`、`POST /api/v1/agent/conversations/{tid}/snapshots/{seq}/restore-plan`、`POST /api/v1/agent/conversations/{tid}/snapshots/{seq}/restore`、`POST /api/v1/agent/conversations/{tid}/snapshots/{seq}/branch`
- **编辑安全防护**（事前防护，配合快照的事后回滚）：
  - **读取窗口与去重**：`file_read` 单次默认读取 2 MiB（绝对上限 10 MiB）；相同规范化真实路径、读取范围与文件指纹在整个 Thread 的有界读取账本中只完整返回一次，历史压缩不会清空账本。Windows 盘符、Git Bash `/d/...`、斜杠和大小写别名会先解析到真实路径再去重；文件变化或范围变化会自动重读，压缩后确实需要精确原文时可显式传 `refresh=true`。
  - **编辑上下文校验**：`file_edit` / `multi_edit` 直接读取磁盘当前内容核对 `oldStr`；精确匹配或仅换行符不同无需先调用 `file_read`，其他位置的修改不会阻止编辑。宽松空白匹配默认要求最新读取记录；写入前再次检查内容，发现变化则中止。
  - **read-before-overwrite**：`file_write` 覆盖**已存在**文件需要先 read（新建文件无门槛）；明确想无脑覆盖时传 `overwrite=true`。
  - **保护路径**：默认禁改 `.env / .env.* / secrets/** / *.pem / *.key / id_rsa / id_ed25519 / .git/**`；可在 workspace 根加 `.harnexignore`（gitignore 语法）扩展，**编辑文件即时生效**，无需重启。
  - 工程级红线：保护路径**不可旁路**，要改请你自己用编辑器改。
  - 详细行为见 [§4.5.1 .harnexignore 与编辑安全](#451-harnexignore-与编辑安全)。
- **历史压缩**：按实际模型可用输入窗口触发；soft/hard 水位默认为 75%/90%，请求前（含纯对话）和工具批后检查。40% 是理想回落目标，已腾出足够工作空间也算有效。压缩之间还要求足够的新上下文，避免短时间反复 compact；窗口充足时保留原文。
- **回答 Agent 提问**：有明确备选方案时显示 2–3 个选项，每项包含简短标题和一句说明；推荐项仅作标记，不自动提交。选择后点击“提交回答”，也可选择“自定义回答”输入多行文字（Ctrl / ⌘ + Enter 提交）。需要填写目录等具体信息时直接显示输入框，不凑选项。提交期间防止重复发送，失败后保留回答并允许重试。
- **取消进行中的 agent**：UI 红色 "STOP" 按钮 → `POST /api/v1/runs/{runId}/cancel`，秒级生效；断开 SSE 订阅本身不会取消 Run。

### 4.5.1 `.harnexignore` 与编辑安全

文件工具、命令的 `cwd` 和写入检查共享路径解析：优先使用项目相对路径；`cwd` 也接受工作区内的绝对路径，但仍检查真实路径，不能借助符号链接跳出工作区。Windows 支持原生盘符、UNC，以及 `/d/...`、`/cygdrive/d/...`、`/mnt/d/...` 盘符别名；`C:relative.txt` 这类依赖盘符当前目录的写法会提示改用明确路径。macOS/Linux 使用当前 Runtime 的 POSIX 路径，不会把 `C:/...` 猜成项目文件。

Windows 安装 Git Bash 时，`/tmp` 等挂载路径通过该安装的 `cygpath` 转为真实宿主路径；没有可用转换器时会明确报告路径问题。系统临时目录是内置的路径例外：识别 JVM 临时目录、`TMPDIR`／`TEMP`／`TMP` 指定的实际目录，以及 Unix `/tmp`；即使 `workspace.outside-write-policy` 为 `ask` 或 `deny`，普通临时文件也不触发工作区外写入限制。Docker 的 `/tmp` 同样适用。敏感文件、Harnex 私有数据、工具自身权限和沙箱限制仍然生效；符号链接按最终真实路径判断。不创建额外的任务临时目录，也不增加配置项。错误会区分路径无法解析、受保护路径和工作区外写入。命令行中的 `/c` 等包装器开关和程序可执行文件路径不会被当成写入目标。

`bash` 工具的实际解释器以工具说明为准：macOS/Linux 默认 `/bin/sh`；Windows 优先 Git Bash，否则执行 CMD（PowerShell 仅负责 UTF-8 包装）。需要 PowerShell 语法时应显式调用 `powershell.exe -NoProfile -NonInteractive -Command '...'`，从 Git Bash 调用时用单引号包住脚本，避免 `$env:...` 被外层 Bash 展开。不同 shell 的语法不会自动互译；生成文件、截图和临时脚本优先用带引号的项目相对路径，子目录通过 `cwd` 指定。复杂脚本与动态路径的静态检查仍是尽力而为，不能替代操作系统沙箱。

`file_read` 对图片只能提取文字/OCR，不提供视觉判断。`image_inspect` 只会提供给实际支持图片输入的模型（包括切换模型和子任务），参数必须使用已上传或生成图片的资产 ID，不能用文件名或空数组替代。

> **痛点**：AI 这次改 a.txt 时，把上一次（甚至你刚在 IDE 里改的）改动覆盖了。
> **解法**：snapshot 兜底 + 事前防护双管齐下；下面是事前防护的用户侧约定。

**内置文件保护**（由文件工具执行，不提供全局关闭开关；设置页可展开“文件保护说明”查看）：

1. `file_edit` / `multi_edit` 可用包含足够上下文的 `oldStr` 直接编辑；未读或读取记录过期时，只接受精确匹配及换行符差异，不做宽松空白匹配；
2. 文件其他位置被修改后仍可编辑；目标不匹配、有歧义或写入前内容再次变化时中止并提示重读。`multi_edit` 任一片段失败，整次调用均不写入；覆盖整个文件的 `file_write` 仍需最新读取记录或显式 `overwrite=true`；
3. 以下路径默认禁改：`.env / .env.* / secrets/** / *.pem / *.key / id_rsa / id_ed25519 / .git/**`。

**自定义保护**——在工程根（= 你打开的工程目录 / `HARNEX_WORKSPACE` / 进程工作目录）放一个 `.harnexignore`，gitignore 语法：

```gitignore
# 不让 agent 碰生产配置
config/prod.yml
config/prod.*.yml

# vendor 目录整体只读
vendor/

# 但 vendor 里这个文件允许改（取反）
!vendor/our-fork.js

# 任何深度的 *.lock 都保护
*.lock
```

**保存即时生效**，agent 不需要重启；按 mtime 缓存重载。

**文件工具不能用 `force=true` 绕过保护路径**。这些规则约束 `file_write`、`file_edit`、`multi_edit` 等文件写入流程，不构成对任意 Shell 程序的 OS 隔离。获准执行的 host 命令仍可能修改项目文件；命令审批与按需隔离需分别配置。需要修改受保护文件时，应由用户明确决定并在编辑器或受控流程中处理。

**对模型可见的错误信息**（直接出现在工具结果里，模型自己会"想办法"）：

| 触发 | 错误内容（节选） | 模型一般如何反应 |
|------|----------------|-----------------|
| 目标片段不匹配或有歧义 | `oldStr not found` / `oldStr matches ... times` | `file_read` 后使用当前片段及周边上下文重试 |
| 编辑准备期间文件又被改了 | `refusing edit: file changed while preparing the edit; no changes written` | 重读后基于当前内容重试 |
| 命中保护 | `refusing to edit protected path: ... (matched .harnexignore or harnex.safety.protected-globs)` | 换路径 / 报告需要人介入 |

**配置全清单**（`agent-config.yml` 里 `harnex.safety.*`，全部可选）：

```yaml
harnex:
  safety:
    respect-ignore-file: true             # 默认 true；关掉就只看下面的 protected-globs
    tracker-max-entries-per-thread: 256   # 每会话记忆最多几个文件读取戳
    protected-globs:                      # 静态保护规则；与 .harnexignore 合并为一份有序规则表（last-match-wins），
                                          # 静态规则在前、.harnexignore 在后；.harnexignore 里的 `!pattern` 可反选（解除）
                                          # 上面的静态规则。注：root 的 .harnexignore 文件自身受写保护，agent 工具改不了。
      - "**/.env"
      - "**/.env.*"
      - "**/secrets/**"
      - "**/*.pem"
      - "**/*.key"
      - "**/id_rsa"
      - "**/id_ed25519"
      - "**/.git/**"
```

**与 Git 的关系**——Snapshot 不替代 Git，也不把 Git 暴露成专用模型工具：

- `.git/**` 默认禁止通过文件写入工具直接修改；获准运行的 `git add`／`git commit` 等命令仍会更新 Git 元数据；
- agent 想看历史可以主动 `bash git diff HEAD` / `git log`，这仍然只是 bash 能力；
- Harnex 内部会用 `git status --porcelain=v1 -z` 做 bash 副作用兜底：捕获 tracked 文件变化、新 untracked 文件和 `git_head_changed` warning；
- **推荐工作流**：你的 workspace 自己 `git init` → snapshot 用于"AI 这一轮做错了，秒回滚"，git 用于"我对这一阶段满意了，提交一下"。两者职责正交，互不干扰。

### 4.3 子 Agent（Subagent Delegate）

主 Agent 可通过两种方式发起子 Agent：

**方式一：LLM 自主调用 `delegate` 工具**（推荐）

Agent 在对话中判断需要子任务时，自行调用 `delegate` 工具：
- `goal`：子任务描述
- `completionCriteria`：必填的可观察完成条件，例如“返回命中规则的文件列表与对应行号”；达到后立即停止
- `context`：传递给子 Agent 的背景信息
- `toolsets`：可选，指定子 Agent 的工具集（默认 `default`）
- 子 Agent 不提供独立模型选择：始终继承当前对话的 Provider、模型与 reasoning 配置，避免同一家族执行中静默换模型
- `maxIterations`：可选，只能降低本次子任务上限；省略时使用 `harnex.subagent.max-iterations`（默认 64），显式配置为 `0` 才继承通用 `harnex.max-iterations`

**方式二：REST API 手动触发**

```http
POST /api/delegate
{
  "goal": "用 read 工具集整理一份 2025 LLM 研发大事记。",
  "completionCriteria": "按时间列出事件、来源文件和可供主 Agent 引用的摘要",
  "toolsets": ["read"],
  "maxIterations": 20
}
```

子 Agent 不是 `/goal` 自动续跑任务，而是一次有完成条件的有界 AgentLoop；终态为 `COMPLETE` 或 `BLOCKED`。跑完后只把**最终文本**回传给主线，执行过程通过 Delegate 对应的右侧详情查看，子线程不会出现在普通历史会话或历史搜索中。
子 Agent 的内部计划自行处理，缺少信息或需要审阅的方案先返回父 Agent，由父 Agent 统一协调，避免多个子任务分别向你提问。必要的工具安全审批仍使用父任务的回复通道，且不会扩大权限。交互任务中，子 Agent 的工程外审批显示在父对话，并只授权原 child/call；没有回复通道时不会创建不可见等待，也不会自动授权。直接 `/api/delegate` 默认只读。
子任务默认执行 20 分钟后在下一安全点整理进度，随后可以继续；`timeout-ms=0` 默认不设本地硬执行时限，排队默认最多 2 分钟且不占执行预算。64 轮模型迭代上限仍独立生效。若显式配置硬时限，临近上限时系统尝试交还完成内容、证据和剩余工作；时间/迭代不足使用 `BUDGET_EXHAUSTED`，不冒充完成，也不等同于缺少外部条件的 `BLOCKED`。

普通 Chat 与 Goal 的子任务使用相同规则；Goal 还受整个任务剩余预算约束。Goal 到达时间或资源预算时进入可恢复的 `BUDGET_LIMITED`，修改预算后可继续同一 Run。已有显式 `timeout-ms` 配置保持原值；设为 `0` 只关闭子任务本地硬限制，不关闭父任务、Goal、排队和工具执行器的兜底。执行中的工具、下级委派和审批等待仍计入执行时长。

同一时刻同一线程最多 `cfg.subagent.max-per-thread` 个（默认 3，见 `SubagentLimitMiddleware`）。
`delegate` 工具描述会动态告知模型该上限与显式配置的硬执行预算（默认不设本地时限）；更多任务应等待本波结果后再提交。模型若单轮超额，系统只接纳前 N 个并通过 `delegate_limit_exceeded` 明确要求下一轮补交，其余任务不会静默消失。

### 4.4 MoA（Mixture-of-Agents）

专治"一个模型搞不定"的题目：

```http
POST /api/moa
{
  "prompt": "给出下面需求的 3 种架构选型对比"
}
```

- 先在 `harnex.moa` 中启用并配置 `reference-models` 与 `aggregator-model`，每项使用 `provider/model`。
- 一次并行调用已配置的参考模型，再由聚合模型合成结果；请求只接收提示词，不支持通过 `layers`／`aggregator` 指定多层执行或更换聚合器。
- 当前 Chat 页面没有 MoA 复选框。可调用此 REST 入口，或将 `mixture_of_agents` 加入自定义工具集供 Agent 使用；默认不加入任何预设。

### 4.5 自动化任务

从侧栏的 **自动化** 进入，无需先打开项目。计划和运行结果索引统一保存在用户目录，切换项目不会切换这份列表。

点击侧栏“会话”或“Agent”会进入对应页面，恢复离开前选中的会话、输入草稿和运行状态；尚未选中会话时显示引导页。“新对话／新任务”用于明确开始新的内容。自动化表单有修改时显示“未保存”，页面切换保留草稿，返回后可继续编辑；只有关闭编辑或改为编辑另一份任务、需要丢弃内容时才确认。草稿不会提前修改已保存的计划。

1. 在“做什么”中填写每次执行的完整指令。
2. 在“什么时候”选择每天、工作日、每周、每小时或自定义六段 Cron，确认预览中的下次执行时间与时区。
3. “在哪里执行”默认选**个人**，使用普通文字会话能力；选择**指定项目**后可使用项目 Agent 的工具。个人任务不提供项目文件、Shell 或 MCP 工具。
4. 按需展开“高级设置”修改名称、时区和模型。项目任务额外提供工具集和修改权限；远端模型／Provider 留空时采用远端默认值。新建和编辑时高级设置均默认折叠。
5. 高级设置中可选择先保存为暂停状态，再点“立即执行”验证。手动执行仍遵守任务原有权限，也不会自动启用计划。

**运行条件与任务冲突**：

| 情况 | 行为 |
| --- | --- |
| 个人 Runtime 在线 | 可以执行个人自动化，前台项目切换不影响它 |
| 指定项目未打开或 SSH 未连接 | 显示“等待项目打开”或“等待远程项目连接”，打开或连接后自动继续，不需要重复点击执行 |
| 环境内有其他未结束任务或已排队的用户请求 | 显示“等待当前任务结束”，自动化等待，不并发操作同一环境 |
| 自动化正在执行，用户提交新任务 | 统一准入会提示忙碌；已有提交队列继续等待，可在自动化页取消本次执行 |
| 关闭／切换正在执行任务的项目 | 沿用现有取消流程；计划保留，未取回结果等待原环境恢复，不自动从头执行 |
| 等待期间错过多个计划时间 | 合并为一次待执行，避免恢复后连续补跑 |

暂停取消后续定时和待执行请求，不中断已接受的运行；“取消本次执行”清除等待或请求取消现有 Run；删除计划也会请求取消当前 Run，保留已有结果快照。

每张任务卡片直接展示“最近结果”的输出片段，耗时、估算费用和变更数量放在次要位置；内容不变时不会在每次轮询重新读取结果。点击“全文与历史”在卡片内展开完整输出、文件变更与历次执行位置。费用未知时不会显示为免费。已经保存的结果快照可在项目关闭后查看；尚未取回的结果显示“等待确认结果”，连接恢复后自动更新。失败显示原因并提供“重新运行”，等待或执行中禁用重复运行。每次执行使用独立会话，因此“刚才那个文件”等依赖临时对话的指令需要改为明确来源。

管理和执行仍需要 Harnex 宿主在线。本轮没有新增 Runtime 池、自动打开项目、系统开机服务或应用退出后的常驻行为。

API：

```http
POST /api/cron
{
  "name": "定期汇总",
  "targetId": "personal",
  "cron": "0 0 9 * * *",
  "timeZone": "Asia/Shanghai",
  "prompt": "按这里完整给出的资料和要求生成摘要",
  "toolsets": [],
  "allowMutations": false,
  "disabled": true
}
```

`GET /api/cron/targets` 返回可选环境，项目目标使用返回的 `target.id`。带 `id` 的 POST 更新原计划；服务端维护运行时间和计数。

| 接口 | 用途 |
| --- | --- |
| `GET /api/cron` | 全局列表、目标在线状态、等待原因和最近结果 |
| `POST /api/cron/preview`，正文 `{cron, timeZone}` | 时间预览 |
| `POST /api/cron/{id}/enabled`，正文 `{enabled}` | 暂停／恢复计划 |
| `POST /api/cron/{id}/run` | 加入一次待执行请求，重复等待或执行返回 409 |
| `POST /api/cron/{id}/cancel` | 取消本次等待或执行 |
| `GET /api/cron/{id}/history` | 最近运行记录 |
| `GET /api/cron/results/{attemptId}` | 已归档的结果快照 |
| `DELETE /api/cron/{id}` | 删除计划 |

计划和执行认领保存到 `<userDataDir>/automation/state.json`，结果快照位于同目录的 `results/`。写入失败返回错误并保留原计划，不误报保存成功；Agent 文件工具不能访问或改写这些调度控制文件。

项目执行仍受 `harnex.cron.allowed-toolsets`、`max-jobs`、每个任务的 `allowMutations` 和路径权限约束。系统临时目录以外的普通工程外写入还需要 `outside-write-policy=allow`；无人回复不构成授权。Cron 不创建或启动 Goal。项目任务可按需开启“IM 提醒”，选择每次完成／失败或仅失败；个人自动化不提供通知。通知沿用执行项目的默认已授权会话，详见下文 IM 客户端。

### 4.6 工具输出预算 / 审批

工具输出的界面预览与模型输入使用独立预算：

1. 超过 `harnex.budget.per-tool-chars`（默认 8000 字符）时，将经配置脱敏的完整输出保存到 `<sharedDataDir>/agent/tool-results/<threadId>/<sha>.txt`，界面使用 `preview-chars`（默认 1200）预览和 `persistRef` 引用。
2. 模型优先读取独立的 `llmContent`，默认单工具上限 `per-tool-chars-for-llm=100000`；在该上限内仍可收到完整内容，不能用界面预览长度估算模型消耗。
3. 单轮界面预算为 `per-turn-chars=30000`，模型聚合预算 `per-turn-chars-for-llm=0` 默认不额外限制；模型上下文水位和摘要仍生效。工具全文通过 `/api/tools/result/{threadId}/{ref}` 读取，与会话图片的资产接口区分。

审批有三档：`bypass` / `default` / `strict`（在 `agent-config.yml → harnex.approval.mode`）：
- `default`（默认）：把决策交给**线程级 permission-mode**（`ask` / `accept-edits` / `yolo`）；命中危险正则始终先 DENY。
- `strict`：**所有**工具调用都必须 ASK，不再看线程 permission-mode（用于审计强约束环境）。
- `bypass`：所有非危险工具自动 ALLOW（仅研发调试用）；命中危险正则仍 DENY。

`outside-write-policy=ask` 是比上述模式更外层的跨工程边界：即便线程为 `yolo` 或全局为 `bypass`，
普通工程外写仍逐次询问；系统临时目录属于内置例外，直接交回普通工具审批模式。其他目录只有显式选择 `outside-write-policy=allow` 才交回普通审批模式。

**重要**：dangerous-pattern 拒绝是**最后一道保险丝**，不受 mode 影响。内置 deny 列表故意写得很窄，只覆盖“任何情况下都不该自动执行”的灾难命令（`rm -rf /` / `/home` / `/etc` / `$HOME`、`mkfs.*`、`dd of=/dev/sdX`、`curl|sh`、`chmod -R 777 /` 等 root-ish / 不可恢复目标），**不**拦截 `rm ./tmp.txt`、`rm -rf ./build` 这类工作区内删除——后者走 ASK，由用户在前端确认。运维场景需要批量删除某些固定目录时，建议封装专用工具（带 dry-run + allowlist 根 + 显式审批），不要扩宽内置 denylist。

`harnex.approval.dangerous-patterns` 现在是**追加模型**——你写的规则会**追加**到内置硬化基线上，不再静默覆盖。如确实需要放宽某条内置规则，显式设置 `harnex.approval.replace-default-patterns: true` 并提供完整列表（启动会打 WARN）。

审批请求通过 SSE `approval_required` 事件推给前端。点击回应走 `POST /api/v1/agent/conversations/{threadId}/interactions/{callId}`（kind=approval）。

### 4.7 细粒度钩子（Hooks）

钩子在 Agent 工具执行的**每个调用**前后触发，提供比中间件更精细的控制：

| 钩子 | 触发时机 | 能力 |
|------|---------|------|
| `preToolCall` | 每个工具执行**前** | 审计日志、修改参数、拦截执行（veto） |
| `postToolCall` | 每个工具执行**后** | 检查/修改结果、通知 |
| `onError` | Agent 循环异常时 | 错误日志、告警 |

完整中间件链（7 段）执行顺序：

```
before → [LLM调用] → afterLlm → preToolCall → [工具执行] → postToolCall → afterTools → after
                                                                              ↑ onError（异常时）
```

**配置方式**：在 `agent-config.yml → harnex.hooks.rules` 中添加规则：

```yaml
harnex:
  hooks:
    rules:
      # 审计所有工具调用
      - name: audit-all
        phase: preToolCall
        tool-pattern: "*"
        action: log

      # 拦截包含 rm -rf / 的 bash 命令
      - name: block-dangerous-bash
        phase: preToolCall
        tool-pattern: bash
        action: veto
        veto-reason: "Bash blocked by hook policy"
        args-match: "rm\\s+-rf\\s+/"

      # MCP 工具调用完成后通知前端
      - name: notify-mcp-calls
        phase: postToolCall
        tool-pattern: "mcp__*"
        action: notify

      # 记录 Agent 循环错误
      - name: log-errors
        phase: onError
        action: log
```

**规则字段说明**：

| 字段 | 说明 |
|------|------|
| `name` | 规则名称（用于日志标识） |
| `phase` | 触发阶段：`preToolCall` / `postToolCall` / `onError` |
| `tool-pattern` | 工具名匹配模式，`*` 匹配所有，`mcp__*` 匹配所有 MCP 工具 |
| `action` | 动作：`log`（审计日志）/ `veto`（拦截，仅 preToolCall）/ `notify`（SSE 事件通知前端） |
| `veto-reason` | action=veto 时的拒绝理由 |
| `args-match` | 可选，参数正则匹配（仅匹配到才触发） |
| `disabled` | 设为 `true` 可临时禁用规则 |

**查看当前规则**：
- **Web UI**：设置 → 钩子规则
- **REST API**：`GET /api/v1/hooks`

### 4.8 历史压缩（SummarizationMiddleware · 强制开启）

> ⚠️ **此中间件始终启用，无法关闭**。它是长对话防溢出的最后一道安全网。  
> 你能配置的是它的**工作模式**，而不是是否启用。

**为什么强制开启**：Agent 在多轮工具调用中不断累积消息，如果不压缩，长对话会触达模型 context window。`SummarizationMiddleware` 在工具批后检查 soft token 水位、每次模型调用前检查 hard token 水位，并用最近一次 Provider 上报的 prompt usage 校准本地估算；超过阈值时把“受保护的原始请求 + 早期对话摘要 + 最近 N 条消息”重新拼装为新的 messages 序列。

**两种工作模式**：

| 模式 | 触发条件 | 实现 | 成本 | 何时选 |
|------|---------|------|------|--------|
| **LLM 摘要模式** | `harnex.summarizer.enabled=true` | 调用配置的摘要目标或当前任务模型生成结构化 continuation summary；超时或失败自动回退确定性模式 | 按实际模型尝试计费 | **推荐生产环境**：摘要会成为后续上下文，模型应足够可靠 |
| **确定性模式**（`enabled=false`） | `harnex.summarizer.enabled=false` | 生成同样六段结构，保留 Todo、已检查文件/切片、变更/验证、工具错误与非空 assistant 检查点 | 0 | 离线 / 无可用摘要模型 / 不愿额外花钱时；仅保存可确定提取的事实，不等价于语义摘要 |

**关键参数**（写在 `agent-config.yml → harnex.summarizer`）：

| 配置 | 默认值 | 说明 |
|------|--------|------|
| `enabled` | `true` | `true` 启用 LLM 摘要（默认）；`false` 走确定性结构化 digest |
| `provider` | *(空)* | 留空优先使用当前任务实际 Provider/Model；填写则将该端点作为摘要首选目标 |
| `model` | *(空)* | 配合显式 provider 覆盖其 `default-model`；只填 model 时使用路由默认端点 |
| `context-window` | `128000` | 模型和 Provider 均未声明窗口时的回退预算；优先模型，其次 Provider 默认 |
| `output-reserve-tokens` | `16000` | 为本轮输出预留，不参与输入水位计算 |
| `safety-reserve-tokens` | `0` | 额外安全余量，实际路由至少预留 256 tokens；工具 schema 已显式计入输入 |
| `soft-threshold-percent` | `75` | 请求前和工具批后的软压缩水位，占可用输入窗口百分比；同时检查新增量 |
| `hard-threshold-percent` | `90` | 下一次 LLM 请求前的同步硬门 |
| `target-percent` | `40` | 压缩后期望回落的水位，必须小于 soft |
| `min-new-tokens` | `16000` | 上次压缩后至少新增多少 token 才允许再次请求摘要 |
| `min-new-context-percent` | `15` | 新增上下文的相对门槛；实现取它与 `min-new-tokens` 中较小者 |
| `minimum-reduction-percent` | `20` | 仍高于 soft 时，降到 hard 内且至少缩减此比例也算有效；回到 soft 内则直接清除失败计数 |
| `max-ineffective-compressions` | `3` | 连续未解除容量压力且缩减不足时请求收尾；真正收尾前重新检查完整请求，硬裁剪、模型切换或工具负载减少后已恢复空间则继续任务 |
| `keep-tail` | `0` | 可选的最近原文条数上限；0 表示仅按 Token 预算保留 |
| `keep-tail-chars` | `0` | 可选的最近原文字符上限；0 表示不额外限字符，Token 预算仍生效 |
| `summary-max-chars` | `24000` | 最终保存的摘要正文字符上限，适用于模型摘要和本地摘要；不含受保护原文、近期历史及独立的事实候选，最小 `256` |
| `max-output-tokens` | `16384` | 摘要生成最高额度；实际按摘要模型剩余窗口与已声明的最大输出缩小，正文、事实候选及模型计入的推理共享此额度 |
| `max-concurrent` | `2` | 普通会话与 Agent 在同一配置版本内共享的摘要并发数；槽位占满时使用本地历史处理 |
| `timeout-ms` | `180000` | 本次压缩的所有摘要目标和格式修复共用的等待预算，不是 TTFT；还有时间时尝试其他目标，耗尽后本地处理，主任务继续 |
| `attempt-timeout-ms` | `90000` | 单次模型调用上限；同时受整次摘要及任务剩余时间限制，已有显式总时限不变 |
| `prefix-reuse` | `false` | Agent 软水位下尝试复用兼容主请求前缀；容量不足、换模型或硬上限/溢出恢复时使用原摘要路径 |

**保留策略细节**：

- 第 0 条 system prompt 和第一条真实用户请求**原文保留**
- 默认按 Token 保留最近原文：先计入系统指令、工具定义、最新用户要求和 Goal 状态，为摘要预留空间；摘要完成后按实际 Token 补回能容纳的最近原文。`keep-tail` / `keep-tail-chars` 仅在大于 0 时作为额外上限。切点按完整工具组对齐，不拆开 call/result 配对，也不丢弃尚未纳入摘要的原文
- 中间部分被替换为单条 `[Compressed history summary]\n<内容>` 的 assistant 消息
- 摘要 prompt 同时参考受保护头部和最近原文，强制按“当前目标、已完成工作、发现与决策、未完成工作、其他历史请求、必须保留的上下文”六段结构生成 continuation state；空白/无结构结果会严格重试一次
- 摘要区分用户已确认的要求、模型建议、工具观察和未验证陈述；数值与单位、环境和计数含义一起保留，未知信息不补成事实。超长时优先保留完整条目，省略明确标记，不把半句话当成完整结论
- Agent 模型摘要会收到脱敏的当前 Todo 状态和成功读取文件/切片记录；当前结构化状态覆盖旧摘要中的待办状态。完整工具参数不进入摘要提示；失败或状态未知的读取不能被标为已检查。
- 已消费的 system/memory/plan reminder 不作为真实用户请求进入摘要；旧大型 tool result 在送入摘要模型前保留头尾并压缩中段
- 确定性模式使用相同六段结构，显式合并受保护的原始请求、上一代六段摘要、当前 Todo 和跨压缩 file-read 账本；只把无 Tool Call 的 assistant 结论作为“未验证 checkpoint”，工具失败取持久 `toolError`，不会因读取到的源码恰好含有错误字样而误报
- 当前 Todo 状态会清理旧摘要里的过期待办；重排或清空后的旧事项作为历史保留，未能核对的事项标记为未知。容量不足时优先保留较新的完整条目；确需摘录较长原文时保留首尾并标记不完整
- 硬阈值的应急裁剪同样保留首尾，便于留下结尾的错误信息或约束；有可用来源时附原文定位，后续可用历史读取工具取回。完整档案不被裁剪
- 压缩日志分别记录 `summarySource=model|deterministic` 与 `sizeEffective`；后者表示是否恢复有效工作空间，不要求必须达到 40%，也不代表摘要语义质量
- `summary-max-chars` 约束最终保存长度，`max-output-tokens` 在请求阶段约束真实生成工作量，两者不可互相替代；摘要 `timeout-ms` 覆盖本次压缩的全部非流式尝试，若任务已有显式时限，再取其剩余时间。它不创建新的任务时限，也不触发任务收口；子 Agent 摘要失败只冷却对应目标，不会永久停用后续模型摘要。
- 摘要请求统一不发送 `temperature`，使用所选模型自己的采样默认值；普通对话摘要和 Agent 摘要使用相同策略，备用模型也不继承采样参数。设置页保留模型摘要开关、Provider 和模型选择，生成上限、整次摘要超时和单次调用超时收纳在“高级限制”中，超时以秒显示。原文条数/字符上限、摘要字符上限、并发数和断路器内部参数只保留配置文件入口。

- 上下文容量依次取 `providers.<id>.models[].context-window`（含内置模型定义）、`providers.<id>.context-window`、全局 `summarizer.context-window`（128000）。Provider 默认只作用于没有模型容量的型号；通用 API 和自定义别名不会自动猜测容量。设置页对已知模型或显式模型覆盖显示只读容量；未识别容量时仅显示简短说明，将“备用上下文容量（Token）”输入收纳在默认折叠的“高级设置”中。模型覆盖可在该 Provider 的高级 JSON 中配置。模型信息显示当前配置的窗口、来源与 Agent 的实际触发阈值。
- 普通聊天与 Agent 共用自适应摘要预算：扣除主模型的必需输入后，摘要块最多使用剩余空间的 25%，普通聊天的近期摘要和更早历史覆盖说明共享这份预算；其余空间用于原文。摘要模型按自己的计数器计算完整请求，生成额度取配置上限、已声明的模型最大输出、剩余上下文空间及本次所需额度的最小值。生成预算为正文、事实候选及可能的推理分别留出空间，这些是规划份额，不保证模型恰好按比例生成。

- `providers.<id>.models[].max-output-tokens` 可填写模型或部署声明的最大输出，并继承同名内置模型定义。它与 `context-window`、摘要的全局生成上限分别表示不同限制；未声明时不会从窗口大小猜测最大输出，仍受配置上限和剩余窗口约束。
- 摘要返回后按主模型计数器和字符上限双重验证。模型输出过长、被上游截断、事实候选结构不完整或来源校验失败时，不靠裁掉模型事实来冒充完整结果；最多尝试完整、约一半、约四分之一的来源范围，并共用原有超时和调用预算。Agent 保留未覆盖的原文，普通聊天按完整轮次选取来源并保留历史覆盖与恢复入口。本地回退按完整条目和省略标记受双重限制；这些检查不能证明所有语义事实都被模型提取。

- 摘要执行器允许最多 `max-concurrent` 个独立 Run 并行且不设等待队列；同一 AgentLoop 的压缩仍然同步串行，槽位已满时快速使用确定性摘要
- 真正触发压缩后，对话区会用同一张活动卡显示“正在摘要对话历史”，history 重写完成后原位更新为“摘要完成”，并标出模型/确定性来源及压缩前后 token；这只是进度可见性，同一 Run 仍会阻塞等待摘要完成。Run 结束后卡片不再黏在最终答复底部，完整记录仍可从本次 Run 活动查看
- AgentLoop 的工具循环保护与压缩反抖动相互独立：短窗口内同一 Tool batch 或同一文件高重叠读取第 3 次复现时先做一次无工具 checkpoint；checkpoint 后再次复现才收尾。连续 12 个只读批次只强制综合、不会单独终止；成功变更会重置进展 epoch，大文件互不重叠的新分页仍视为新证据
- `file_read` 完整读取过且文件指纹未变时，后续改用 `offset/limit` 也会去重；压缩不会清空账本。文件变化自动失效，确需再次取得原文时使用 `refresh=true`
- Run 的最终 Assistant 消息以服务端会话档案为真源；前端在 `done` 后自动对账，因此 SSE `buffer_miss` 或中途恢复不会永久丢失最终输出
- 打开历史会话继续提问时，服务端按当前分支组织上下文，滚动位置和工具详情的展开状态不影响模型取材。Agent 在原分支复用已有执行上下文；切换分支时恢复问答、附件和近期工具结果的有限摘录。历史结果不会重新执行，也不代表当前文件状态；恢复点则保留该时刻保存的执行上下文。

**`summarizer.provider` ↔ `harnex.providers.<id>` 是什么关系？（常见误解）**

`harnex.providers` 是 **LLM 端点 Map**（Map key 是唯一 id）；`harnex.summarizer.provider` 是 **一个字符串引用**，指向其中某个 id——不是重复配置，而是指针。

代码路径：`SummarizationMiddleware.llmSummarise()` → `ProviderRouter.oneShotOn(providerName, model, …)` → `byName.get(providerName).oneShot(model, …)`。`oneShot` 返回文本、实际 Provider/Model 与上游 usage，摘要消耗因此能归入当前 Run/Goal。启用摘要器且显式 `provider` 不存在或已禁用时，启动校验直接报错。

| 配置 | 角色 | 类型 |
|---|---|---|
| `harnex.providers.<id>` | LLM 端点的**定义** | Map key 是稳定标识符 |
| `harnex.summarizer.provider` | **引用**上面某个 name | 字符串 |
| `harnex.router.default-provider` | Auto Chat 默认 Provider；留空取首个启用的非 fallback 端点，不是 failover 列表 | 字符串 |

默认配置提供 `primary`、`fallback`、`anthropic`、`openai-responses` 四个 Map 槽位；`fallback` 默认禁用，配置端点/密钥/模型并将其 `enabled` 打开后才参与自动容灾。摘要目标按以下顺序去重尝试：显式 `summarizer.provider/model`（若配置）；否则当前任务实际 Provider/Model；随后是已启用的保留 fallback；显式摘要目标失败时最后还可回到当前任务模型。每个目标按错误类型独立冷却，配置/鉴权错误冷却较久，瞬时错误指数退避，取消不锁存。

普通会话与 Agent 共用该目标顺序、摘要执行器和目标冷却，默认模型先解析为真实 Provider/Model 再去重；任务已运行在 `fallback` 的其他型号上时，该实际型号仍可作为后备。普通会话会冻结专用摘要目标及连接指纹；摘要端点变化后跳过失效目标，不把排队请求静默送往新端点。全部目标失败、模型摘要关闭或摘要等待预算耗尽后，Agent 使用确定性结构化 digest，普通会话在可用空间内保留带消息 ID/版本的历史引文和近期完整轮次；原始历史仍在档案中。

普通会话缓存摘要只描述被摘要片段当时的目标和未决事项，近期记录及最新用户要求优先；本地引文不推断当前完成状态，省略内容明确标为片段。两条路径的模型摘要用量都计入 Run 汇总，并标为 `summarizer`，不会把主对话模型显示改成摘要模型；上游未返回用量时标记为估算。

下面"最佳实践"中的 **`cheap` 不是关键字**，是用户自定义的第 3 条 provider 名（叫 `tiny` / `summarizer-llm` / `whatever` 都行）—— 增加它的目的是让摘要走完全独立的 Key/账单/速率限额，不挤占主流量。

**生产环境最佳实践**：

```yaml
harnex:
  providers:
    primary:
      profile: openai-chat
      base-url: https://api.openai.com/v1
      default-model: gpt-4o
    cheap:                               # 专门给 summarizer / subagent 用
      profile: deepseek-v4
      base-url: https://api.deepseek.com/v1
      api-key: ${DEEPSEEK_API_KEY:}
      default-model: deepseek-v4-flash
  router:
    default-provider: ""                 # 空=首个启用的非 fallback 端点；也可显式写 Provider id
  summarizer:
    enabled: true
    provider: cheap
    context-window: 128000
    output-reserve-tokens: 16000
    safety-reserve-tokens: 0
    soft-threshold-percent: 75
    hard-threshold-percent: 90
    target-percent: 40
    min-new-tokens: 16000
    min-new-context-percent: 15
    minimum-reduction-percent: 20
    max-ineffective-compressions: 3
    keep-tail: 0
    keep-tail-chars: 0
    summary-max-chars: 24000
    max-output-tokens: 16384
    max-concurrent: 2
    timeout-ms: 180000
    attempt-timeout-ms: 90000
    prefix-reuse: false
```

**环境变量覆盖**：目标使用 `HARNEX_SUMMARIZER_ENABLED/PROVIDER/MODEL`；生成与并发预算使用 `HARNEX_SUMMARIZER_MAX_OUTPUT_TOKENS`、`HARNEX_SUMMARIZER_MAX_CONCURRENT`、`HARNEX_SUMMARIZER_TIMEOUT_MS`、`HARNEX_SUMMARIZER_ATTEMPT_TIMEOUT_MS`；前缀复用开关为 `HARNEX_SUMMARIZER_PREFIX_REUSE`。其他 token 水位、最小新增上下文和 tail 参数仍通过 YAML 配置。

> ⚠️ 这里写的 `cheap` 必须真实存在且启用于 `harnex.providers`。错误引用会阻止启动；运行期上游超时或失败仍会由摘要器回退到确定性摘要。

**常见疑问**：

- **Q：能彻底关掉吗？** 不能。`enabled=false` 只是切换到不调用模型的确定性结构化 digest，压缩动作仍会发生。
- **Q：压缩会不会让 Agent 忘记早期工具结果？** 会丢失原文细节，但 LLM/确定性模式都保留结构化 continuation state，后者还能提取已检查文件。若需保留更多原文，可将 `keep-tail` / `keep-tail-chars` 设为 0 去掉额外限制，或在容量允许时提高 `target-percent`（仍须小于 soft）；不要降低最小新增上下文门槛来制造频繁摘要。
- **Q：摘要器自己会不会调用工具？** 不会。`router.oneShotOn(...)` 只走单轮 chat completion，不挂任何 tool schema。
- **Q：LLM 摘要失败怎么办？** 当前目标失败后先尝试可用 fallback/任务模型；所有目标不可用才回退确定性结构化 digest。不是“一次失败后本 Run 永久禁用”：每个目标按错误类型冷却，后续达到水位时可恢复探测。

## 5. CLI / TUI 模式

> **CLI vs TUI 概念澄清**：
> - **CLI** 是广义命令行接口 —— 含 `harnex serve` / `harnex stop` 这类一次性子命令、以及 `harnex cli -p "xxx"` 一句话执行（脚本/CI 友好）。
> - **TUI** 是 Rust/Ratatui 实现的交互客户端 —— 显式执行 `harnex tui`，提供固定 Composer、流式
>   Transcript、picker、审批、Diff、Goal 和恢复点。Java REPL 已退役，终端统一使用 native CLI/TUI。

Harnex 的 CLI / TUI 通过 Runtime API 执行任务，适合本机终端、SSH 项目和无桌面环境。

运行域分两种：普通终端没有 manifest 时，TUI 启动并管理自己的 Command Domain 和内置 Java Runtime；
VS Code 集成终端存在有效 `HARNEX_DOMAIN_MANIFEST` 时，TUI 作为 Client 精确连接当前 IDE Runtime，
不启动第二个 JVM，也不能停止 Owner。显式 manifest 无效时 fail closed，不会扫描端口或退回 standalone。

锁冲突取决于两个 Runtime 是否使用同一个执行 dataDir。桌面默认使用项目数据根下的 `runtime-stores/tauri`，managed VS Code 使用 `runtime-stores/vscode-<storage-id>`，独立 CLI 默认使用项目 `.harnex/data`；因此仅“打开同一项目”不必然冲突。共享档案通过文件事务协调，同一活动或暂停会话仍受跨进程占用限制，代码工作树本身没有因此隔离。

需要复用桌面的实时运行状态时，显式使用其受信 manifest。若确实发生同一执行目录锁冲突，CLI 会说明占用；当 `tauri-main/domain.json` 与当前 Workspace 匹配时，错误中给出 `--domain-manifest ... tui --workspace ...` 命令。其他 JVM 启动失败保留退出码并指向当前 Command Domain 的 `runtime-err.log/runtime-out.log`。

### 5.1 启动方式

```bash
# 无项目普通会话，支持自然语言生图
harnex tui --conversation
harnex cli --conversation -p "解释这段文字"

# 日常项目 Agent：默认 fullscreen/auto theme
harnex tui
harnex tui --workspace D:\code\my-project

# 不使用 alternate screen，保留主屏/scrollback，适合部分 SSH/tmux/辅助场景
harnex tui --renderer inline

# Windows 默认使用稳定帧传输；界面与其他平台完全相同
harnex tui --render-strategy stable

# 显式使用更高频的 Ratatui cell-diff 传输（视觉内容不变）
harnex tui --render-strategy diff

# 显式主题与颜色退化
harnex tui --theme dark
harnex tui --theme light
harnex tui --theme ansi
NO_COLOR=1 harnex tui                  # PowerShell: $env:NO_COLOR='1'; harnex tui

# 脚本/CI/headless 单次执行
harnex cli -p "分析当前目录的项目结构"
harnex cli -p "运行测试" --model gpt-5.6-terra --toolsets act

# 外部终端显式连接某个受信 Runtime Domain
harnex --domain-manifest <domain.json> tui
```

**启动参数一览**：

| 参数 | 简写 | 说明 |
|------|------|------|
| `tui` | — | 启动 native 交互客户端 |
| `--workspace <path>` | — | 显式指定项目目录；不得把 Runtime Bundle 安装目录作为 workspace |
| `--lang auto\|zh-CN\|en` | — | TUI 界面语言；首次启动跟随系统，可在 `Ctrl+P → language` 中切换并记住偏好 |
| `--renderer fullscreen\|inline` | — | alternate-screen 全屏或保留 scrollback 的 main-screen 承载方式；共用同一 UI |
| `--render-strategy auto\|stable\|diff` | — | 两种策略共用同一 Ratatui 富视觉帧；Windows `auto` 使用整行单次写入的 `stable`，其他平台使用 `diff`；旧 `compat` 值仍作为 `stable` 别名 |
| `--theme auto\|dark\|light\|ansi` | — | 终端主题；首次默认 `auto`，可在命令面板的“设置 → 主题”中即时切换并保存；此参数优先于已保存选择 |
| `--color auto\|always\|never` | — | 颜色策略；同时尊重 `NO_COLOR` |
| `--prompt <text>` | `-p` | 单次执行模式，执行后自动退出 |
| `--max-work-iterations <n>` | 64 | 明确设置普通任务的单步迭代上限，受 Runtime 配置限制；持续推进使用 `/goal` |
| `--model <name>` | — | 覆盖默认模型（使用 provider 当前模型目录中的精确 ID） |
| `--toolsets <a,b>` | — | 覆盖默认工具集（逗号分隔，如 `read,inspect`） |
| `--verbose` | `-v` | 显示原始 SSE 事件调试信息（thinking 过程默认已显示，无需此参数） |

请在项目目录执行 `harnex tui`，或传 `--workspace`。如果当前目录位于
`dist/runtime-bundles/...`、安装目录或其 `bin/` 下，CLI 会拒绝启动，避免把会话 `data/` 写入已签名 Bundle。

源码开发时先构建并准备 Runtime Bundle：

```powershell
npm run build:runtime
.\dist\runtime-bundles\1.0.0-win32-x64\bin\harnex.exe tui
```

独立 TUI 按 F6 在个人会话与项目 Agent 之间切换，分别保留草稿、记录与模型选择。提交尚未确认时先等待接收结果；切换失败保留原空间，重试无需放弃草稿。个人 Runtime 可与 GUI 共享，退出借用它的 CLI 不会关闭 GUI 的运行进程。退出自有 TUI 时会检查后台空间仍在执行的任务。

Windows 下直接关闭终端或强制结束 CLI，也会回收该 CLI 自行启动的 Runtime、工具子进程与本地 SSH 连接进程。借用桌面版或 IDE 的 Runtime 仍由原宿主管理。需要正常保存退出状态时使用 `Ctrl+D`。

每次重新启动 TUI 默认进入新会话，不自动选中工作区的历史记录。按 `Ctrl+P → threads` 手动打开历史会话，或按 `Ctrl+N` 新建会话；F6 返回当前进程中已打开的空间时仍保留其会话和草稿。

TUI 的命令面板、帮助、状态栏、批准提示等界面支持简体中文和英文。按 `Ctrl+P → language` 选择中文、English 或跟随系统，偏好保存到用户数据目录（默认 `~/.harnex`）下的 `tui-language`。语言优先级为命令行 `--lang`、环境变量 `HARNEX_LANG`、已保存偏好、系统语言；显式 `auto` 使用系统语言。系统检测优先读取 `LC_ALL`、`LC_MESSAGES`、`LANG`，Windows 无这些变量时使用用户界面语言，macOS 使用 AppleLocale。用户消息、模型回复、工具输出、文件路径和自定义名称保留原文。命令面板支持按中文说明或英文命令标识搜索；使用方向键滚动选择，帮助窗口也支持方向键及 PgUp/PgDn。

精确附着到 VS Code 等宿主的终端固定使用该 PROJECT Runtime，不能 F6 切换，也不接受 `--conversation`。图片结果使用引用与文本展示。

### 5.2 TUI 快捷键

主页优先显示 **Ctrl+P 命令菜单** 与 **F1 快捷键帮助**，下一行列出菜单内的历史会话、模型与推理强度、设置入口；模型、强度和新建会话作为次级快捷操作。底部右侧始终保留 `F1 快捷键`，包括已有草稿、通知和弹窗时。帮助可用上下键、PgUp/PgDn、Home/End 浏览；再按 F1 或 Esc 返回，不改变草稿。下表中的 `Ctrl+X → Q` 是两步操作：先按住 Ctrl 再按 X，松开后按 Q，无需同时按三个键。前缀等待约两秒，页脚显示可用操作；Esc 取消前缀。也可从 `Ctrl+P → quit` 退出。

`Ctrl+P` 按操作范围分层：模型、推理强度、权限、工具集、技能引用、还原点、目标、待办和上下文放在“当前会话”；任务输入、完成后发送草稿、变更、批准和停止放在“当前任务”；语言、换行与发送快捷键、思考详情和侧栏放在“设置”。没有会话、任务或草稿时，对应操作显示不可用原因。输入关键字可跨分类搜索，例如输入 `language` 或“语言”。弹窗标题显示当前路径，`Esc` 返回上一级并保留搜索和选中位置，`Ctrl+P` 随时返回命令首页；从命令首页再按 `Esc` 返回输入框。

通过 `Ctrl+P → 设置 → 换行与发送快捷键`，或在命令菜单搜索 `input-keys`，选择以下两组：

| 组合 | 换行 | 发送 |
|---|---|---|
| 默认 | `Shift+Enter` | `Enter` |
| Ctrl+Enter 发送 | `Enter` | `Ctrl+Enter` |

选择立即生效并保存到用户目录 `tui-input-keys`，在项目／个人空间之间共用，重启后恢复。草稿、提问回答、计划反馈和目标反馈遵循同一设置；菜单选项和非文本审批仍用 Enter 确认。页脚、帮助和输入提示显示当前组合。第二组的 Ctrl+Enter 用于正常发送；“完成后执行”可用 Alt+Enter 或 Ctrl+X → I。粘贴中的换行不会触发发送。

`/` 菜单使用清晰的 `>` 标记选中行，每行先显示 `/skill`、`/plan` 或 `/goal`，随后显示参数和说明。确认后回到输入框补充参数，不会立即执行命令。

模型和推理强度作用于下一次新任务；当前正在执行的任务及其补充输入继续使用原先的配置。显式强度绑定到具体 Provider/模型，Agent 的工具调用限制会收窄可选档位。切换到不支持原档位的模型时恢复 `auto` 并提示。模型与强度按空间保存，输入框边框明确显示“下次任务模型 / 推理强度”；重新打开历史会话时读取该会话的默认配置。

右侧栏按“当前任务 → 本次任务模型 → 本次用量”分组：状态使用对应颜色，模型名占独立行，数字右对齐，总用量突出显示。当前任务尚未返回模型信息时显示等待提示，不借用下次任务的选择。未开始任务时显示下次任务配置；没有用量数据时显示说明，避免空数字占满侧栏。较矮窗口优先保留状态、输入／输出、缓存读取与命中率，较宽窗口增加模型详情的空间。

运行中发送消息后，TUI 会等待服务端确认接收再清理原草稿；期间可以继续编辑，较晚到达的确认不会清除新内容。发送失败时草稿保留，并显示失败原因。后续任务的发送不会切换持续生效的输入模式，Agent 的下一次 Enter 仍然补充当前任务；普通会话始终排队新轮次。

草稿、已接收输入的本地历史、最近模型和收藏按工作区／个人空间保存在用户目录的 `tui/workspaces`。草稿约每两秒保存一次并在正常退出时保存；再次启动仍进入新会话，但会恢复未发送文字。历史保留最近 500 条并限制存储体积。大段输入显示行数和字符数，可全文预览或打开外部编辑器。编辑器配置可带参数，例如 `EDITOR="code --wait"`；应使用等待编辑完成后退出的参数，编辑器进程结束时 TUI 读取文件。

空输入框使用较淡的斜体“提示”文案，与已输入内容区分。Windows Terminal 等支持括号粘贴协议的终端中，右键或快捷键粘贴只写入草稿，保留多行文本；粘贴中的换行不会发送消息，确认内容后另按当前组合的发送键。

独立 PowerShell 的旧控制台即使不提供粘贴标记，也会将整批多行文本插入草稿，包含开头或结尾的换行；长文本不会因分批读取而把最后一个换行当成发送。粘贴完成后，另按当前组合的发送键。

鼠标滚轮可以直接翻阅 TUI 会话，包括重新打开的历史会话。左键拖选屏幕内文字后，右键或 `Ctrl+C` 复制；未选中文字时，右键将剪贴板内容粘贴到草稿，另按当前组合的发送键才发送。选中期间画面保持稳定，`Esc` 取消选择；无选区时 `Ctrl+C` 仍用于取消任务／清空空闲草稿。也可使用 `PgUp/PgDn` 翻页，`Ctrl+Home/End` 跳到开头／最新位置。退出 TUI 后恢复终端原有输入模式。

macOS 使用同一套 TUI，但需要对应的 `darwin-arm64`（Apple Silicon）或 `darwin-x64`（Intel）发行包。快捷键里的 Ctrl 指 **Control**，不替换成 Command；F1/F2/F3/F6 可能需要配合 Fn。`Ctrl+P` 可进入帮助、模型、强度和设置，无需依赖功能键。剪贴板使用系统 `pbcopy` / `pbpaste`。所选组合中的 `Shift+Enter` 或 `Ctrl+Enter` 必须由终端发送独立键码；不能区分修饰 Enter 的终端需要配置按键映射或使用支持增强键盘协议的终端。也可用 `Ctrl+X → E` 在外部编辑器输入多行内容。Option/Alt 类快捷键与鼠标事件是否转发取决于终端设置；这里不把 Ctrl+J 作为换行键。参考 [Apple 功能键说明](https://support.apple.com/en-us/102439) 和 [终端快捷键协议说明](https://opencode.ai/docs/keybinds/#shiftenter)。

Harnex 会在支持 Kitty keyboard protocol 的终端启用 modified-key 消歧，使 `Ctrl+M` 与 Enter 可被分别
识别。但操作系统全局热键、输入法或 IDE 主窗口级快捷键发生在终端把按键交给进程之前，TUI 无法强行
抢占；遇到这类宿主拦截时使用 `F2`、`Ctrl+X` 后按 `M`，或 `Ctrl+P → Models`，功能完全相同。
VS Code 集成终端若希望在 terminal 聚焦期间把大多数快捷键交给 TUI，可在用户设置中启用：

```json
{ "terminal.integrated.sendKeybindingsToShell": true }
```

该设置只改变集成终端聚焦时的路由；焦点回到编辑器后仍使用 VS Code 快捷键。代价是 terminal 聚焦时
`Ctrl+F` 等默认由 VS Code 处理的组合也会发给 TUI/当前 shell，应按个人习惯选择是否启用。

Interaction overlay 使用上下文键：Approval 为 `a` 单次允许、`w` 本 Thread 白名单、`d` 拒绝；Plan
Review 为 `a` 批准、`r` 打回并填写反馈；Question 直接输入答案后 Enter。Snapshot 列表中 `c` 只恢复
对话、`r` 先预览并恢复对话与文件、`b` 从恢复点创建新 Thread。所有写盘、恢复与审批仍由 Runtime 执行。

### 5.3 斜杠命令与 Command palette

Agent 中直接输入自然语言即可执行项目任务。以下 `/plan`、`/goal`、`/skill` 为 Agent 功能，由 Runtime 统一解析，Web/VS Code/TUI 不维护不同语义：

| 命令 | 说明 |
|------|------|
| `/skill <name> [input]` | 引用某技能：把技能正文**预注入**后再带上你的输入执行（无参 = 列出技能） |
| `/plan [task]` | 进入 plan 模式：只读探索 → `submit_plan` 出计划 → 你批准 / 打回(可填反馈) → 执行；`/plan cancel` 放弃 plan 模式 |
| `/goal <objective> [+budget]` | 设定自动续跑目标，agent 反复跑直到达成 / 受阻 / 触达预算（如 `/goal 重构鉴权模块 +200k`）；`/goal` 看状态、`/goal clear\|pause\|resume` 控制 |

`/help`、`/new`、`/status`、`/model` 等历史命令属于 Java REPL 本地命令，不发送给 Runtime。native TUI
分别使用 `?`、`Ctrl+N`、Context overlay、`Ctrl+M`/`F2` 等客户端动作，退出使用 `Ctrl+D`。

`Ctrl+P` palette 负责客户端视图动作；斜杠命令负责服务端会话/Agent 语义，两者不冲突。例如选择
“Snapshots”不会向模型发送文字，而输入 `/goal 重构鉴权 +200k` 会进入持久 Goal 服务。

### 5.4 CLI 与 Web 页面的区别

| 维度 | Web 页面 | CLI 模式 |
|------|---------|---------|
| **启动方式** | 浏览器访问 Runtime/Supervisor | `harnex tui`；脚本用 `harnex cli -p` |
| **交互方式** | 图形化聊天界面 | Ratatui fullscreen/inline + headless CLI |
| **多会话** | 左侧会话列表，可切换 | `Ctrl+P → Threads` fuzzy picker |
| **工具调用展示** | 可折叠的卡片 UI | 淡色短分隔线分组，命令／路径和结果分别保留；长输出自动换行，可滚动查看 |
| **MoA 混合模型** | ❌ 已从聊天中移除；需要请调 `POST /api/moa` | ❌ 不支持（CLI 为单模型模式） |
| **审批交互** | 弹窗 Allow / Deny / 白名单 | 统一 Interaction overlay：`a/w/d`、Plan feedback、Question 输入 |
| **会话搜索** | 搜索框 Lucene 语法 | Thread picker 标题/id 过滤；Agent 仍可用 `session_search` |
| **运行时选择** | 设置页管理 Provider/Proxy；Model/Toolset 覆盖当前会话 | `Ctrl+M`/`F2` Model、`Ctrl+U` Toolset、`Shift+Tab` Permission |
| **记忆与技能** | ✅ 共享（同一 Runtime） | ✅ 共享；`Ctrl+K` Skill picker，`/rescan` 热加载 |
| **Cron 定时任务** | 设置页管理 | ❌ 不支持管理（但已有作业仍会运行） |
| **主题 / 样式** | 多套 GUI theme | `auto/dark/light/ansi` + `NO_COLOR` |
| **适用场景** | 日常使用，可视化操作 | SSH 远程、无桌面环境、脚本自动化、CI/CD 集成 |
| **会话持久化** | ✅ 自动保存到 `<workspaceDataDir>/agent/threads/` | ✅ 自动保存到 `<workspaceDataDir>/agent/threads/` |
| **登录认证** | 本地 Domain boot-token | 同一 boot-token + workspace/instance identity 校验 |
| **并发支持** | 每 Runtime Domain 单 active workspace | standalone Owner 或 IDE Domain 内多个 Client |

### 5.5 使用场景推荐

- **服务器开发**：使用 `harnex tui --remote <连接> --workspace <远端目录>` 让 Agent 帮你改代码、查日志
- **脚本自动化**：`-p "..."` 单次执行，可将输出重定向到文件
- **CI/CD 集成**：在构建脚本中调用 CLI 做代码审查、生成 changelog
- **快速提问**：不想打开浏览器时，终端里一句话问答

## 6. 隐藏 / 需手动操作的功能

常用设置可在 GUI 完成；以下列出配置维护及 API 对接方式，供需要手工管理的用户参考。

### 6.1 配置 / 数据维护类

| 功能 | 操作方式 |
|------|---------|
| **整理记忆** | 编辑当前 `<dataDir>/memory/MEMORY.md` 与 `USER.md`；新会话加载最新快照，当前 Agent 可通过 `memory_list` 读取最新内容 |
| **整理经验沉淀** | 编辑当前 `<dataDir>/memory/LESSONS.md`（Agent 通过 `lesson_record` 工具自动写入；超过 2× HARD_CAP 自动按 bullet 行从顶部裁剪），手工删除过时条目可保持 prompt 槽位干净 |
| **添加技能** | 在项目 `.harnex/skills/<slug>/SKILL.md` 或用户 `~/.harnex/skills/<slug>/SKILL.md` 写 YAML 前缀 + Markdown，Web 设置页点击「重新扫描」/ CLI `/rescan` / `POST /api/v1/skills/rescan` 热加载 |
| **配置硬验证 checks** | `agent-config.yml → harnex.verify.checks: {compile: "mvn -q test-compile", unit: "mvn -q test", fe-build: "cd frontend && npm run build"}`，模型完成任务前会调用 `verify` 工具运行所有 check，失败则回灌错误尾 800 字符让模型修复重跑 |
| **手工进入 / 退出 plan-mode** | 输入 `/plan <task>` 进入 plan 模式，模型探索后调用 `submit_plan` 提交计划待审批；也可用 `/plan cancel` 退出。plan-mode 下所有非 PLAN_MODE_SAFE 工具自动短路 |
| **添加 MCP 外部工具服务器** | `agent-config.yml → harnex.mcp.servers[]`，支持 stdio、sse 和 streamable-http（别名 http）三种 transport。**系统特性**：首次执行需要相关工具集的任务时连接并发现工具，成功后复用至 Runtime 退出；只对已启用过的连接每 60s 健康检查并按退避重连。未使用的普通 MCP 不启动子进程，IDE Editor Bridge 保持宿主连接行为；工具执行失败时仍可重连一次。详见 §9.2 完整 MCP 配置及 `GET /api/mcp/servers` 查看实时连接状态 |
| **MCP 服务健康状态监控** | `GET /api/mcp/servers` 返回各 MCP 服务的 `status`（not_started/connecting/connected/disconnected）及已发现的工具列表；not_started 表示尚未使用，不是连接故障 |
| **切换 Provider / 增加模型** | Web/Tauri 设置页编辑 Provider 基础字段，或编辑 `agent-config.yml → harnex.providers.<id>`；用于后续新任务，当前任务保留原快照。关联 HTTP／钥匙串凭据变更按提示重连；详见 §9.0／§9.1 |
| **启用 LLM 摘要（可选独立模型）** | `harnex.summarizer.enabled: true`；不填 provider 时复用任务实际模型并可尝试 fallback，显式 provider 可指向可靠且成本合适的摘要模型；全部不可用时回退确定性结构化 digest。详见 §4.8 |
| **调整摘要触发阈值** | `context-window`（128K）扣除 output/safety reserve 后，使用 soft/hard/target（75%/90%/40%）水位；`min-new-*` 限制压缩频率，完整参数表见 §4.8 |
| **新增危险命令正则** | `agent-config.yml → harnex.approval.dangerous-patterns` 追加即可 |
| **自定义工具集** | `agent-config.yml → harnex.toolsets.presets` 新增一个 key，后续新任务采用新配置；当前任务不换工具集 |
| **子 Agent 并发上限** | `agent-config.yml → harnex.subagent.max-per-thread`（默认 3） |
| **工具并行度** | `harnex.tool-parallelism`（默认 8） |
| **Agent 单次最大循环** | 顶层交互对话取 `min(harnex.max-iterations=200, harnex.ordinary-max-iterations=64)`；Goal 与子 Agent 不受交互上限影响。ordinary-max-iterations=0 只取消普通任务额外限制，仍受总上限与预算约束 |
| **SSE 超时** | `harnex.sse-timeout-ms`（默认 900 000=15 分钟）+ `spring.mvc.async.request-timeout` 同步调整 |
| **修改端口** | Web 入口默认 `18081`，各入口覆盖参数见[端口约定](04_部署方案.md#12-默认端口与覆盖方式)；开发后端 API 默认 `8088`，桌面／VS Code 内部端口自动分配 |

### 6.2 鉴权 / 安全类

| 功能 | 操作方式 |
|------|---------|
| **开启可选远程/API 鉴权** | 设置 `HARNEX_AUTH_ENABLED=true`；本地 GUI 不提供账号页，API 客户端使用 Bearer、Session 或宿主 boot-token |
| **Bearer Token** | `HARNEX_AUTH_TOKENS=a,b,c` 设置静态 token 列表，调用时带 `Authorization: Bearer a`，适合脚本 / CI |
| **本地默认** | `HARNEX_AUTH_ENABLED=false`，仅绑定 loopback；Supervisor control token、CSRF/Origin 与 instance guard 仍然生效 |
| **会话 TTL** | 当前硬编码：24h 绝对上限 + 2h 滑动空闲；如需调整改 `AuthService.SESSION_TTL_MS / SESSION_IDLE_MS` 后重新编译 |
| **登录限流** | 同 IP 60s 内 ≥20 次失败将临时封禁；规则在 `ApiAuthFilter` |

### 6.3 命令执行环境

设置 → 安全与权限 → 命令执行环境。默认 host 使用当前 Runtime 的工具链；SSH 项目使用远端工具链。需要隔离时选择配置支持的原生沙箱或 Docker，依赖缺失时明确失败，不降级到主机执行。平台支持、安装条件与 YAML 见[部署方案](04_部署方案.md#execution-environments)。

审批与隔离分别生效；容器不自动授权命令，普通主机命令也不是 OS 沙箱。取消当前 Agent 使用停止按钮／Run cancel API，关闭 SSE 仅结束订阅。

### 6.4 数据维护

历史、标题和删除使用侧栏／会话 API；不要直接改 JSON 绕过提交记录和 revision。全文索引与原始档案分离，索引异常先备份、停止写 Runtime，再按诊断定位对应索引。文件恢复使用 Snapshot；普通消息分支不会回滚文件。

备份、恢复与改变用户根见 §7 及[部署方案](04_部署方案.md#8-持久化--备份)。项目未交付，不提供旧配置／旧数据的自动迁移；同版本重启恢复、提交幂等和删除防复活仍是正常产品保证。

### 6.5 集成 / 对接类

| 功能 | 操作方式 |
|------|---------|
| **同步 Webhook 网关对接 IM** | `POST /api/gateway/inbound`（`X-HARNEX-Signature` HMAC、`HARNEX_GATEWAY_SECRET`），阻塞式返回，agent loop 必须 ≤5s 完成，见 §10 FAQ Q6 |
| **异步 Webhook 网关对接 IM** | 调用 `GatewayDispatcher.asyncDispatch(...)` 或扩展相应 ChannelAdapter，立即返回"⏳ Processing..."占位符，backend 在线程池异步执行 agent loop，完成后通过 `ReplyCallback` 主动推送结果回 IM 平台（各平台都支持主动发送消息），解决 agent 超时问题 |
| **Prometheus 抓取** | `GET /actuator/prometheus`，配置见 §7.5 |
| **健康检查 / 探针** | `GET /actuator/health`、`/actuator/info` |
| **刷新配置** | 业务设置按 §9.0 的新任务／重连边界生效；端口、目录等启动配置和 `application.yml` 的基础设施变更仍需重启 |
| **JVM 内存调优** | 启动加 `-Xms512m -Xmx2g`；docker 启动经 `JAVA_TOOL_OPTIONS` 注入 |

## 7. 运维与排障

### 7.1 关键目录

| 路径 | 内容 |
| --- | --- |
| `<项目>/.harnex/data` | 默认项目数据，或使用宿主显式登记的 dataDir |
| `<项目>/.harnex/skills` | 项目技能，可提交 Git |
| `~/.harnex` | 默认用户配置、用户技能、个人会话、连接和运行域 |
| `<用户根>/personal` | 普通会话、附件、图片、用量，不随项目切换 |
| `<dataDir>/diagnostics/logs` | 后端日志；启动前的宿主日志在运行域目录 |

设置 → 诊断显示实际路径，本机可点击打开数据目录，SSH 只显示远端路径。

默认存储策略优先保留会话内容、附件原件和用量账本，诊断与临时副本单独限制：

| 数据 | 默认保留策略 |
|------|-------------|
| 应用日志 | 单文件 5 MB，归档最多 20 MB／7 天；当前文件另计 |
| 宿主捕获的 stdout／stderr | 每个文件最多 2 MiB，保留一个备份；Web 宿主还会清理超过 7 天或目录预算 32 MiB 的非活动日志 |
| 模型调用、上下文诊断 | 各保留最近 7 天，分别以 8 MiB／2048 个文件为清理目标；写入时定期执行，因此可能短暂超出 |
| 交互、Run Input 诊断 | 各保留当前和上一份 JSONL，每份最多 2 MiB |
| 回滚快照 | 默认每个会话 20 份，当前 dataDir 总预算 256 MiB；仍保留运行恢复所需的受保护快照 |
| 图片接收临时文件 | 图片原件和操作引用持久化、校验通过后回收临时字节；保存失败时保留用于恢复 |
| 会话事务日志 | 完整落盘后只保留搜索和幂等校验需要的引用，不长期重复保存正文；尚未完整落盘的事务保留原内容用于恢复 |

成功模型调用的详细流日志只在 DEBUG 级别输出。完整 LLM 审计仍默认关闭。上述策略不是整个 dataDir 的硬配额：真实历史、图片原件、用量记录会随使用增长；附件供模型／工具读取的副本目前也会保留。已有日志上限和快照配置的显式覆盖继续生效，历史记录与原件不会按诊断保留期自动删除。

默认项目数据跟随项目所在磁盘。要把用户配置、个人会话和下载缓存也移到其他盘，在启动所有宿主前设置：

```powershell
$env:HARNEX_USER_DATA_DIR = 'D:/HarnexUserData'
```

这不会自动搬迁现有资料。运行目录自动包含忽略全部运行文件的 `.gitignore`，不要因此忽略整个项目 `.harnex/`，否则会误排除可共享的 skills。已跟踪文件不受新增忽略规则影响。

### 7.2 常见启动失败

| 现象 | 解决 |
|------|------|
| `port already in use` | 查看本次宿主日志与端口归属；不要停止其他应用拥有的 Runtime |
| `401 Unauthorized from provider` | 未设 `OPENAI_API_KEY` |
| `Connection refused` 调模型 | 代理问题；设置 `https_proxy` 或换 `base-url` |
| 前端白屏 | `npm run build` 后 `dist/` 没挂载；或 nginx 指向错了 |
| Lucene 索引损坏 | 先备份并停止所属 Runtime，检查 `<dataDir>/indexes` 及诊断；原始档案独立保存 |
| **MCP 服务连接失败** | 检查 `agent-config.yml` 中 `harnex.mcp.servers[]` 的 `transport`/`command`/`url` 是否正确；`stdio` 模式确保程序可执行；`sse` / `streamable-http` 模式确保端点正确、网络连通、环境变量（如 `MCP_TOKEN`）已设置 |
| **MCP 工具调用失败** | 检查后端日志 `grep MCP` 查看连接状态；若显示 disconnected，系统会自动重连；可 `GET /api/mcp/servers` 查看实时连接状态 |
| **IM Gateway 消息没回复** | 检查 `HARNEX_GATEWAY_SECRET` 是否与 bridge 侧配置一致；确保 webhook URL 可外网访问；同步模式下 agent loop 必须在 5s 内完成（否则返回超时），长任务建议改为异步 `asyncDispatch` |

### 7.3 日志定位

先在设置 → 诊断查看本次 Runtime 的 dataDir、运行域和 instanceId。应用日志位于 `<dataDir>/diagnostics/logs`；JVM 未成功启动时查看 `<userDataDir>/runtime-domains/<id>/` 下宿主提供的 stdout／stderr 日志，不能只根据 `runtime_exited` 或未发布 manifest 判断原因。

端口就绪必须属于本次实例，dataDir 锁冲突表示已有写入者。不要仅按端口杀其他宿主的进程；返回所属应用关闭项目，或使用匹配的受信 manifest 连接。

### 7.4 备份策略

停止对应 Runtime 写入后，分别备份项目 dataDir、`.harnex/skills`、用户配置和 personal。Node 启动器可用 `harnex backup --personal` 或 `harnex backup --workspace <项目>`；原生二进制没有 backup 子命令。完整选项与恢复边界见[部署方案](04_部署方案.md#8-持久化--备份)。

### 7.5 Prometheus 指标

Runtime 显式开启 `management.endpoints.web.exposure.include=health,info,metrics,prometheus` 并满足认证边界后，`GET /actuator/prometheus` 可暴露以下业务指标（标签 `application=harnex`）：

| 指标 | 说明 |
|---|---|
| `harnex_chat_requests_total` / `harnex_chat_errors_total` | 流式对话请求 / 异常数 |
| `harnex_tool_calls_total` / `harnex_tool_errors_total`     | 工具调用总数 / 失败数 |
| `harnex_tool_duration_seconds`                            | 工具执行耗时分布 |
| `harnex_provider_failovers_total`                         | 主 provider → fallback 切换次数 |
| `harnex_approval_blocks_total`                            | 审批拦截次数 |
| `harnex_llm_stream_seconds`                               | LLM 流式响应耗时 |

以下示例假定 `runtime-host:8088` 是可访问的 Java Runtime 指标端口。Compose 的 `backend:8088` 默认是 Supervisor，需要另行配置到目标 Runtime 的转发，不能直接套用：
```yaml
- job_name: harnex
  metrics_path: /actuator/prometheus
  static_configs: [{ targets: ['runtime-host:8088'] }]
```
告警建议：`rate(harnex_chat_errors_total[5m]) > 0.1`、`harnex_approval_blocks_total` 异常跃升。

API 消费者使用[生成 OpenAPI](../packages/protocol/openapi.json)及当前后端 Controller。OpenAPI 当前只覆盖已导出的工作台资源，配置、记忆、部分元数据入口还需对照相应 Controller；不能将未导出理解为接口不存在。常用入口：

| 用途 | 资源 |
| --- | --- |

## 9. 配置项参考

### 9.0 配置怎么读取、怎么改（最重要，先读这一节）

很多人一上来就问："配置到底放哪？是改文件还是设环境变量？TUI / 桌面 exe / Web 三种形态配法一样吗？" 答案：**三种形态用的是同一个后端 jar、同一套配置项、同一套优先级规则，唯一区别是"外置配置文件被自动发现的目录"不同。** 本节把机制讲透。

#### 9.0.1 两个配置文件分别管什么

| 文件 | 前缀 | 管什么 | 你通常改的 |
|---|---|---|---|
| **`agent-config.yml`** | `harnex.*` | Harnex 业务配置：providers（大模型）、router（路由/容灾）、toolsets、summarizer、sandbox、auth、workspace、gateway（IM）、memory、cron、mcp… | **90% 的自定义都在这里** |
| **`application.yml`** | `server.*` / `spring.*` / `logging.*` / `management.*` | Spring Boot 基础设施：HTTP 端口、日志级别、management 端点 | 偶尔改端口/日志 |

两者都**内置在 jar 里有一份默认值**（`backend/src/main/resources/` 下）。普通字段按属性覆盖；但最高
优先级文档一旦声明 `providers`，就完整接管 concrete Provider Map，内置端点和同名字段不会自动补入。

#### 9.0.2 配置的来源与优先级（高优先级覆盖低优先级）

后端遵循 Spring Boot 标准外部化配置规则，从高到低：

```
1. 命令行参数         --harnex.auth.enabled=false   --server.port=9090   （临时、最高）
2. JVM 系统属性       -Dharnex.auth.enabled=false
3. 操作系统环境变量    HARNEX_AUTH_ENABLED=false                          （最常用）
4. 外置覆盖文件        <某目录>/agent-config.yml + application.yml
5. jar 内置默认        backend/src/main/resources/agent-config.yml       （最低、兜底）
```

> 环境变量有**两种**作用方式，都很常用：
> - **直接绑定**（relaxed binding）：`HARNEX_AUTH_ENABLED` → 属性 `harnex.auth.enabled`；`SERVER_PORT` → `server.port`。规则：大写、`.`/`-` 变 `_`、加前缀。
> - **占位符替换**：`agent-config.yml` 里写成 `api-key: ${OPENAI_API_KEY:}` 的地方，由同名环境变量填充，`:` 后是缺省值。

#### 9.0.3 各形态去哪里找你的 `agent-config.yml`（关键差异表）

| 形态 | 启动方式 | 自动发现外置配置的目录 | 备注 |
|---|---|---|---|
| **TUI（终端 REPL）** | `harnex`（npm 全局命令） | `~/.harnex/agent-config.yml` + `application.yml` | Windows 是 `C:\Users\你\.harnex\` |
| **Web（本机 serve）** | `harnex serve` | **同上**，`~/.harnex/` | 与 TUI 完全一致 |
| **Web（Workspace Supervisor）** | `harnex supervisor` | **同上**，`~/.harnex/` | 单 active workspace JVM 加载用户级配置 |
| **桌面 exe** | 双击 `Harnex` | 用户级 `~/.harnex/agent-config.yml`；不自动导入工作区根配置 | 项目共享根默认 `<工作区>/.harnex/data`，执行目录为其 `runtime-stores/tauri` 子目录 |
| **VS Code 插件** | 打开当前 workspace 的 Harnex 插件 | managed 使用用户级 `~/.harnex/agent-config.yml`；existing 沿用原宿主配置 | 可独立启动或受信连接当前项目已有 Runtime；existing 不接管宿主生命周期，当前窗口终端 native/npm CLI 可作为域内 Client，见[VS Code 使用说明](../extension/README.md) |
| **Docker Compose** | `docker compose up` | Supervisor 自动加载 `/root/.harnex/agent-config.yml` 与可选 `application.yml`；Web 保存的模型配置落在该用户卷 | `.env` 提供可选环境覆盖；自定义 JAR／K8s 启动方式需自行明确配置加载路径 |
| **开发模式** | `node scripts/dev/dev.mjs --config <dir>` | 你用 `--config` 显式指定的目录 | 调试用 |

> 共同点：以上所有形态最终都是 `java -jar harnex.jar`，**配置项 key 完全一样**，区别只在上表"自动发现目录"这一列。所以你在文档里看到的任何 `harnex.xxx` 配置，三种形态都适用。

#### 9.0.4 怎么改配置——两条路，按场景选

**路线 A：设环境变量（快、临时、适合密钥/开关）**

```powershell
# Windows PowerShell（当前会话有效）
$env:OPENAI_API_KEY = "sk-xxxx"
$env:HARNEX_SUMMARIZER_MODEL = "deepseek-v4-flash"
harnex serve
```
```bash
# macOS / Linux
export OPENAI_API_KEY=sk-xxxx
harnex
```
Docker 则写进 `docker-compose.yml` 的 `backend.environment:` 块。变量清单见 [§9.3](#93-环境变量速查表)。

**路线 B：写外置 `agent-config.yml`（持久、适合 providers/toolsets 等结构化配置）**

1. 在**你这个形态对应的目录**（见 9.0.3 表）新建 `agent-config.yml`，例如 TUI/Web：
   - Windows：`C:\Users\你的用户名\.harnex\agent-config.yml`
   - macOS/Linux：`~/.harnex/agent-config.yml`
   - 桌面 exe：同样放在用户目录 `~/.harnex/agent-config.yml`；Provider/Proxy/Safety 是用户级，
     不从工作区根加载。
2. **普通标量/Map 可只写差异；`providers` 必须写全本文件拥有的端点**。例如只希望使用一个
   DeepSeek Provider：
   ```yaml
   harnex:
     providers:
       deepseek:
         label: 我的 DeepSeek
         profile: deepseek-v4
         base-url: https://api.deepseek.com/v1
         api-key: ${DEEPSEEK_KEY:}
         default-model: <控制台当前可用的 DeepSeek 模型 ID>
   ```
3. 保存后，新对话轮次和任务会读取新配置；正在进行的任务继续使用启动时的配置。各项目与个人 Runtime 会在下一次请求或任务开始时同步同一份用户配置。

> Web/Tauri 设置页可以持久化用户级 Provider 连接配置，并使用 revision、校验、masked Secret 与原子备份；
> Provider、路由、摘要、安全与路径策略、工具集、Hooks、搜索、图片模型及命令执行设置保存后用于新任务。
> 全局 HTTP 代理、MCP 连接、桌面钥匙串新凭据及其关联设置按提示重连生效。聊天框的 Model/Level 只覆盖当前会话，
> 不会改写 Provider 配置。

> 模板从哪来：仓库根的 [`agent-config.example.yml`](../agent-config.example.yml) 是带全量注释的样例，复制需要的片段过去即可。完整可选项见 [§9.2](#92-yaml-配置与图片模型)。

#### 9.0.5 怎么确认配置真的被加载了

- **TUI / Web（npm）**：启动时若发现用户级配置，会打印一行灰字 `[harnex] loading user config from <路径>`。
- **桌面 exe**：无控制台，查看运行域 `~/.harnex/runtime-domains/tauri-main/logs/` 中的 `desktop-shell.log` 及 JVM 输出；实际位置见设置 → 诊断。
- **通用**：通过 `GET /api/v1/config` 的有效配置、`GET /api/v1/models` 和诊断页核对生效值；`/actuator/health` 只证明健康状态，不能证明某个 Provider 配置已应用。

> ⚠️ **常见坑**：(1) 把 `agent-config.yml` 放错目录；(2) 未区分当前任务快照与需要重连的变更；(3) 同时设了环境变量又改了文件，按 9.0.2 优先级**环境变量赢**；(4) 用户文档声明 `providers` 后忘记把仍需保留的端点写入同一 Map；(5) 使用非空 `router.default-provider` 或 `summarizer.provider` 时忘记同步修改引用。

### 9.1 大模型接入大全（providers / 模型适配）

Harnex 有四个独立协议适配器。普通用户只选择 `profile`；profile 在维护层确定 adapter `type` 和 wire 能力，模型 ID 仍由用户填写。

| `type` | API | 适用范围 |
| --- | --- | --- |
| `openai-compatible` | Chat Completions | 实现标准 messages、SSE、`tool_calls`/`finish_reason` 基线的 OpenAI-compatible 端点 |
| `openai-responses` | OpenAI Responses | 原生 Responses semantic events、reasoning/output items、function call、图片/文件 |
| `anthropic` | Anthropic Messages | 原生 Messages named events、`tool_use`、thinking/signature、prompt caching、图片/PDF |
| `gemini` | Google Gemini Interactions | 原生 step events、function call/result、thought/signature、Google Search、图片/音频/视频/PDF |

上表中的 API 是 `type` 对应的协议说明，不是需要另外配置的 YAML 字段。后端只读取 `type`，再自动推导内部协议。

`OpenAiCompatibleProvider` 不是“完全协议透明”。标准文本、流式和 function tools 通常可以直接复用；thinking 控制与回放、reasoning effort、prompt cache、附件 shape、终止原因、usage 字段等扩展能力因厂商/模型而异，必须以该端点的官方文档和实际契约测试为准。

普通会话允许一种结束兼容：收到非空白正文和 `[DONE]`，但整个响应缺少 `finish_reason`，且没有工具调用、拒绝或错误时，可以正常保存回答。日志及 `message_end.completionSource=done_sentinel` 保留这次兼容判定，不伪造上游 `stop`。这表示客户端接受流结束，无法证明上游从未截断内容；若用量已达到请求的输出上限，仍按未完成处理。只有用量、只有思考、没有 `[DONE]` 的断流，以及明确的 `length` 等错误不会走此兼容。Agent、工具调用和工具性请求（探测、摘要等）继续使用严格结束校验。

#### 界面名称与 YAML profile

界面简称用于识别服务；YAML 仍使用下面的 profile ID，两者不要混写：

| 界面名称 | YAML profile |
| --- | --- |
| openai-chat | `openai-chat` |
| openai-responses | `openai-responses` |
| anthropic-messages | `anthropic-messages` |
| deepseek | `deepseek-v4` |
| kimi | `moonshot-kimi-chat` |
| grok | `xai-responses-grok45` |
| gemini | `gemini-interactions` |
| qwen | `dashscope-qwen-chat` |
| glm | `zhipu-glm-chat` |
| 通用 Chat 兼容 | `openai-compatible-chat-safe` |

通用 Chat 兼容采用基础流式／函数工具请求，省略流式用量请求、采样控制、推理回传、缓存及原生附件扩展；openai-chat 按声明的精确型号启用相应 OpenAI 能力。未知别名不自动继承未来型号或视觉能力；刷新上游目录只发现 ID，不代替能力验证。

模型目录是程序内置适配元数据，不是上游实时能力承诺。Profile／精确型号规则决定 thinking、effort、工具和模态，用户的 default-model／models 选择优先。Responses 的图片工具和独立图片型号由图片模型页管理，不混入语言模型列表。

#### 9.1.1 通用配置模板

`providers` 是唯一用户入口。Map key 是稳定路由 id，`label` 仅用于显示。`profile` 是内部接入模板：
它定义适配器和 wire capability，厂商专用模板还可提供安全的官方地址、默认模型与目录；Provider
中的非空字段覆盖这些默认值。`features` 省略时
`attachments/prompt-cache/web-search/reasoning/effort/reasoning-history` 全部为 `auto`。
路由 id 必须匹配 `[A-Za-z0-9][A-Za-z0-9_-]{0,63}`；中文、空格等展示文本放在 `label`，
避免 id 在模型引用、环境覆盖和 URL/诊断路径之间产生歧义。

这里的“Provider 字段覆盖 Profile 默认值”与“配置文件如何分层”是两件事：Profile 是可复用模板；
concrete `providers` 不跨 YAML 合并。用户目录和项目目录都声明 `providers` 时，以优先级更高的那份
完整 Map 为准；命令行、系统属性和环境变量仍可在其上覆盖 API Key 等单字段。

```yaml
harnex:
  providers:
    my-openai:
      label: 我的 OpenAI
      profile: openai-responses
      base-url: https://api.openai.com/v1
      api-key: ${OPENAI_API_KEY:}
      default-model: <控制台当前可用模型 ID>
```

省略 `models` 时只把有效 `default-model` 暴露给前端，不会把 Profile 维护的全部官方型号发布给这个
Key/平台。平台只开放有限型号或用户只想使用默认模型时无需额外配置；需要切换多个型号时才显式列出：

```yaml
      models:
        - id: <平台开放型号 A>
        - id: <平台开放型号 B>
```

该列表是端点的运行时选择目录，不是能力定义的副本。同 ID 会自动继承 Profile 中的 label、tier、
精确 capability 与已验证附件模态；Provider 条目只需填写差异。若列表没有写 `default-model`，后端会
自动补入且保持其原始大小写。

`features` 是少量用户意图，不要求普通用户理解各厂商 wire 字段：

| 字段 | `auto` | `on` / 显式值 | `off` |
| --- | --- | --- | --- |
| `reasoning` | 继承 profile/模型默认 | 按 resolved capability 映射：thinking 型发送厂商开关，effort 型选择声明的平衡档；不支持或与 function tools 冲突时启动即报错 | thinking 型发送关闭值；effort 型发送真正的 `none`；always-on 型号会明确拒绝 |
| `effort` | 继承或由 `reasoning:on` 选择 | `none/minimal/low/medium/high/xhigh/max`，必须在该模型白名单内 | — |
| `attachments` | 保留安全默认与本地降级 | 只有所选精确 model 声明 image/file/pdf/audio/video 才允许 | 禁止原生内联，仍保留 `file_read`/OCR 提示 |
| `prompt-cache` | 继承 profile intent | resolved profile 必须声明缓存模式；适配器再发送该协议对应的 key/breakpoint/cache_control | 不发送可选缓存控制字段 |
| `web-search` | 继承 profile intent | Responses/Anthropic/Gemini 的 resolved profile 声明原生 server tool 时允许；Chat 请使用本地 `web_search` tool | 不启用 provider 原生搜索 |

`reasoning-history` 是高级意图，合法值为 `auto/preserve/discard`。`auto` 按型号契约处理：
optional 型号默认不增加历史保留成本，required 型号自动完整回放；显式 `preserve` 会同时发送厂商保留开关
并回放完整 reasoning，显式 `discard` 对 required 型号会在本地拒绝。未声明可配置历史策略的型号只接受
`auto`，避免用户覆盖被静默忽略。

国产 OpenAI-compatible 服务应选择经过验证的 profile，并填写厂商兼容端点和精确模型 ID：

```yaml
harnex:
  providers:
    my-qwen:
      label: 我的 Qwen
      profile: dashscope-qwen-chat
      base-url: https://dashscope.aliyuncs.com/compatible-mode/v1
      api-key: ${DASHSCOPE_API_KEY:}
      default-model: <控制台当前模型 ID>
```

环境变量风格 `${VAR:default}` 可在 YAML 任意位置使用。所有启用 Provider 都会进入模型下拉目录。
交互式 Chat 始终粘住所选 Provider：对允许容灾的瞬时错误最多尝试
`router.selected-provider-max-attempts` 次（默认 5）。只有保留 id `fallback` 存在且 `enabled=true` 时才会
切换；否则直接返回原错误，不会把其他 Provider 当作隐式故障链。`fallback` 必须使用该小写名称，
它自身的 enabled 就是自动容灾开关；默认关闭，其端点、密钥和模型仍可编辑。

同一 Provider/实际模型达到 `router.circuit-failure-threshold` 个连续瞬时失败后进入 OPEN；启用了
`fallback` 时，在 `router.circuit-open-ms`（默认 30 秒）冷却期间直接使用它。冷却结束只放行一个
HALF_OPEN 探测，成功立即恢复该 Provider/模型，失败则重新冷却。同一 Provider 的其他模型拥有独立
状态。EWMA degraded 只用于诊断，不会覆盖用户选择或动态重排端点。

`router.default-provider` 只在“自动/未显式选择”时指定默认 Provider；留空取用户所有 Provider 中首个
启用的非 fallback 端点，非空则严格引用该 id。摘要显式配置 `summarizer.provider/model` 时优先使用它；
未配置时优先复用当前任务的实际 Provider/Model，并在可用时尝试保留 fallback。标题由本地规则生成，vision/附件
沿用主 Chat 所选模型。MoA 的 reference 和 aggregator 必须写成 `provider/model`，不会把模型名发给
另一个端点。删除、禁用或改名 Provider 时，设置页保存前会校验 default-provider、summarizer 和 MoA
等引用。

`openai-compatible` 必须提供最终 `base-url`（可由 profile 继承或在 provider 覆盖），因为该
协议类型无法推断厂商地址；缺失时启动直接报错。`openai-responses`、`anthropic` 与 `gemini` 可省略并使用
各自官方默认地址。地址必须是无凭据、query 和 fragment 的绝对 `http(s)` URL，密钥只放
`api-key`。路由 id 和 `profile` 引用的匹配大小写不敏感，同一 id 的大小写变体会去重，避免重复请求。
`default-model` 与 `models[].id` 在能力匹配时同样不区分大小写，但后端会保留其原始文本并原样发送给上游；
由于厂商或中转站自身可能区分大小写，配置时应使用其文档给出的准确模型 ID，且不要声明仅大小写不同的重复型号。

未知或自定义模型不会仅凭名称获得型号规则，而是继承所选 Profile 的基线；因此新厂商、Ark 或本地
OpenAI-compatible Chat 端点应选 `openai-compatible-chat-safe`，避免继承 OpenAI 官方缓存/usage
扩展。该安全基线不启用 reasoning、厂商缓存字段、原生搜索或附件，附件仍可走文本提取/OCR 降级。
只有拿到该端点的明确契约并验证后，才在 provider 下为
**精确模型 ID**补目录条目，例如：

```yaml
harnex:
  providers:
    my-qwen:
      # ...profile/base-url/api-key/default-model 同上
      models:
        - id: <与 model 完全相同的 ID>
          input-modalities: [text, image]
```

普通中转站不需要写 capability：选择其真实 API 协议对应的 profile，填写 `base-url/api-key/default-model`
即可。若中转站把官方模型 ID 改成私有 alias，而你希望它继续使用当前 profile 中已验证的型号规则，
可显式映射 canonical model：

```yaml
harnex:
  providers:
    relay:
      profile: openai-chat
      base-url: https://relay.example.com/v1
      api-key: ${RELAY_KEY:}
      default-model: relay-gpt
      models:
        - id: relay-gpt                 # 原样发送给中转站
          capability-model: gpt-5.6-terra
          input-modalities: [text, image, file] # 只在该端点实测后声明
```

`capability-model` 只参与当前 profile 的规则匹配，不改变上游 `model`，也不自动继承附件模态；
如果 canonical id 未命中当前 profile 的任何规则，后端启动时直接报告配置错误。
若不配置它，alias 仍可正常调用，只是保持保守基线。只有一个中转 endpoint 混合了不同厂商的
wire 契约时，才需要高级的 `models[].profile` 或 `models[].capabilities`。

严格校验官方 CLI 身份的中转站可在对应 Provider 上选择一种配置，不能把两组键复制到同一个条目：

```yaml
# OpenAI Chat/Responses 中转
client-emulation: codex
client-version: 0.142.5       # 可省略
```

```yaml
# Anthropic Messages 中转
client-emulation: claude-code
client-version: 2.1.187       # 可省略
```

普通兼容站不要开启模拟。`codex` 只允许 OpenAI Chat/Responses profile，其中 Responses 模式使用
Codex WebSocket transport；`claude-code` 只允许 Anthropic profile，并加入 Claude Code identity、
beta 与 billing system block。配置到错误协议会在启动阶段失败。

Web/Tauri 已提供持久化 Provider 配置；CLI/TUI 仍可编辑同一用户级 YAML。配置以版本快照发布，
新任务读取新版本，活动任务与子任务保留原版本；旧连接在最后一个使用者退出后释放。
全局 HTTP 代理、MCP 连接以及桌面钥匙串新凭据等连接依赖仍需按提示重连。
“测试调用”是保存前的真实请求，按模型能力使用流式调用，最多等待 45 秒；超时表示暂未确认，
不会将模型标为不可用，也不会写文件或修改路由。

> `harnex.providers` 是用户层整表 Map；`harnex.provider-profiles` 及其中的
> `model-capability-rules` 是可分层复用的适配器维护层。协议差异只在统一的 `profile` 命名空间表达。

#### 9.1.2 Profile 与模型能力配置（高级/维护者）

普通会话和 Agent 不再统一发送 16K 输出上限。预算优先级为：本次请求的明确额度（例如摘要／探测）→ Provider 的正数 `max-tokens` → 明确声明的型号级 `default-max-tokens`。都没有时，Chat、Responses、Gemini 省略上限参数，采用服务端默认；Anthropic Messages 要求填写，使用型号预置值，未声明型号的旧配置保留协议兼容值。

`output-reserve-tokens` 是上下文规划的估计，不限制生成长度。内置可选上限接口的预算提示放在此字段，DeepSeek 默认预留 64K；服务端实际默认值仍可能随思考模式或中转线路变化。未知或过大的预留估计会按当前上下文窗口收敛，并在上下文诊断中标明估计。明确设置的输出额度不会静默缩小：若无法与输入、安全余量共存，请求在发送前失败。标题仍由本地文字生成，摘要和连接测试保留各自的小额度。

不要在代码中枚举所有模型。一个 profile 是维护者拥有的接入模板：用唯一的 adapter `type` 选择
wire protocol，并可为厂商专用模板附带官方 endpoint/default model 与内部能力/建议目录；内部 API 类型由 `type`
自动推导，不存在需要重复填写的 `api`。Provider 实例拥有 Key 和覆盖值。
规则/精确模型通过 `profile` 引用同一命名空间：

```yaml
harnex:
  provider-profiles:
    my-chat-profile:
      type: openai-compatible
      instruction-role: system
      max-tokens-field: max_tokens
      output-reserve-tokens: 32768        # 上下文预留估计，不发送为请求上限
      # default-max-tokens: 32768         # 仅在确实需要型号级默认请求上限时声明
      streaming: true
      stream-usage: true
      function-tools: true
      sampling-policy: when_thinking_off   # always | when_thinking_off | omit
      reasoning-efforts: []                # null=未知；[]=明确不支持；或 [low, medium, high]
      function-tool-reasoning-effort: null # 省略/null=继承；effort=约束；unconstrained=子 overlay 清除
      reasoning-replay: never              # never | tool_calls | all | native_items
      reasoning-history: none              # none | optional | required；Chat 专用
      # reasoning-history-field: preserve_thinking # 可选厂商顶层 boolean 字段
      prompt-cache-mode: none              # none | auto_prefix | key | openai_explicit | content_cache_control
      native-web-search: false
      request-options: {}                   # 受信任静态厂商扩展；不能覆盖协议保留字段

    my-reasoning-profile:                   # rule/exact 可复用的 model-level overlay
      type: openai-compatible
      max-tokens-field: max_completion_tokens
      reasoning-efforts: [low, medium, high]

  providers:
    vendor:
      profile: my-chat-profile
      base-url: https://vendor.example/v1
      api-key: ${VENDOR_KEY:}
      default-model: exact-model-id
      models:
        - id: exact-model-id
          profile: my-reasoning-profile
          # capability-model: canonical-id   # 只复用当前根 profile 的 rule 时优先使用这个简单映射
          input-modalities: [text]

  # 规则属于维护层 profile，而不是用户 Provider：
  # provider-profiles.my-chat-profile.model-capability-rules:
  #   - match: 'exact-model-id-\d{8}'
  #     profile: my-reasoning-profile
```

解析按固定顺序逐层合成，不是 provider/rule/exact 三选一：

```text
协议基线 → provider 选中的 profile
        → 首条 model-capability-rule full match（如有）
            → rule profile → rule capabilities（无附件模态）
        → exact model overlay（如有）
            → model profile → model capabilities → input-modalities
```

注意：

- Java 不按名称前缀、substring 或厂商名猜能力。exact 匹配大小写不敏感；规则是 provider-local、有序且全串匹配。rule 与 exact 同时命中时两层都会应用，exact 只覆盖自身显式字段。自由输入 alias 在两者都未命中时仍继承 provider-wide profile，但不会获得其它 model-level overlay 或附件模态；显式 `capability-model` 可让已配置 alias 匹配当前 profile 的 canonical rule，实际上游 ID 不变。
- 显式写了 `profile:` 却找不到同名 profile 时会 fail-fast；不会靠拼写错误触发回退。
- Profile 名不要含点号，Spring Binder 会把带点号的 Map key 拆成层级。内置的 `moonshot-kimi-chat`、`dashscope-qwen-chat`、`zhipu-glm-chat` 等按厂商端点命名；同厂商官方型号差异内联在根 profile 的规则中，不占用独立 profile 名。
- 内部 `api` 由 `type` 单向推导，不是 YAML capability 字段；`instruction-role`、`max-tokens-field`、`streaming`、`stream-usage`、`function-tools`、sampling/reasoning/cache/thinking/native search 等字段描述请求和终态契约，不是模型质量评分；`strict-terminal` 仅能用于 Anthropic。
- `function-tools` 与 `reasoning-efforts` 分别声明 standalone 能力；若端点对两者组合另有限制，用可选 `function-tool-reasoning-effort` 声明。省略/null 表示继承父 profile，子 model/rule 必须写 `unconstrained` 才能显式清除继承约束。`openai-chat` 的 GPT-5.6 规则都保留 `none/low/medium/high/xhigh/max` 六档；当前 Chat Completions 的实际 400 只明确点名 Sol，且[官方模型指南说明 `gpt-5.6` alias 路由到 Sol](https://developers.openai.com/api/docs/guides/latest-model)，所以只有 Sol/alias 首条规则在 function tools 时要求 effective effort=`none`：未显式配置时自动使用 `none`，显式其它档位请求前失败并提示 Responses；无 tools 时六档仍可用。Terra/Luna 及 `openai-responses` 的 GPT-5.6 规则不设置该约束；这代表 Harnex 不从 Sol 无依据外推，并不代表厂商端点组合已经认证。依据是 [Developer Community 中记录的 Sol 服务器 400](https://community.openai.com/t/gpt-5-6-chat-completion-reasoning-effort-bug-behavior-change/1386454)，不是官方文档新增的通用规范；官方 API 参考仍分别列出两项能力，[reasoning 指南](https://developers.openai.com/api/docs/guides/reasoning)建议 reasoning + tools 优先使用 Responses。Harnex 不发送 `tool_choice`，能力配置中不提供 `tool-choice-policy`。
- `reasoning-replay` 用来表达厂商静态差异：`tool_calls` 只在 assistant 发起工具时回放，`all` 回放所有适用 assistant reasoning，`native_items` 用于 Responses/Anthropic/Gemini 等原生 item/block/step 状态。Chat 型号还可声明 `reasoning-history:none/optional/required`；用户通常保持 `features.reasoning-history:auto`，只有明确需要可选的跨轮推理保留时才用 `preserve`。
- 缓存方式由所选服务与型号的内置能力自动选择；用户通常保持 `features.prompt-cache: auto`，无需判断 system 或历史消息能否缓存。运行时根据已有 `prompt-cache-mode` 与请求类型生成缓存控制；未知端点使用保守协议基线。
- 原生 web search 同样要求双门控，但不会因型号不支持而让请求失败：用户 `features.web-search:auto|on` 表示原生优先；所选 model 按 rule→exact 合成后的 capability 只有同时包含 `native-web-search:true` 和非空工具类型时，Responses/Anthropic/Gemini 才暴露服务端工具并移除该请求中的本地 `web_search`。能力未命中时不发送原生字段，已配置且健康的本地 `web_search` 会继续作为 function tool；`off` 只关闭原生偏好，Chat 继续使用本地工具。
- 内置 Anthropic profile 的未知 model/relay alias 不自动开启严格 late-refusal 缓冲；官方 Claude 型号由 profile-local rule 设置 `strict-terminal:true`。自定义 alias 必须先做终态契约测试，再用 `capability-model` 选择对应规则或显式声明差异。
- `request-options` 只适合官方文档明确的静态扩展。适配器会拒绝覆盖 `model`、`messages`、`input`、`tools`、`stream` 等协议保留键。
- Reasoning 回放统一由 model capability 的 `reasoning-replay` 控制。

##### 会话和 Agent 的历史缓存

普通会话与 Agent 尽量保留稳定系统前缀及已经发送的历史。动态会话事实放在近期输入位置；Agent 新状态随最新安全输入／工具结果加入，已经发送的状态投影保持原样，由较新的状态明确替代。相同工具集的顺序与 schema 序列化保持稳定。角色、工具调用配对、权限及原始档案不为缓存让步；用户纠正、分支重建、压缩、模型或工具能力变化仍可能导致必要的前缀失效。

选择服务和型号后，运行时自动区分普通会话、Agent 主请求与一次性辅助调用，采用对应的缓存策略。端点/型号能力由项目维护，不需要额外配置历史缓存开关；高级自定义端点仍使用已有的协议能力声明。

| 已声明的协议能力 | 带会话 scope 的主请求 | 无会话 scope 的一次性辅助请求 |
| --- | --- | --- |
| `openai_explicit` | 保留现有首部指令表示与断点，使用 `prompt_cache_options.mode: implicit`，允许历史 user/tool 边界复用 | 显式缓存首部指令 |
| `content_cache_control`（Anthropic / Qwen） | 保留首部断点；在最近最多三个现有输入消息末尾添加断点，包含工具结果批次末尾；总数不超过四个 | 缓存首部指令 |
| `auto_prefix` / `key` / `none` | 保持原协议行为，不发送其他厂商的缓存字段 | 同左 |

历史断点按适配完成后的消息选择，不拆分 system，不合并工具消息，不修改带签名的 assistant/thinking 原生内容。Qwen 使用消息末尾边界；Anthropic 使用已有 user 内容块（包括 tool_result）末尾边界，避免依赖兼容服务未实现的顶层自动缓存字段。TTL 保持端点默认值，最低长度和是否命中以实际模型为准；不会填充提示词或主动发送预热请求。

启用 DEBUG 日志的 `com.harnex.provider.PromptCachePlan` 可查看实际采用的历史缓存策略及新增断点数，日志不包含提示词正文。实际收益结合调用记录中的 `cachedInput`、`cacheWriteInput`、首字延迟及用量账本费用判断；缓存标记或相同 scope 不代表已经命中。DeepSeek 的 `prompt_cache_miss_tokens` 计入普通输入，不计为显式缓存写入。`features.prompt-cache: off` 关闭 Harnex 的主动缓存控制，不能保证关闭厂商默认的隐式缓存。

协议依据：[OpenAI Prompt caching](https://developers.openai.com/api/docs/guides/prompt-caching)、[Claude Prompt caching](https://platform.claude.com/docs/en/build-with-claude/prompt-caching)、[百炼上下文缓存](https://help.aliyun.com/zh/model-studio/context-cache)。

##### 第三方网页搜索设置

打开 **设置 → 网页搜索**，启用第三方搜索并选择一个服务：Tavily、Exa、Brave Search、SearXNG、Perplexity（当前使用 Sonar）、AnySearch 或 TinyFish Search。云服务填写 API Key；SearXNG 填写实例根地址，并在实例侧启用 JSON 搜索响应，无需 API Key。高级设置可调整自定义搜索接口、最大结果数（默认 10，仅要求正整数）和超时（默认 15 秒）。网络连接沿用当前运行环境的网络设置。

AnySearch 使用独立 Search API，校验 HTTP 状态与业务结果码；本项目要求 API Key，不使用匿名自动注册流程。TinyFish 使用独立 Search API，不调用 Browser/Agent；其接口未提供结果数量参数，Harnex 仅按用户设置截取已返回的结果，不自动分页。两项均可在高级设置选择搜索语言（中文/英文/服务默认）；留空时遵循服务默认值，TinyFish 当前默认英文与美国地区。Harnex 不写死服务商的结果数或每分钟请求上限，官方 API 返回的参数错误和限流沿用既有错误处理。接口依据：[AnySearch](https://www.anysearch.com/docs/api-endpoints/v1-search)、[TinyFish Search](https://docs.tinyfish.ai/search-api/reference)。

“测试搜索”使用尚未保存的填写内容执行一次固定查询，展示耗时和最多三条结果；不会修改配置或当前服务的熔断状态。已保存的密钥以掩码展示，未修改时会保留；切换服务会清空密钥及自定义地址，避免跨服务误用。“已配置”只代表必要字段已填写；测试成功是一次请求的结果，不保证后续请求始终可用。修改配置后旧测试结果会标记过期。

保存后用于新任务；同时改变全局 HTTP 代理等连接依赖时按提示重连。该配置属于用户级设置；从 Personal 页面也可以配置和测试，但第三方搜索仅用于项目 Agent，且需要所选工具集包含 `web_search`。Personal 对话继续仅使用模型原生搜索。关闭此页开关不影响模型原生搜索；原生搜索未启用或能力未声明时 Agent 才使用已配置的第三方，原生请求报错不会自动切换到第三方服务。已有的调用失败提示与熔断机制保持不变。

项目 Agent 中，工具集的 `web_search` 同时控制原生与第三方搜索权限；移除它将禁用两条搜索路径。保留它并不保证搜索可用：模型不支持原生搜索、第三方又未配置时，不向模型提供搜索工具；即使模型仍尝试调用，也会在本地直接返回不可用，不会请求第三方服务。新会话的提示词使用固定条件指引，不随每轮搜索状态变化；已有会话的 system 前缀保持不变。

| `openai-chat` → GPT-5.6 Sol/alias 规则 | GPT-5.6 Sol 与 `gpt-5.6` alias Chat | standalone `none..max`；function tools 时 effective effort 必须为 `none`（省略自动补齐，显式其它值本地失败）；稳定前缀显式缓存 |
| `openai-chat` → o3 规则 | o3 Chat | `low/medium/high` effort、无 sampling 参数 |
| `openai-responses` → GPT-5.1 / GPT-5.5 规则 | GPT-5.1 / GPT-5.5 Responses | 完整 reasoning/output item 原生回放、cache key；各版本独立 effort 白名单 |
| `openai-responses` → GPT-5.5 Pro 规则 | GPT-5.5 Pro Responses/Batch | 非流式，防止被普通 5.5 规则误当成交互式流 |
| `openai-responses` → GPT-5.6 规则 | GPT-5.6 Responses | 完整 output item 回放、`none..max` effort；无 Chat function-tools/effort 组合约束；显式稳定前缀缓存 |

GPT-5.5 Pro 的非流式契约保留在 `openai-responses` 的首条能力规则中，但不放入默认交互模型列表；需要时应为 one-shot/Batch 路径显式配置，不能加入 SSE 主路由冒充普通 GPT-5.5。

要让模型使用厂商服务端原生搜索，在 Responses/Anthropic/Gemini provider 上显式开启用户 intent：

```yaml
harnex:
  providers:
    openai-responses:
      profile: openai-responses
      features:
        web-search: on
```

这不会给未知型号“补能力”：所选 model 按 rule→exact 合成后的 capability 仍须声明 `native-web-search:true` 和工具类型，二者缺一时适配器会省略原生工具，而不是发送无效配置或报能力错误。`native-web-search-type` 只配置在 model capability，provider 层不提供该字段。能力命中时该 provider 的请求只保留原生服务端搜索工具；能力未命中时，若 Harnex 本地 `web_search` 已配置且健康，它仍作为 function tool 提供，否则请求中没有搜索工具。Chat Completions adapter 不转换为原生搜索。

#### 9.1.7 Anthropic Claude / OpenAI Responses / Google Gemini 原生协议

- **Anthropic Claude（已支持原生直连）**：`type: anthropic`，走原生 Messages API（`/v1/messages`）。设置 `ANTHROPIC_API_KEY` 并启用 Provider 后即进入模型目录。支持 `tool_use`、thinking/effort、prompt caching、思考块签名跨轮回放、原生 web search，以及显式声明后的图片/PDF 输入；native search 在用户 intent 为 `auto/on` 且所选 resolved capability 声明支持时启用，未声明时安全降级到可用的本地搜索。遇到服务器工具返回 `pause_turn` 时，provider 会把这次 assistant content blocks 原样加入历史并使用同一套 model/system/tools/options 自动续接；`server_tool_use` 及其 hosted result 只回放给 Anthropic，不转换成本地 `ToolCall`。单次用户请求最多自动续接 4 次，错误或超限会安全终止并清除未提交的工具/opaque state，避免半成品被执行。通过兼容网关调用 Claude 时，应按网关实际暴露的协议选择 type，不能只看模型名。
- **OpenAI Responses API（已支持原生直连）**：`type: openai-responses`，面向 GPT-5.x / o 系列（`/v1/responses`）。无状态模式会设置 `store:false` 并请求加密 reasoning；成功且原生 function calls 与 AgentLoop 最终接受结果一致时，完整 `response.output` items 才会按原顺序和原字段保存/回放，从而保留 reasoning、item id、`phase`、`caller` 以及未来扩展 item。快照缺失、损坏或不匹配时只重建已验证文本/function calls，不回放不可信 opaque state。`response.incomplete` 会保留已显示的部分文本，但以 incomplete 终止、不执行其中工具、不产生可回放 continuation state；refusal 会作为明确标记的文本/终态呈现。图片和普通文件分别要求精确模型声明 `image` / `file`，否则降级为 `file_read`/OCR 提示。支持 capability/intent 双门控后的原生 web search。GPT-5.5 Pro 不支持交互式 Responses 流时应改用 one-shot/Batch 或基础非 Pro 型号。工具轮应保留完整 output，参见 [OpenAI 官方 reasoning items 指南](https://developers.openai.com/cookbook/examples/responses_api/reasoning_items#how-reasoning-models-work)。
- **Google Gemini（已支持原生直连）**：`type: gemini`，选择 `gemini-interactions` profile，走 `https://generativelanguage.googleapis.com/v1beta/interactions`。适配器使用 `store:false`，把成功响应的完整 step 列表按原顺序保存并在下一轮回放，因此 thought signature、function call/result 及内置 Google Search step 不会被 OpenAI messages 形状抹平；完整 stateless thought replay 依据 [Google thought signatures 指南](https://ai.google.dev/gemini-api/docs/thought-signatures)。支持 function tools、capability/intent 双门控后的 Google Search，以及精确 model 声明后的图片、PDF/CSV、音频和视频内联。流式事件和 step 形状以 [Interactions API](https://ai.google.dev/api/interactions-api) 与 [streaming 指南](https://ai.google.dev/gemini-api/docs/streaming)为准。最小配置如下：

Personal `CONVERSATION` 允许上述 Provider 在一次模型请求内执行其原生 hosted web search，但仍不加载 Agent 的本地工具注册表。因此支持原生搜索的精确模型可按 `features.web-search:auto|on` 使用服务端搜索；不支持原生搜索时直接省略搜索工具，不会在 Personal 会话中启动第三方 `web_search` function-call 循环。

  ```yaml
  harnex:
    providers:
      my-gemini:
        profile: gemini-interactions
        api-key: ${GEMINI_API_KEY:}
        default-model: gemini-3.6-flash
    router:
      default-provider: my-gemini
  ```

#### 9.1.8 多 provider 组合实战（高级完整列表）

```yaml
harnex:
  providers:
    primary:                 # 主任务：高智商
      profile: openai-compatible-chat-safe
      base-url: https://openrouter.ai/api/v1
      api-key: ${OPENROUTER_KEY:}
      default-model: anthropic/claude-3.5-sonnet
    fallback:                # 失败容灾：国内直连
      profile: deepseek-v4
      base-url: https://api.deepseek.com/v1
      api-key: ${DEEPSEEK_KEY:}
      default-model: deepseek-v4-flash
    cheap:                   # 可选的独立摘要器端点；子 Agent 不单独选模型
      profile: deepseek-v4
      base-url: https://api.deepseek.com/v1
      api-key: ${DEEPSEEK_KEY:}
      default-model: deepseek-v4-flash
    local:                   # 离线兜底
      profile: openai-compatible-chat-safe
      base-url: http://localhost:11434/v1
      api-key: ""
      default-model: <本地服务当前已安装且支持 tools 的模型 ID>
  router:
    default-provider: primary           # cheap 仅作 summarizer；local 仍可由会话显式选择
  summarizer:
    enabled: true
    provider: cheap
    model: deepseek-v4-flash
```

> ⚠️ **注意**：Agent 模式要求模型和端点都支持 function/tool calling。不要用静态“某家某代一定支持”的清单代替能力验证；同一模型经不同网关转发时也可能丢失工具字段。上线前至少验证一次“模型发起工具 → Harnex 回灌结果 → 模型给出最终文本”的完整闭环。

#### 9.1.9 Prompt cache 使用原则

- 把稳定的 system/instructions、工具 schema、权限策略放在请求前缀，用户消息、工具结果、时间戳等动态内容放在后面；不要每轮重排工具或改写等价 system 文本。
- 支持 `prompt_cache_key` 的官方端点自动使用经 provider/model 隔离并散列后的 thread id：同一会话跨轮稳定、不同会话隔离，用户无需配置或向上游暴露内部 id；one-shot 无 thread id 时回退到稳定前缀指纹。显式 breakpoint 只应在对应模型官方支持时开启。Anthropic 使用其原生 `cache_control`。第三方兼容端点未声明支持时不要发送 OpenAI 专有缓存字段。
- 缓存是精确前缀匹配优化，不是会话存储。是否命中以响应 usage 的 cached-token 字段为准；请求成功或设置了 key 不代表已经命中。
- 国产厂商的缓存 usage 字段和 retention 规则并不统一。接入前先看厂商文档，并用重复的长稳定前缀做一次契约测试。

### 9.2 YAML 配置与图片模型

完整、可校验的字段模板统一维护在[agent-config.example.yml](../agent-config.example.yml)，内置默认值位于[后端配置](../backend/src/main/resources/agent-config.yml)。手册不再复制整份默认配置，避免实际代码已改变而文档仍保留旧参数。

```yaml
harnex:
  data-dir: .harnex/data
  skills-dir: .harnex/skills
  image-services:
    illustrations:
      label: 插图模型
      profile: openai-images
      base-url: ${IMAGE_BASE_URL:https://api.openai.com/v1}
      api-key: ${IMAGE_API_KEY:}
      model: ${IMAGE_MODEL:}
  default-image-service: illustrations
```

`IMAGE_MODEL` 应填写服务实际支持的图片型号。Responses 生图改用 `profile: openai-responses-image`，并增加支持图片工具的 `main-model`，保留独立图片 `model`。`illustrations` 是配置内部键；界面显示 label／model，不要求用户另找服务 ID。只有确认要用图片功能时才添加该配置。

设置页也可选择以下原生图片协议，两者都复用会话和 Agent 的 `image_generate` → 素材保存 → `image_inspect` / `image_export` 链路：

| Profile | 接入方式 | 参数边界 |
|---|---|---|
| `gemini-images` | Google 原生 `generateContent`，使用 `x-goog-api-key`；地址可填 API 根、`/v1`、`/v1beta` 或匹配型号的完整 endpoint。例：`gemini-nano-banana-2.1` | 文生图和参考图编辑，单次 1 张、最多 14 张参考图；PNG，quality/background 仅 `auto`，不支持 mask。尺寸使用服务返回的 presets，可选常见 1K/2K/4K 尺寸；模型自身仍需支持对应分辨率。 |
| `dashscope-images` | Qwen 原生同步 `/api/v1/services/aigc/multimodal-generation/generation`；必须填写账号工作空间和地域对应的 `/api/v1` 地址，不填 compatible-mode。例：`qwen-image-2.1-pro` | 文生图和参考图编辑，最多 6 张输出；2.1 型号最多 10 张参考图，其他型号保守限制 3 张。PNG，quality/background 仅 `auto`，不支持 mask。尺寸 `宽x高` 转换成原生 `宽*高`；总像素限制 512²–2048²，宽高比限制 1:8–8:1。 |

原生接口未声明的质量、透明背景控制、mask 或超量请求会在发送前拒绝，避免静默忽略用户参数。透明效果仍可由模型根据提示词生成，但不宣称支持通用 `background=transparent` 开关。参考图以素材 ID 读取，不发送主机路径。Gemini 的 thought 预览图和被拒绝候选不会发布为结果；Qwen 的图片 URL 下载后保存为本地素材，下载不会携带 API Key，且拒绝私网地址和重定向。

上述适配器使用同步完整响应，尚未接入供应商后台任务轮询或渐进图片预览。取消会中止本地连接，不把它描述为已撤销服务商侧任务；响应中断也不会自动重发付费生成请求。参数依据：[Gemini 生图](https://ai.google.dev/gemini-api/docs/generate-content/image-generation)、[Qwen 原生接口](https://help.aliyun.com/zh/model-studio/qwen-image-generation-and-editing-api-reference)。

图片服务请求统一使用“网络”中的全局代理及绕过规则；旧配置中的图片服务 `proxy` 字段不再覆盖全局设置。高级设置仅保留图片请求超时，用于适应生成图片耗时较长的情况。

未指定数量时仍生成 1 张。OpenAI Images 协议默认允许用户明确请求 1–10 张，当前 Responses 图片调用每次限 1 张；显式设置的 `capabilities.max-count` 可进一步收紧数量。OpenAI 的尺寸可使用 `auto` 或 `宽x高`（如 `1536x864`），默认不以固定尺寸列表拦截请求；原生接口采用上表的边界。非空的 `capabilities.sizes` 列表会进一步限制支持的尺寸，不能扩大协议能力。上游拒绝请求时，错误详情会保留脱敏后的错误码、参数名和原因，不会自动重发请求。

单价可选；语言模型在对应 model 定义配置 input/output/cached/cache-write 每百万 Token 费率，图片选择每张或分项 Token 计价。费率不决定实际 Token 用量，也不自动同步供应商价格。

### 9.3 环境变量速查表

> 配置的整体加载机制、各形态的文件目录、改配置的两条路线见 [§9.0](#90-配置怎么读取怎么改最重要先读这一节)。本节只列**变量清单**。

`agent-config.yml` 里所有形如 `${VAR_NAME:default}` 的占位符都遵循 Spring Boot 标准外部化配置规范，按以下优先级解析（高优先级覆盖低优先级）：

1. 命令行参数 `--VAR_NAME=...`（最高）
2. JVM 系统属性 `-DVAR_NAME=...`
3. 操作系统**环境变量** `VAR_NAME=...`（最常用）
4. 都没有 → 使用 `:` 后的默认值

#### 设置方式

| 部署方式 | 设置方法 |
|---|---|
| **docker-compose** | 在 `backend.environment:` 块加 `KEY: "value"` |
| **Kubernetes** | Deployment `spec.containers[].env` 或 ConfigMap/Secret 挂载 |
| **systemd** | service 文件 `[Service]` 段 `Environment=KEY=value` |
| **Linux/macOS shell** | `export KEY=value` 或一次性 `KEY=value mvn spring-boot:run` |

## 10. 常见问题 FAQ

**Q1. 支持哪些大模型？怎么接入第三方平台 / 中转网关 / 国产大模型 / 本地推理？**

A：当前有四种 Provider。原生 OpenAI Responses、Anthropic Messages、Google Gemini Interactions 分别使用 `openai-responses` / `anthropic` / `gemini`；国产模型、中转网关和本地推理通常使用 `openai-compatible`。后者在服务端完整实现 `/v1/chat/completions`、SSE、`tool_calls` 和标准终止字段时，可直接获得文本/流式/工具基线，但不代表厂商扩展能力完全透明。详见 §9.1「大模型接入大全」。

- ✅ **原生适配**：OpenAI Responses、Anthropic Messages、Google Gemini Interactions。
- ✅ **共同基线**：DeepSeek、Kimi/Moonshot、智谱 GLM、DashScope Qwen、豆包 Ark，以及 OpenRouter、SiliconFlow、One-API/New-API、Ollama、vLLM、LM Studio 等端点，在其确实实现标准 Chat/SSE/tool-calls 时可接入。
- ⚠️ **厂商扩展**：thinking 的开启/关闭与跨轮回放、reasoning effort、缓存、图片/文件 shape、usage 和特殊终止原因必须逐端点核对；精确模型的输入模态需要显式声明。
- ✅ **Google Gemini 原生**：使用 `gemini-interactions` profile；只有在现有网关确实只提供 OpenAI 协议时才改用 `openai-compatible`，此时能力边界以网关为准。

普通用户用 `harnex.providers.<id>` 配 `profile/base-url/api-key/default-model`；省略 `features`
即为安全的 `auto`。`provider-profiles/model-capability-rules` 是高级维护层。

多 provider 同时配置后，可以在以下三处单独指定模型：
1. 后端 `harnex.providers.<id>.default-model`
2. 前端聊天框模型选择（按本次会话覆盖，不会持久化 Provider 配置）
3. CLI `--model` 启动参数 / `/model <name>` 斜杠命令

交互式 Chat 粘住所选 Provider，对瞬时故障完成有界重试后只切换到保留 id `fallback`；不会沿全部 Provider 逐个消耗。切换和重试都只发生在用户尚未看到 token 之前，避免拼接或重复输出。摘要器仍可单独指向廉价 Provider 节省成本（见 §9 设置 `harnex.summarizer.provider`）。

**Q2. Agent 卡死怎么办？**
A：三种办法——（1）WebUI 点 STOP（`POST /api/v1/runs/{runId}/cancel`）显式中断；（2）只想离开页面时直接导航，Run 与 SSE 订阅生命周期已经分离，稍后从 Run/Thread 权威投影重挂；（3）普通交互 Run 默认受 `interactive-max-iterations=64` 硬止损，Goal 还受独立的 turns/model/tool/token/cost/wall-clock 预算；把限制设为 0/负值只关闭对应层，不能绕过安全策略。

**Q3. Agent 能记住上次聊的事吗？**
A：**会话内**全部记得；**跨会话**需要：
  1. 让它用 `memory_remember` 写入关键事实，下次自动注入；或
  2. 让它用 `session_search` 工具自己去捞旧会话。

**Q4. SKILL.md 可以嵌套吗？**
A：可以，`SkillLoader` 最多搜到第 3 层，但**一个技能一个目录**是推荐做法。

**Q5. 同时有几个人用会怎样？**
A：支持，但默认无鉴权。生产环境请：
```bash
export HARNEX_AUTH_ENABLED=true
export HARNEX_AUTH_TOKENS=team-alice-xxx,team-bob-yyy    # 逗号分隔
```
显式认证的 API 客户端在 HTTP 头添加 `Authorization: Bearer <token>`；失败 60s 内 ≥20 次会被临时封 IP。
`/api/v1/auth/login` 成功后会下发 `HARNEX_TOKEN`（HttpOnly + SameSite=Strict）Cookie，
同源 `EventSource` / `fetch` 可自动携带，禁止把 token 放进 URL。

> ⚠️ 安全：`/api/v1/runs/{runId}/events` 等 SSE 端点**不支持** `?token=xxx` 查询参数回退——URL 参数会泄漏到 Nginx access log、浏览器历史、CDN 日志、Referer、崩溃报告等。请改用上述 Cookie 方案，或在非浏览器客户端用 `Authorization: Bearer` 头。

**Q6. 如何把 Agent 的结果对接到飞书/钉钉/TG？**
A：本地桌面使用钉钉、企业微信、飞书或 Telegram，优先使用下面的 **IM 客户端**，无需公网地址。其他平台或自建桥接可使用通用 Webhook。

#### IM 客户端：钉钉 / 企业微信 / 飞书 / Telegram

打开要操作的项目，进入 **设置 → IM 客户端**。连接属于当前工作区，个人普通会话不提供此入口。

**项目任务通知**：

1. 连接机器人并确认会话授权后，在本页“项目默认通知会话”选择一个收件人。列表按平台、机器人、私聊／群聊、用户和会话 ID 区分；未连接但仍已授权的会话可选，连接恢复后发送。授权不等于订阅，默认不向所有会话广播。
2. 点击项目任务页顶部的铃铛，开启“IM 提醒”。当前客户端按项目记住开关，后续普通 Agent 和 `/goal` 任务沿用；发送、新建任务和刷新页面不会自动取消，直到手动关闭。修改开关仅影响后续启动的任务，正在运行的任务保持启动时的通知设置。项目自动化仍按每个计划保存提醒配置，可选择“仅失败”。
3. 收件人随任务启动固定。修改默认会话只影响后续启动的任务；Goal 继续执行仍使用原收件人。设置被清空或授权失效时，新任务开启提醒需要先修复收件设置。
4. 通知包含项目、运行主机、任务描述、状态和完整文本结果；长结果按平台消息长度限制编号分段，前段确认送达后才发送后段。需要验收或继续处理时，仍需回到 Harnex 操作。Goal 只在完成、待验收、受阻或预算限制时提醒，每轮执行不单独通知；主动暂停／取消不提醒。从 IM 发起的任务继续回复原会话，不另发通知。

执行结果和投递状态分开保存。授权撤销或机器人更换后停止向旧收件方发送，不自动换人；网络断开时排队，恢复后发送。临时错误重试消息，发送结果未知时提示核对，不重复执行任务。投递问题仍在本页的发送记录中查看。项目 Runtime 必须运行；关闭项目后不会新增后台进程，重开后可恢复持久记录中的待投递结果。

钉钉通知使用主动消息接口，因此除了现有收消息／卡片权限，还需机器人具有相应主动发送权限及接收范围。平台拒绝时会显示投递原因；未知私聊／群聊类型的旧授权需要先在该会话给机器人发一条消息，再选择通知会话。飞书、企微和 Telegram 复用现有发送通道。

**个人使用优先选择机器人私聊，无需建群，也不用每条消息 @**。钉钉企业内部应用机器人发布后，在客户端搜索机器人名称，从“功能”结果进入单聊；飞书应用机器人可搜索名称进入单聊，Harnex 连接成功后也提供“打开飞书私聊”入口。找不到时检查应用已发布、当前账号所在组织及应用可见范围。应用的组织／团队身份是平台侧创建和发布要求，与是否使用聊天群不同。这里使用的是应用机器人，不是仅推送群消息的自定义 Webhook 机器人。

从群聊改用私聊时，首次消息会为这个新会话申请授权，需在 Harnex 再确认一次；以后直接连续发消息即可。群聊仍按平台与当前适配器的 @ 规则处理。钉钉群内未 @ 的普通消息通常不会投递给机器人，Harnex 无法靠去掉本地检查收到它们；飞书当前也只接受群内明确 @当前机器人的任务。

**Telegram 首次接入**：在官方 [@BotFather](https://t.me/BotFather) 发送 `/newbot` 创建机器人，在 Harnex 的 Telegram 标签页填入完整 **Bot Token**，点击“保存并连接”。Bot ID 自动从 Token 提取，无需手工填写。私聊先发 `/start`，到 Harnex 核对并确认会话授权，再重发任务。原生按钮支持批准／拒绝、问答选项、详情、取消，终态会清除按钮，无需创建卡片模板。

Telegram 的 [Bot API](https://core.telegram.org/bots/api#getupdates) 使用 HTTP 长轮询接收消息，钉钉／飞书使用 WebSocket 长连接；区别在平台协议和应用配置，Harnex 内的授权、模型命令和审批流程相同。Telegram 无需企业应用发布和事件订阅，同一 bot 的长轮询与 Webhook 互斥。已有 Webhook 时先在原服务关闭，Harnex 不会自动删除；其他地方也在长轮询时需停止另一处接入。无法连通 Telegram 时检查全局代理。

Telegram 普通群中明确 `@机器人用户名`，或发送 `/status@机器人用户名` 等定向命令。平台 [群隐私模式](https://core.telegram.org/bots/faq#what-messages-will-my-bot-get) 可能不投递普通 @消息：可以回复机器人的消息并明确 @它，或在 BotFather 关闭 Group Privacy 后重新加入群。Harnex 始终要求明确提及当前 bot，不会把它收到的全部群消息当作任务。暂不处理频道、匿名发送者、论坛话题、消息编辑及附件。

**同一机器人与多个工作区**：同一用户数据目录内只有一个 Runtime 能持有该机器人的连接，消息进入持有连接的项目。默认切换项目时关闭原连接，新项目按保存设置连接；若原 SSH 项目选择保留运行，机器人继续服务原项目。授权和会话历史按项目独立保存。普通回复标注运行主机、项目名和 scope ID，`/工作区`（`/workspace`）显示完整路径。已授权会话切换到另一项目后，首条普通任务只提示新目标，不执行；核对后重发才处理。控制命令可直接查询。Telegram 还会跳过交接时刻及以前的积压文字消息，避免旧任务落入新项目。连接锁与切换记录仅覆盖同一用户数据目录，不跨电脑协调。

**跨工作区复用**：保存机器人时会同时加入“复用已保存的机器人”列表。新工作区选择机器人即可填入 ID、密钥占位及卡片模板，再点击“保存并连接”，无需重新输入密钥。选择本身不连接，也不复制其他工作区的会话授权、写入权限或 YOLO 权限；首次消息仍需在本工作区确认授权。密钥仍可通过眼睛按钮查看。各工作区保存独立的连接副本，修改一个工作区的凭据不会自动替换其他工作区的连接；需要更新时重新选择已保存的机器人并保存。

可复用凭据保存于用户数据目录的 `im/credentials.json`（默认 `~/.harnex/im/credentials.json`），只包含平台、机器人 ID、密钥和卡片模板；列表接口不返回密钥。工作区授权及连接设置仍保存在项目数据目录。复用范围是同一台 Runtime 主机、同一用户数据目录；远程工作区使用远端目录，不自动复制本机凭据。

1. 钉钉：创建企业内部应用，开启机器人，选择 **Stream** 接收模式，发布应用并设置可见范围。填写 Client ID / AppKey、Client Secret / AppSecret。
2. 企业微信：创建支持 API 模式的智能机器人，选择**长连接**，填写 Bot ID、Secret。此模式不使用群 Webhook、Token 或 EncodingAESKey。
3. Secret 输入框的眼睛按钮可显示／隐藏明文，已保存的 Secret 也可按需查看。点击 **保存并连接** 后，按钮下方直接显示连接中、认证中、已连接或失败原因，并自动滚动到可见位置；保存成功不代表连接成功。无法取得最新状态时显示“状态未知”。认证失败时检查凭据及平台模式，再点“重新连接”或再次“保存并连接”。同一机器人在本机只能由一个工作区持有连接。
4. 直接给机器人发送一条文字消息，群聊中请 @机器人。首次消息会自动生成授权申请；在十分钟内回到 Harnex，核对两端相同的确认码、用户及会话，点击 **确认授权**。首次消息尚未执行，确认后请重新发送任务。
5. 以后直接发送文字任务即可。每个“机器人＋用户＋会话”保留独立上下文；其他来源需要分别获得本地授权。`/绑定` 保留为兼容命令：未授权时申请，已授权时显示状态，不重复创建会话。重复申请更新同一条待授权记录。

**飞书首次接入**：创建企业自建应用并添加机器人能力，在本页选择“飞书”，填写 App ID、App Secret（或复用已保存的机器人），点击“保存并连接”。再到飞书“事件与回调”选择长连接接收事件及回调，订阅接收消息 `im.message.receive_v1` 和新版卡片回传交互 `card.action.trigger`。开通读取机器人单聊、接收群内 @机器人、以应用身份发送消息的权限，发布应用版本并设置可用范围，然后在 Harnex 重新连接。群聊要将机器人加入群并 @当前机器人，私聊直接发送；首次来源授权与钉钉／企微相同。

飞书使用原生 JSON 消息卡片，无需创建或填写卡片模板；按钮支持审批、问答选项、详情和取消。回复发回原私聊或群聊，各来源的上下文和授权独立。机器人身份未就绪时设置页给出原因，群消息暂不处理；长连接已建立仍可用于保存飞书后台订阅设置。当前只接收文字任务；媒体传输和国际版 Lark 尚未接入。飞书真实账号的发布、收发和按钮点击仍需现场验收，不能以模拟协议测试代替。

**钉钉按钮卡片的首次配置**：为同一个应用开通 `Card.Instance.Write` 权限。在钉钉卡片平台新建模板，**卡片类型选“消息卡片”，模板场景选“普通卡片”**，关联当前机器人应用。在 Harnex 的“按钮审批与点选问答”区域下载模板 JSON，在钉钉编辑器的“更多 → 导入”中导入，检查预览后保存并发布；把发布后的模板 ID 填回 Harnex，保存并连接。模板源文件在 `backend/src/main/resources/im/dingtalk-interaction-card.json`，可用 `node scripts/build/im-card-template.mjs` 重新生成。导入文件使用消息卡片的 `type: im`、`Card` 根组件与 `ButtonList` 按钮组件；若旧下载文件报“卡片类型不符合”，请使用修正后的文件，旧版 `type: standard` 属于标准卡片，不能导入消息卡片模板。导入文件包含可编辑设计数据，最终渲染模板由平台设计器在预览／发布时生成。未配置模板或平台明确拒绝创建时，退回文字提示；卡片请求结果未知时不会重复创建，会提示用 `/状态` 查看。

当前钉钉审批／问答卡片只需要 `Card.Instance.Write`，不需要 `Card.Streaming.Write`；后者用于 AI 卡片内容的流式更新，与机器人接收消息及按钮回调使用的 Stream 长连接是不同能力。

模板保留三组、最多六个按钮。默认审批示例只用四个按钮，编辑画布中第三组可能显示空白占位，预览／实际消息应只有两行；四选项问答会使用第三组显示“查看详情／取消任务”。不要删除预留按钮。各按钮的“请求成功判定条件”绑定私有变量 `actionSucceeded`，服务端在每次点击回调中返回本次处理结果；收到回调不等于批准成功，过期、越权或重复点击会显示未能处理，具体原因显示在卡片中。替换旧模板时需重新导入、保存并发布，同时使用包含该回调字段的新版 Runtime。

企微智能机器人直接使用原生模板卡片，无需另建模板。卡片包含操作摘要、发起人、工作区、实际截止时间、“查看详情”及“取消任务”；审批提供“仅批准本次／拒绝”，问题展示前四个选项按钮，其他选项仍可输入序号。文件操作说明路径、内容预览或替换内容，命令展示工作目录与命令。完整参数可按需查看，常见凭据字段会隐藏。

| 命令 | 行为 |
| --- | --- |
| `/帮助` / `/help` | 查看使用方法 |
| `/状态` / `/status` | 查看当前任务、工具进度及待处理交互 |
| `/取消` / `/cancel` | 请求停止自己的当前任务；已完成的文件操作不自动撤销 |
| `/结果` / `/result` | 取得上一项任务结果，不重新执行任务 |
| `/模型` / `/model` / `/models` | 查看下次任务使用的模型及已配置、启用的模型列表，不调用模型服务 |
| `/模型 编号` 或 `/模型 服务商:模型` | 为自己在当前机器人会话中选择模型，下次任务生效；编号对应最近一次查看的列表 |
| `/模型 默认` | 恢复跟随默认模型，并将强度恢复为 `auto` |
| `/强度` / `/effort` | 查看当前强度及模型支持的档位；例如 `/强度 high`、`/强度 auto` |
| `/模式` / `/mode` | 查看模式；`/模式 ask` 按策略确认，`/模式 yolo` 自动执行普通工具操作，需先在 Harnex 本地允许 |

| `/拒绝 编号 原因` / `/deny CODE REASON` | 拒绝操作，或附修改意见拒绝计划 |
| `/回答 编号 内容` / `/answer CODE TEXT` | 回答问题，选择题也可填选项序号 |
| `/详情 编号` / `/details CODE` | 查看对应请求的完整操作内容 |

默认只读。需要修改文件时，明确勾选“允许已绑定会话请求修改工作区”并保存；工作区路径、工具审批和隔离规则仍生效。可直接点击对应按钮；编号命令保留为备用。只有一个待处理请求且它是问题时，可以直接回复“2”“选第二个”、完整选项或自由答案；多个请求时需要指定卡片或编号。裸发“同意”不会批准工具操作。

模型故障时，直接在 IM 中发送 `/模型`，再发送 `/模型 2` 等指令选择备用模型；群聊同样需要 @机器人。这些命令、`/强度` 和 `/模式` 由客户端直接处理，不依赖当前模型回答，也不进行收费的联网探测。列表仅表示已配置、启用，切换成功不等于连通性测试通过。切换后重新发送任务；原任务不会自动重做。切换范围是当前项目中的“机器人＋用户＋会话”，重启后保留选择，其他用户和会话不受影响。正在执行的任务使用启动时确定的设置，切换作用于下一条任务；要停止当前任务请发送 `/取消`。更换模型会将强度恢复为 `auto`，避免沿用不兼容的档位；其他强度只能从该模型声明支持的选项中选择。

默认模式为 `ask`。只有在 Harnex 本地同时开启“允许已绑定会话请求修改工作区”和“允许在 IM 中选择 YOLO”并保存后，已绑定用户才可发送 `/模式 yolo`；它跳过普通工具确认，仍遵守工作区权限、禁用工具、危险命令限制和全局审批策略。关闭本地授权后，后续 IM 任务按 `ask` 执行。`/模式 ask` 可恢复本会话的确认模式。

在 Harnex 的 **设置 → IM 客户端 → 正在执行的 IM 任务** 中，可看到请求用户、会话、模型和当前进度，点击 **查看执行过程** 进入对应 Agent 会话，查看消息、工具调用、文件变更及结果。钉钉、企微和其他 Webhook 的请求也会进入当前项目的会话历史，用户消息显示来源与发送者；运行中的会话打开后会接续实时执行过程。已打开的空闲会话每三秒检查新外部任务并接续显示，保留输入草稿。客户端会刷新会话列表，已展开的历史列表保留。

IM 工具审批默认等待十分钟，并按剩余运行预算缩短；问题、计划沿用各自配置，并受单任务时限约束，卡片显示实际截止时间。点击会再次校验机器人、发起人、原会话、具体请求与当前等待状态。钉钉可原位更新已批准／已拒绝／已回答／已取消／已过期状态并隐藏按钮。企微在按钮点击回调中更新发起人的卡片；超时、在其他客户端处理等无点击回调的情况另发状态通知，旧按钮在服务端失效。更新失败也会明确通知，不伪装为已更新。重复点击或重启后的旧卡片不会重新授权或重做任务。

IM 是单用户工作区的远程入口，授权来源不是独立租户，文件、工具和运行环境仍由本机用户共享。当前工作区每次只接收一项 IM 任务；无论来源用户、群或平台是否相同，已有任务时新任务明确提示繁忙，未执行且不排队。已有 GUI／TUI／其他任务时，IM 也拒绝启动新任务；控制命令、审批和回答仍能处理。取消／超时后必须等执行线程实际退出才接收下一项。限制仅增加在 IM 入口，不改 GUI／TUI 的现有并发准入，不构成跨所有入口的工作区事务锁。单任务最长 30 分钟，同时受 Agent 迭代和资源预算约束。支持文字任务及企微提供的语音转写；图片／文件请先放入工作区再用文字说明，不支持的 IM 类型会明确提示。

卡片与 Harnex 弹窗展示同一项待处理请求，可以在任一端确认。钉钉回调按官方 Stream 协议返回 `data.response`，点击结果仅更新操作者的私有数据，公共状态更新不覆盖点击反馈。实际点击回调的 `spaceType=im` 表示原始 IM 会话，与投放卡片时的 `IM_GROUP/IM_ROBOT` 属于不同表示；接入按原请求的群／单聊精确核对会话 ID。完整场域标识（如 `dtv1.card//IM_GROUP.<群ID>`）也会先转换为原始 ID，仅统一类型和前缀表示，不改变业务 ID 大小写。回调未携带可选会话字段时，使用该卡片已记录的来源；操作者、机器人、卡片 ID 与当前授权仍需完全匹配，明确不符的会话字段仍拒绝。设置页“最近卡片操作”显示具体反馈；接收与处理结果写入脱敏日志，重启后也能排查，日志不记录原始回调、用户 ID 或凭据 URL。旧卡片、非发起人点击和已失效请求不能执行。

工作区服务停止或所在机器睡眠时不可接收任务；启用“离开后保持远端运行”的 SSH 项目不受本机退出影响。网络恢复后自动重连；进程重启不会重做已接受的任务，`/结果` 可查看中断说明。未确认发送结果时，不自动重复发送；设置页显示发送失败／结果未知，可在原会话发 `/结果` 取回结果。长回复按 UTF-8 字节分段，前段确认送达后才发后段。

**在 IM 中管理会话**：`/新建`（`/new`、`/reset`）开始新话题，原会话保留，模型和权限设置不变。`/会话`（`/sessions`）列出最近 10 个会话，`/会话 关键词` 查找；`/继续 编号`（`/resume 编号`）返回刚才列表中的会话。编号有效期为 10 分钟，重启后需重新查看列表。列表只包含你在这个机器人、聊天和工作区中执行过的任务，不显示其他用户／聊天的历史；删除的会话不可恢复。正在执行任务时不允许新建或切换会话，先等完成，或 `/取消` 后等它停止。`/结果` 返回当前所选会话的最近结果，切换会话不会重新执行旧任务。

**进度反馈**：接收任务后说明当前会话，持续超过约 45 秒时主动发送简洁进度，此后最多每 3 分钟提醒一次。等待审批／回答时以交互卡片为准，不重复发送“正在处理”；主动查看 `/状态` 会推迟下一次提醒。结束后尚未发出的进度会丢弃，避免结果后又收到旧进度。普通回复与 `/工作区` 同时标注运行主机和项目，方便区分本机、SSH 和服务器部署。

凭据、授权与收发状态保存到当前数据目录的 `automation/im/`，文件仅授权当前系统用户访问。配置列表仅返回密钥掩码；点击眼睛时，受保护且禁止缓存的接口才返回对应机器人的明文。隐藏、切换平台或工作区后清除显示缓存，查看本身不修改配置。收发记录保留七天并有容量上限；任务正文按会话档案保留。更换机器人 ID 清空旧授权；移除授权需保存，运行中须先取消任务再修改该渠道设置。

每个会话的模型、强度与控制模式保存在 `automation/im/journal.json`，与收发记录共用原子持久化；这些偏好不随七天收发记录清理而过期。编号列表只在当前进程保留，重启后请先重新发送 `/模型` 再用编号切换。

真实平台的发布、可见范围、群设置和额度需实际验收。Telegram 本地模拟覆盖协议及真实 Agent 审批，真实账号收发和手机端按钮仍需现场验收。飞书原有 HTTP 回调的加密桥接、固定群回传限制不适用于上述原生 IM 入口。

#### 通用 Webhook 桥接

外部 bridge 将各平台消息规范化后调用单一入口。

请求格式（**必须**带签名 + 时间戳 + nonce 三组头，缺一会 401）：

```http
POST /api/gateway/inbound
X-HARNEX-Timestamp: 1718000000000
X-HARNEX-Nonce:     b3c9d2f8e1a74c61bf3a5e2d9c0e8a14
X-HARNEX-Signature: <HMAC-SHA256(secret, ts + "." + nonce + "." + body)-hex>
Content-Type: application/json

{ "user": "u123", "channel": "feishu", "text": "今日产品会议总结 3 条" }
```

签名面**不是**单独的 body，而是 `timestamp + "." + nonce + "." + rawBody`（点号字面值分隔）：
- `X-HARNEX-Timestamp`：客户端**毫秒**时间戳；与服务器时间偏差 > **5 分钟**会被拒（防重放窗口）。
- `X-HARNEX-Nonce`：每次请求唯一的不透明字符串，建议用 UUID v4 或 32 字节随机 hex；服务端在 5 分钟窗口内做去重，重复 nonce 会被拒。
- `X-HARNEX-Signature`：上述拼接字符串的 HMAC-SHA256（hex 编码，小写）。

返回：`{ threadId, channel, reply, durationMs }`。同 `channel+user+threadKey` 会绑定到固定 thread 实现多轮记忆。

最小飞书 bridge 示例（Node/Cloud Function）：
```javascript
import crypto from 'crypto';
export default async (event) => {
  const body  = JSON.stringify({ user: event.sender.id, channel: 'feishu', text: event.text });
  const ts    = String(Date.now());
  const nonce = crypto.randomBytes(16).toString('hex');
  const sig   = crypto.createHmac('sha256', process.env.HARNEX_GATEWAY_SECRET)
                      .update(ts + '.' + nonce + '.' + body)
                      .digest('hex');
  const r = await fetch('https://harnex.example.com/api/gateway/inbound', {
    method: 'POST',
    headers: {
      'Content-Type':      'application/json',
      'X-HARNEX-Timestamp': ts,
      'X-HARNEX-Nonce':     nonce,
      'X-HARNEX-Signature': sig,
    },
    body,
  });
  const { reply } = await r.json();
  // 再把 reply 通过飞书机器人 webhook 回展即可
};
```

注意：`HARNEX_GATEWAY_SECRET` **未配置（空字符串）时所有 webhook 请求一律 401（fail-closed）**——生产 / 开发环境都必须显式配置一个非空密钥。

> **关于 Bearer**：`/api/gateway/**` 在默认配置里属于 `harnex.auth.public-paths`（见 [agent-config.yml](../backend/src/main/resources/agent-config.yml)），由各渠道自带的 HMAC / 签名 / nonce 校验作为安全边界，**不需要也不会校验 `Authorization: Bearer`**，即使 `HARNEX_AUTH_ENABLED=true` 也一样。除非运维显式把 `/api/gateway` 从 `public-paths` 移除，bridge 端无需加 Bearer 头。

**Q7. MoA 多花多少钱？**
A：N 个 reference 模型 + 1 个 aggregator，顶多 ×(N+1) 于单次调用。仅适合“隔靅难题”，不要袋进聊天循环（否则成本随轮数线性爆炸）。默认 `enabled: false`，需手动在 `agent-config.yml` 里打开并配齐模型。

**Q8. 如何完全离线运行？**
A：为本地推理服务配置 `openai-compatible-chat-safe` Provider、实际地址和模型 ID；凭据按本地服务要求填写。摘要、图片、MCP、搜索和工具也需使用离线资源，移除 `web_fetch` 一项不能保证全部链路离线。命令执行使用 `harnex.execution.environment=host|docker`；原生隔离、网络策略和平台限制见[部署方案 §6.7](04_部署方案.md#execution-environments)，没有旧 `local`／命令级 `ssh` sandbox 选项。

**Q9. 同一会话能混用多个模型吗？**
A：可以。不同 thread 互相独立，每条聊天请求都可以指定不同 `model`。常见组合：
- 主任务使用当前仍受厂商支持、且完成工具闭环验证的强推理模型
- 摘要器 `harnex.summarizer.provider` 指向当前廉价模型，避免与主路共享配额
- 子 Agent 的模型选择受冻结目录、父任务权限与家族预算限制；可通过明确选模、收紧范围／轮次或独立摘要模型控制成本
- MoA 参考层用多家便宜模型，aggregator 用一家强模型

**Q10. tool_calls 不支持的模型怎么办？**
A：必须使用模型和端点都明确支持的 function/tool calling。静态型号列表很快会过时，而且兼容网关可能丢弃或改写 `tools`；请用最小工具闭环做验收。不支持 tools 的模型仍可纯聊天，但不能完成 Harnex 的 Agent 工具循环。

**Q11. 怎么上传图片或文档？**

在输入框使用附件按钮或拖入文件；服务端导入为受当前空间保护的资产，消息保存 artifactId。再次使用时读取真实内容并检查当前型号的图片／文件能力。普通会话不因附件而获得项目文件工具；Agent 按既有文件与 OCR 能力处理可提取文字，无法视觉理解时不会假装已经看过图片。

```http
POST /api/v1/artifacts/imports       # multipart，field=file，可带 clientRequestId
GET  /api/v1/artifacts/{id}          # 元数据
GET  /api/v1/artifacts/{id}/content  # 预览／下载
POST /api/v1/artifacts/{id}/exports # 下载导出信息
```

大小、格式与当前模态能力由后端校验；详见 §3.4 和生成的 OpenAPI。
