# Harnex 部署方案

[English installation guide](en/installation.md)

更新于 2026-11-15。安装、运行环境、存储与发布流程统一维护于本文。

适用版本：1.0.0

## 0. 下载与首次运行

### 0.1 下载和校验

从 [GitHub Releases](https://github.com/debug2048/Harnex/releases/latest) 选择与系统和 CPU 匹配的桌面安装包，或完整 `_offline` 包。发布页保留 5 个主要安装包、5 个完整离线包和一份校验清单。Windows x64 对应 `win32-x64`；macOS M 系列 / Intel 对应 `darwin-arm64` / `darwin-x64`；Linux 对应 `linux-x64` / `linux-arm64`。版本发布页列出实际附件；自动生成的 Source code 归档是源码，不是安装包。

桌面包和完整离线包内置 Java 与 ripgrep。单独的原生 CLI npm 包只含 CLI，不等同于 Runtime Bundle。`npm install` 与 Marketplace 安装仅适用于已在对应渠道发布的版本；首次体验优先使用 Release 附件。

同时下载 `SHA256SUMS`，核对所选文件对应的一行。Windows PowerShell 使用 `Get-FileHash -Algorithm SHA256 .\下载的文件名`；Linux 使用 `sha256sum 文件名`；macOS 使用 `shasum -a 256 文件名`。下载全部附件后才适合用 `sha256sum -c SHA256SUMS` 检查整份清单。校验失败时重新下载，不运行损坏的文件。

### 0.2 安装与系统提示

- Windows：运行 `.exe` 安装器，需要 WebView2。v1.0.0 未做 Authenticode 签名，可能出现发布者未知或 SmartScreen 提示；仅在核实官方来源和哈希后按系统提示处理，受组织策略限制时联系管理员。
- macOS：打开匹配架构的 DMG，将 Harnex 拖入 Applications 后启动。v1.0.0 为 ad-hoc 签名且未公证；系统可能阻止首次打开。核实来源后按“系统设置 → 隐私与安全性”的单应用提示处理，无需全局关闭 Gatekeeper。
- Linux：可下载独立 AppImage；需要 DEB/RPM 时，从完整离线包的 `desktop/` 目录取得，再用发行版包管理器安装及补齐依赖；桌面需要 WebKitGTK 4.1 等系统库。AppImage 也需要兼容的系统环境。当前基线为 Ubuntu 22.04，不支持 Alpine/musl 原生包。
- VS Code：解压对应平台离线包，在“Extensions: Install from VSIX”中先安装 Runtime、再安装 UI，随后重新加载窗口；也可以运行包内 `install-vscode.ps1` / `install-vscode.sh`。只安装 UI 时，需要已有的同项目 Runtime。
- CLI/TUI：保留 `portable/runtime/` 完整目录，运行其中 `bin/harnex`（Windows 为 `bin/harnex.exe`），不要只复制一个可执行文件，也不要把安装目录作为项目目录。

### 0.3 配置模型并完成第一个任务

1. 打开应用，在“设置 → 模型”中配置服务协议、地址、API Key（服务需要时）和准确的模型 ID，然后选择该模型。离线包不附带模型或 API 额度；本地模型服务也需先启动。
macOS 桌面的本机运行环境首次填写或修改 API Key 后，凭据存入钥匙串，当前 Runtime 需要重新打开才能读取新值。若保存后会话仍显示原模型列表，请在设置页点击“重连生效”；通常不必退出整个应用。只修改模型或服务地址、且没有待重连项时，模型列表会随保存刷新。代理等连接配置的变更在其他平台也可能需要重连。

2. 先用个人会话发送“请用一句话介绍你自己”。若失败，依次检查服务地址、协议、模型 ID、凭据及网络，不要先调整高级 Agent 参数。
3. 打开自己的项目，尝试“只阅读项目，说明目录结构，不修改文件”。确认工作目录和执行环境，再批准后续需要写文件或运行命令的任务。
4. 退出并重开应用，确认历史仍在。升级前按设置中的诊断路径备份用户目录及项目 `.harnex/data`，不要删除数据目录来替代重装。

v1.0.0 已记录 Runtime 生命周期、数据保留、Unix PTY 和扩展契约的自动检查，以及 Windows 维护者安装确认。macOS/Linux 桌面交互安装与 VS Code Extension Host 端到端验收仍未完成；这些限制见 [Release 说明](https://github.com/debug2048/Harnex/releases/tag/v1.0.0)。遇到问题请使用 [Issue 模板](https://github.com/debug2048/Harnex/issues/new/choose)，只附脱敏日志；漏洞按[安全报告指引](../SECURITY.md)处理。

## 1. 部署形态

提供七种部署形态：

| 形态 | 场景 | 组件 |
|------|------|------|
| **npm 全局安装** | 个人用户 / Web 工作台与终端交互 | `npm i -g harnex` → `harnex` / `harnex serve` / `harnex stop` |
| **Native CLI / Desktop** | 无 Node/JDK 的 Windows/macOS/Linux 用户 | target-specific Runtime Bundle；Windows NSIS、macOS DMG 等；签名状态按发行流程区分（详见 §3.5／§5.4／§5.6） |
| **VS Code** | IDE 编码工作流 | 轻量 UI VSIX + target-specific Runtime companion VSIX（完全离线，详见 §3.6） |
| **离线便携包** | 隔离网/无安装权限的 Windows/macOS 环境 | portable verified Runtime Bundle + 双 VSIX + 全文件 SHA-256（详见 §3.6） |
| 本地开发 | 开发/调试 | `mvn spring-boot:run` + `npm run dev` |
| 单机 Docker | 个人/小团队（含 Web UI） | `docker compose up` |
| 生产 K8s | 多租户/HA | Helm Chart（规划中） |

> 推荐路径：**只想用 TUI/Web UI** → npm；**完全图形化、零命令行** → 桌面安装包（§3.5）；**二次开发** → 本地源码；**固定服务部署** → Docker（多租户隔离尚未实现）。

### 1.1 多端运行域与数据归属

各形态共用 Java Runtime 与 Local API。Web Supervisor 和桌面宿主提供共享 PERSONAL 与一个活动 PROJECT 槽位，可以同时存在两个 JVM；不同宿主也可以各自拥有项目实例。同一执行 dataDir 只允许一个写 Runtime。桌面与 managed VS Code 在项目数据根下分别使用 `runtime-stores/tauri` 和 `runtime-stores/vscode-<storage-id>`，通过文件事务共享档案与资产；同一活动或暂停会话另有跨进程占用锁。项目切换需按宿主策略关闭或断开旧项目，个人会话不随项目切换。

CLI／TUI 没有显式 manifest 时可启动自己的项目域或启动／借用共享个人域；有 manifest 时精确连接该目标，失效则报错，不另起 JVM。借用者退出不停止 Owner。VS Code 在 managed 模式由窗口管理独立 PROJECT Runtime，也可通过受信 manifest 连接已有项目服务，保持原宿主生命周期；仅提供 Agent 功能，详见[VS Code 使用说明](../extension/README.md)。

用户配置默认在 `~/.harnex`，项目数据默认 `<project>/.harnex/data`，个人档案固定 `<userDataDir>/personal`；域清单、令牌与宿主日志位于 `<userDataDir>/runtime-domains/<id>`。设置 → 诊断显示当前运行环境的实际存储位置。

### 1.2 默认端口与覆盖方式

用户直接访问的 Web／`serve` 入口统一使用 `18081`，内部 Runtime 按宿主分配：

| 入口 | 默认端口 | 覆盖方式 |
| --- | --- | --- |
| Docker Web | `18081` | `.env` 的 `HARNEX_FRONTEND_PORT` |
| npm `harnex`／`harnex launch --webui`／`harnex supervisor` | `18081` | `--port=19081` 或 `HARNEX_SUPERVISOR_PORT` |
| npm／Portable `harnex serve` | `18081` | `--server.port=19081`、`HARNEX_PORT`、`SERVER_PORT`，按此优先级 |
| 源码 `npm run dev` 的 Vite 页面 | `18081` | `npm run dev -- --frontend-port 19081`；单独启动 Vite 用 `npm --prefix frontend run dev -- --port 19081` |
| 源码 `npm run dev:supervisor` | `18081` | `npm run dev:supervisor -- --supervisor-port 19081` |
| 开发后端／直接启动 JAR 的 API | `8088` | `--server.port`、`SERVER_PORT` 或 `application.yml` |
| 桌面、VS Code、独立 CLI/TUI 的内部 Runtime | 自动分配 | 由各宿主和 Domain manifest 管理，不占用固定 Web 端口 |

`harnex serve` 会把解析后的公开端口显式传给 JVM，不再从源码树中的 `application.yml` 推断默认端口；该文件仍管理直接启动后端的 API 默认值。Docker 后端容器内部仍使用 `8088`，前端容器内部使用 `80`。

后端默认跨域白名单对应 `localhost:18081` 与 `127.0.0.1:18081`。Nginx／Vite 代理保留浏览器的 Host 和端口，使自定义端口或 SSH 隧道中的页面请求仍按同源处理；不通过放宽跨域白名单来适配任意端口。

需要在同一机器并行运行多个 Web 入口时，显式指定不同端口；Vite 遇到端口占用会报错，不自动跳到其他端口。新默认值在重新启动后生效，已安装的旧版原生／npm 发行包需要升级或重新构建。已有显式端口参数和环境变量继续优先使用。

## 2. 环境要求

| 项 | 最低 | 推荐 |
|----|------|------|
| JDK | 17 | 21 |
| Node.js | 18 | 20 |
| Maven | 3.8 | 3.9 |
| 内存 | 2 GB | 8 GB |
| 磁盘 | 5 GB | 50 GB |
| 操作系统 | Linux / macOS / Windows（原生支持） | Ubuntu 22.04 LTS |

Node 18 是 npm 启动器的最低要求；源码开发与发行构建使用 Node 20+，原生构建还需下文所列 Rust 和平台工具链。Docker 部署的编译依赖由构建容器提供，宿主机只需 Git、Docker 和 Compose。Windows/macOS native desktop 与 VS Code Runtime companion 自带裁剪
JRE，不要求目标机安装 JDK 或 Node；macOS 正式桌面最低版本为 13.0，并分别发布 Apple Silicon/Intel 包。

### 2.1 支持边界与平台验收

发行目标为 `win32-x64`、`darwin-arm64`、`darwin-x64`、`linux-x64`、`linux-arm64`。
Windows 桌面面向 Windows 10 1903+/11 x64，macOS 桌面要求 macOS 13+。
Linux 原生包需要兼容的 glibc 和 WebKitGTK 4.1；不承诺适用于 Alpine/musl、32 位系统或旧版 glibc。
SSH 服务端目前支持 Linux x64/ARM64。

便携包、桌面包和 VS Code Runtime companion 自带 JRE、ripgrep 与 native CLI。
npm/源码运行需要系统 Java 17+ 和 ripgrep；完整源码构建需要 Node 20+、Maven、Rust 1.88+ 和对应平台的桌面依赖。
Windows 内置 Java 17 的安装目录应避免 emoji 等补充平面字符。
项目自己的 Git、Python、Node、编译器和 MCP 服务仍由项目环境提供。

公仓不包含独立测试用例和验收脚本；内嵌在业务源码中的测试可保留。
构建后可运行 `node scripts/build/runtime-bundle.mjs --verify <portable/runtime> --target <目标>` 校验 Runtime 完整性，行为验收须另外执行并留证。
平台构建、桌面显示、签名、公证和实际启动的验证结果应随发行说明列出。
只在一个操作系统完成构建不代表其他平台已经验收。

macOS Keychain 引用不会自动传给独立 VS Code/CLI Runtime；需显式凭据或连接桌面已经启动的 Runtime。
SQL 历史后端、Redis 缓存和对象存储后端尚未交付，基础部署不需要安装这些服务。

## 3. 终端用户：npm 全局安装

> 适用对象：只想"用"Harnex 的人（不改源码）。前提是包名 `harnex` 已被维护者发布到 npm registry —— 维护者首次发版请看 §5。

```bash
# 1. 安装（需 Node ≥ 18 + JDK ≥ 17）
npm install -g harnex

# 2. 配置任一兼容 OpenAI 协议的 Key
export OPENAI_API_KEY=sk-...
export OPENAI_BASE_URL=https://api.openai.com/v1

# 3. 三种用法
harnex               # 交互式启动菜单：Web UI / Terminal
harnex tui           # 直接进入原生 TUI
harnex cli -p "总结 README.md"   # 一句话模式（脚本/CI 友好）
harnex serve          # 后台 server：Web UI + REST API on :18081
harnex stop           # 跨 shell 停掉 standalone-web Runtime Domain
harnex status         # 查看是否在跑
```

**进程管理要点**：
- `harnex serve` 在 `~/.harnex/runtime-domains/standalone-web/owner.json` 写入 Owner lease，并在 READY 后发布 `domain.json`
- `harnex stop` 在任意终端可读 PID 强停 —— Windows 用 `taskkill /T /F`，Unix 先 `SIGTERM` 5 秒后升 `SIGKILL`
- 父 shell 收到 `SIGINT/SIGTERM/SIGHUP` 时 Node 启动器会下发给 JVM 子进程
- TUI 中按一次 **Ctrl-C** 优雅取消当前 agent 回合（不杀 JVM），空闲时清空输入，Composer 为空时 Ctrl-D 退出

**命令执行环境**：默认使用 Runtime 所在主机工具链；按需配置原生隔离或 Docker，SSH 通过远端项目连接。配置和平台限制见 [§6.7](#execution-environments)。

**自定义 jar 路径**（`HARNEX_JAR`）：
- npm launcher 默认在 `backend/target/` 中查找 `harnex-*.jar`；当**无本地构建**或希望指向其它位置（如统一发布目录）时，设置 `HARNEX_JAR=/abs/path/to/harnex-x.y.z.jar` 即可——launcher 优先读取该变量并校验文件存在性，**不再要求 `backend/target/` 下也必须有 jar**。

**升级 / 卸载**：

```bash
# 升级到最新
harnex stop                                    # 先停掉 server（如果在跑）
npm update -g harnex                   # 或: npm i -g harnex@latest
harnex version                                 # 验证

# 完全卸载
harnex stop                                    # 先停 server
npm uninstall -g harnex                # 移除全局命令 + node_modules

# 用户数据默认放这里，按需手动删除（卸载不会自动删，避免误清）
#   Linux/macOS: ~/.harnex/        （用户配置、个人会话与运行域；项目另有 dataDir）
#   Windows:    %USERPROFILE%\.harnex\
rm -rf ~/.harnex                       # ⚠️ 会删掉所有会话历史 / 上传文件 / 索引
```

> **环境变量**：如果你之前在 `~/.bashrc` / `~/.zshrc` / Windows 系统环境变量里设过 `OPENAI_API_KEY` / `HARNEX_*`，卸载后想完全清理需自己删。

## 3.5 原生桌面安装包（Windows / macOS，零依赖）

> 适用对象：**完全不想碰命令行、也不想装 Node/JDK** 的 Windows/macOS 最终用户。底层是
> Tauri 轻量原生宿主，复用同一 Vue SPA 与 Runtime API。

### 3.5.1 用户侧

1. Windows 下载 `Harnex_x.y.z_x64-setup.exe`；Mac 按 CPU 下载 `Harnex_x.y.z_aarch64.dmg` 或 x64 DMG；
2. Windows 按 NSIS 向导安装；Mac 打开对应架构 DMG 并将 `Harnex.app` 拖入 Applications。普通本地构建使用 ad-hoc 签名；只有完成正式签名流程并通过验收的制品才声明 Developer ID 签名与公证，下载时以该制品的发行说明为准；
3. 从开始菜单 / 桌面启动 “Harnex”。有历史项目时自动打开最近使用项目；首次无历史项目时直接进入
   空工作台，点击左上 Workspace 后才弹出系统原生目录选择；
4. 关闭窗口只隐藏到系统托盘，唯一 Workspace Runtime 继续运行；托盘“退出 Harnex”才会先 drain
   再结束整个 Runtime 进程组。SSH 项目若显式选择“离开后保持远端运行”，退出时只断开隧道，服务留在服务器；该选项不设置服务器开机自启。Windows/Linux 可用默认全局快捷键；macOS 默认不抢占 Finder
   `⇧⌘H`，可通过 `HARNEX_GLOBAL_SHORTCUT` 自行配置。打开/切换 Workspace 始终使用应用内
   左上角同一个入口，托盘不提供第二套项目菜单。

无需预装 JDK / Node：安装包使用已校验 Runtime Bundle（jlink JRE + jar + native CLI）；Windows
复用 WebView2，macOS 复用 WKWebView。Windows 安装器可管理 machine PATH；Mac 用户可执行 App 内
CLI 的 `harnex path install` 创建 `~/.local/bin/harnex`，不会修改系统目录。
该命令及 `path uninstall` 只管理目标确实指向当前 executable 的 symlink；同名普通文件、broken link 或
指向其它程序的链接会被拒绝，绝不覆盖/删除。

安装资源根中的 `resources/ui/` 是独立的桌面 SPA，不属于 `runtime-bundle.json` 的 JVM/native 文件集；
桌面校验器只对这个顶层 UI 目录作边界排除，仍递归拒绝 symlink，任何其他未声明文件继续 fail closed。
NSIS 的 PATH 询问在 POSTINSTALL 阶段按 `$LANGUAGE` 选择显式中英文文本。macOS Provider Key
默认写入 Keychain，YAML 只保存 `${HARNEX_KEYCHAIN_PROVIDER_*:}` 引用；旧明文配置继续兼容但强制 0600。
`MUI_LANGUAGE` 声明时自定义 `LangString` 解析为空。

用户级配置、Skill 状态和共享 Recent registry 默认位于 `%USERPROFILE%\.harnex\`；Tauri 的进程状态与日志位于其独立 Runtime Domain 子目录。每个 Workspace
的会话、上传、索引和 Snapshot 位于其 `dataDir`（默认 `<workspace>/.harnex/data`）。若存在
`~/.harnex/agent-config.yml`，会被自动追加进 `SPRING_CONFIG_ADDITIONAL_LOCATION`。

### 3.5.2 构建侧（开发者出包）

公共工具链：Rust/cargo、Tauri CLI v2、Maven 3.9+、JDK 17+（含 jlink/jdeps）。Mac 还需要
Xcode Command Line Tools；正式发行需要 Developer ID Application 证书和 App Store Connect API Key。

```bash
npm run build:desktop:check    # 体检工具链，不构建
npm run build:desktop          # release 安装包 → src-tauri/target/release/bundle/
npm run build:desktop:updater  # minisign updater artifacts
npm run build:desktop:macos:release # Developer ID + notarize/staple + updater
npm run build:desktop:debug    # debug 构建（更快、体积大）
node scripts/build/build.mjs --target desktop   # 统一构建入口，等价于 build:desktop
```

macOS 严格执行：CLI/JRE 内全部 Mach-O 先 codesign → 生成 Runtime 哈希 → 打包/签名外层 App →
notarize/staple → `codesign --deep --strict`、`spctl` 与真实启动验收。ARM/Intel 必须使用对应原生 runner，
不在另一架构上猜测 jlink 镜像，也不把两套 JRE 合成 Universal App。

Tauri v2 updater 已启用：启动时后台检查，托盘/菜单栏可手动检查；下载、安装前必须验证 minisign，
没有 endpoint/pubkey 时功能关闭，不提供 unsigned fallback。构建必须提供：

- `HARNEX_UPDATE_ENDPOINT`：HTTPS updater manifest URL；
- `HARNEX_UPDATE_PUBKEY`：内嵌到 release 的 minisign 公钥；
- `TAURI_SIGNING_PRIVATE_KEY`（及按需 `TAURI_SIGNING_PRIVATE_KEY_PASSWORD`）：只在构建环境使用的私钥。

### 3.5.3 环境变量（与 `bin/harnex.mjs` 对齐）

| 变量 | 作用 | 默认 |
|------|------|------|
| `HARNEX_PORT` / `SERVER_PORT` | Tauri Runtime 显式监听端口 | 未设置时自动选择空闲 loopback 端口 |
| `HARNEX_DATA_DIR` | 当前 workspace Runtime 数据目录 | `<workspace>/.harnex/data` |
| `HARNEX_USER_DATA_DIR` | 共享用户配置根目录；各宿主的 Boot Token/运行状态须按 Runtime Domain 隔离 | `~/.harnex` |
| `HARNEX_RUNTIME_DOMAIN_ID` | Owner 显式指定的运行域标识 | 由宿主生成 |
| `HARNEX_RUNTIME_DOMAIN_DIR` | 当前 Owner 的 token/owner/port/log/manifest 目录 | `<userDataDir>/runtime-domains/<runtimeDomainId>` |
| `HARNEX_DOMAIN_MANIFEST` | Client 精确连接受信 Runtime 的 manifest 路径；不等价于任意 base URL | 无；由 VS Code 等受信宿主注入 |
| `HARNEX_JAR` | 覆盖 jar 路径（开发用，无内置资源时） | 内置 `resources/harnex.jar` |
| `HARNEX_UPDATE_ENDPOINT` | HTTPS 签名更新 manifest | 无（不配置则关闭更新） |
| `HARNEX_UPDATE_PUBKEY` | updater 签名验证公钥 | 无 |

更多细节见 [src-tauri/README.md](../src-tauri/README.md)。

## 3.6 VS Code、native CLI 与完全离线包

VS Code 正式分发采用双 VSIX：

- `harnex-vscode-<target>-<version>.vsix`：平台无关的轻量 UI/Editor Bridge；
- `harnex-runtime-<target>-<version>.vsix`：目标平台 Runtime companion，包含完整 Runtime Bundle。

生成正确脚本和路径，Darwin 不依赖 PowerShell。

offline kit 顶层 `SHA256SUMS` 覆盖双 VSIX、portable 与可选 NSIS/DMG；各 Runtime Bundle 还独立包含
`runtime-bundle.json + SHA256SUMS`。Darwin Bundle 额外记录 `codeSigning.signedBeforeHash=true`。

### 4.3 摘要压缩模型配置（重要）

Harnex 默认开启**历史摘要压缩**（防止 token 撑爆上下文窗口）。它使用一个**独立的廉价侧路模型** —— 不一定要和主模型同家。建议显式配置：

```bash
# 方案 A：留空，优先复用当前任务实际 Provider/Model（默认）
export HARNEX_SUMMARIZER_PROVIDER=
export HARNEX_SUMMARIZER_MODEL=              # 与 provider 一起留空时沿用任务实际模型

# 方案 B：为摘要加一个独立 Provider（推荐，不与主路或 Chat fallback 共享 Key/额度）
#   需在 agent-config.yml 的 harnex.providers Map 里先加一条：
#     cheap:
#       profile: deepseek-v4
#       base-url: https://api.deepseek.com/v1
#       api-key: ${DEEPSEEK_API_KEY:}
#       default-model: deepseek-v4-flash
#   然后：
export HARNEX_SUMMARIZER_PROVIDER=cheap
export HARNEX_SUMMARIZER_MODEL=deepseek-v4-flash

# 方案 C：关闭 LLM 摘要（改走确定性结构化 digest，无模型调用）
export HARNEX_SUMMARIZER_ENABLED=false
```

触发门槛（`agent-config.yml → harnex.summarizer`）：

| 键 | 默认 | 含义 |
|---|---|---|
| `context-window` | 128000 | 当前执行模型的上下文窗口；部署不同模型时必须按其真实上限调整 |
| `output-reserve-tokens` / `safety-reserve-tokens` | 16000 / 0 | 从上下文窗口扣除的输出与额外安全余量 |
| `soft-threshold-percent` / `hard-threshold-percent` | 75 / 90 | 基于可用输入窗口的软门与硬门；工具批后检查软门，每次调 LLM 前同步检查硬门 |
| `target-percent` | 40 | 一次压缩期望回落到的水位 |
| `min-new-tokens` / `min-new-context-percent` | 16000 / 15 | 两次压缩之间至少新增的上下文；实现取两者中较小值，兼顾不同窗口模型 |
| `minimum-reduction-percent` / `max-ineffective-compressions` | 20 / 3 | 有效压缩判定与连续无效压缩上限；达到上限后进入一次无工具收口轮 |
| `keep-tail` | 0 | 可选的尾部原文条数上限；`0` 表示仅按 Token 预算保留 |
| `keep-tail-chars` | 0 | 可选的尾部原文字符上限；`0` 不额外限字符，Token 目标预算仍生效 |
| `summary-max-chars` | 24000 | 保存的摘要正文字符上限，不含受保护原文与近期历史 |
| `max-output-tokens` | 16384 | 摘要生成最高额度；实际按模型剩余窗口及已声明的最大输出缩小，正文、事实候选及计入的推理共享预算 |
| `max-concurrent` | 2 | 独立 Run 的摘要并发上限；超出时快速使用确定性摘要，不排队 |
| `timeout-ms` | 180000 | 本次压缩全部模型尝试的共享时限；在剩余额度内尝试后备目标，耗尽后本地处理，主任务继续 |
| `attempt-timeout-ms` | `90000` | 单次模型调用上限；同时受整次摘要及任务剩余时间限制，已有显式总时限不变 |
| `prefix-reuse` | `false` | Agent 软水位下尝试复用兼容主请求前缀；容量不足、换模型或硬上限/溢出恢复时使用原摘要路径 |

> ⚠️ **关键点 1：非空的 `HARNEX_SUMMARIZER_PROVIDER` 必须是 `harnex.providers` 中某个 Map key** — 它是引用不是重复配置；留空优先复用当前任务的实际 Provider/Model，再尝试可用 fallback。指错名会在启动校验时报错。
> ⚠️ **关键点 2：显式指定摘要 Provider、但不填模型时使用该 Provider 的 `default-model`**；两者都留空时优先使用任务实际模型。需要独立成本与额度时，显式配置摘要 Provider/Model。

### 4.5 多模态：Vision 模型 & OCR 兜底

WebUI 支持图片/文档上传（`POST /api/v1/artifacts/imports`；上传上限与原生内联上限分别由 Web multipart 和附件配置控制）。处理路径有两条：

**A. Vision 多模态（首选，零额外依赖）**
- `HARNEX_VISION_ENABLED=true` 只是全局门控；还必须让对应 Provider 的**精确模型 ID**从同 ID Profile
  条目继承，或在 Provider `models` 中显式声明 `input-modalities` 包含 `image`。
- 四个适配器分别生成 Chat Completions `image_url`、Responses `input_image`、Anthropic `image` block、Gemini Interactions 原生 content；普通文件/PDF/音频/视频也只在相应协议和精确模型声明支持时发送。
- 不按 `gpt-*`、`qwen-vl-*` 等名称猜能力。兼容网关是否透传附件由具体端点决定，模型更名或 alias 也必须单独声明并验收。
- 能力未知、未声明、MIME 不支持或超限时，Harnex 不发送未知 content part，而是向模型追加可见的 `file_read`/OCR 降级提示。
- 详细参数表见 [docs/06 §3.4.1](06_用户手册.md)

**B. OCR 兜底（用纯文本模型也能"看"图）**

`HARNEX_OCR_FALLBACK=true` 时，上传图片会用 Tika+Tesseract 生成同名 `.extracted.txt` sidecar；后续 `file_read` 工具可读取。**无 Tesseract 时不报错、不阻塞上传**，只是 sidecar 留空。

> ⚠️ **是否要默认安装 Tesseract？取决于部署方式**：
> - **Docker** — `backend/Dockerfile` 已默认装 `tesseract-ocr` + 英文/简体中文语言包（约增 30 MB），开箱即用
> - **npm 全局安装** — `npm i -g harnex` 的 `postinstall` **只检测不安装**（避免要求 root / 拖网络），缺失会高亮提示
> - **本地源码运行** — 需用户自行安装

**各 OS 安装命令**：

| OS | 命令 |
|---|---|
| Ubuntu / Debian | `sudo apt install -y tesseract-ocr tesseract-ocr-eng tesseract-ocr-chi-sim` |
| CentOS / RHEL | `sudo yum install -y tesseract tesseract-langpack-eng tesseract-langpack-chi_sim` |
| macOS (Homebrew) | `brew install tesseract tesseract-lang` |
| Windows (Chocolatey) | `choco install tesseract`（中文包另需按发行版说明安装 `chi_sim.traineddata` 到 `tessdata/`） |
| Alpine | `apk add tesseract-ocr tesseract-ocr-data-eng tesseract-ocr-data-chi_sim` |

**完全不需要 OCR**：`export HARNEX_OCR_FALLBACK=false` 即可关闭，节省启动期探测和上传期 OCR 调用（适合纯 vision 模型场景）。

**OCR 语言**：`HARNEX_OCR_LANG=eng+chi_sim`（默认）。需要日韩等再装对应 `tessdata-{jpn,kor,...}` 包后追加，例如 `eng+chi_sim+jpn+kor`。

### 4.6 Provider 协议选择与国产模型上线检查

#### 4.6.1 Profile 配置模型

用户层只配置 `providers.<id>`；维护层的 `harnex.provider-profiles` 是 adapter/wire 模板，厂商专用
模板还可附带安全的官方 endpoint/default model 与内部能力/建议目录。Profile 目录不会直接发布给
该端点：Provider 省略 `models` 时只暴露默认模型，显式列表只暴露平台实际开放的有限集合并自动补默认；
同 ID 条目继承 Profile 元数据/能力。Provider 非空字段覆盖模板默认值；
rule/model 也使用同一个 `profile` 命名空间。`type` 是唯一协议选择，内部 API 类型自动推导：

```yaml
harnex:
  provider-profiles:
    vendor-chat:
      type: openai-compatible
      instruction-role: system
      max-tokens-field: max_tokens
      default-max-tokens: 16384
      streaming: true
      stream-usage: true
      function-tools: true
      sampling-policy: when_thinking_off
      reasoning-efforts: []
      function-tool-reasoning-effort: null # 省略/null=继承；effort=约束；unconstrained=子 overlay 清除
      reasoning-replay: never
      reasoning-history: none
      prompt-cache-mode: none
      request-options: {}
  providers:
    vendor:
      profile: vendor-chat
      base-url: https://vendor.example/v1
      api-key: ${VENDOR_KEY:}
      default-model: exact-model-id
      features:
        prompt-cache: auto
        web-search: auto
        reasoning-history: auto
      models:
        - id: exact-model-id
          # capability-model: canonical-model-id # relay 改名时复用当前 profile 的规则
          input-modalities: [text]
```

解析按“协议基线 → provider profile → 首条有序 full-match rule（如有）→ 精确 model overlay（如有）”逐层合成。rule 与 exact 同时命中时，exact 只覆盖自身显式字段；只有 exact 条目最后应用 `input-modalities`。部署检查必须确认：

- Java 不按模型名、前缀或厂商猜能力。unknown/自由输入 alias 在 rule 和 exact 都未命中时继承 provider-wide profile，但不获得 model-level overlay 或附件模态。显式 alias 可用 `capability-model` 选择当前 profile 的 canonical rule；实际 model ID 不变，附件仍需单独声明。
- `sampling-policy`、`reasoning-replay`、`reasoning-history`、`prompt-cache-mode`、thinking 字段和值来自厂商当前契约。`function-tools` 与 `reasoning-efforts` 分别声明 standalone 能力；若端点另有组合限制，用 `function-tool-reasoning-effort` 声明。该字段省略/null 表示继承，子 model/rule 用 `unconstrained` 显式清除继承约束。`openai-chat` 的 GPT-5.6 规则都保留 `none..max` 六档；当前 Chat Completions 的实际 400 只明确覆盖 Sol，且[官方说明 `gpt-5.6` alias 路由到 Sol](https://developers.openai.com/api/docs/guides/latest-model)，所以只有 Sol/alias 首条规则要求 function tools 的 effective effort=`none`（省略自动补齐、显式非 `none` 本地失败并提示 Responses）。Terra/Luna 及 `openai-responses` 的 GPT-5.6 规则不继承该约束；这只是避免无依据扩大限制，不等于真实端点组合认证。证据是 [Developer Community 中记录的 Sol 服务器 400](https://community.openai.com/t/gpt-5-6-chat-completion-reasoning-effort-bug-behavior-change/1386454)，并非官方文档新增的通用规则；官方文档仍分别列出两项能力，并[建议 reasoning + tools 优先使用 Responses](https://developers.openai.com/api/docs/guides/reasoning)。Harnex 不发送 `tool_choice`，能力配置中不提供 `tool-choice-policy`。
- Profile cache 字段描述 endpoint/model **能力**；Provider 的 `features.prompt-cache` 描述用户**意图**。两者必须同时满足才发送缓存字段。
- 原生 web search 同样双门控并支持安全降级：`features.web-search:auto|on` 表示原生优先；只有 resolved capability 含 `native-web-search:true` 和非空工具类型时，Responses/Anthropic/Gemini 才转换为服务端工具。能力未命中时不发送无效原生字段，并保留已配置且可用的本地 `web_search` function；`off` 只禁用原生偏好，Chat 始终使用本地工具。
- `request-options` 只能放受信任的静态扩展，不能覆盖 model/messages/input/tools/stream 等协议保留键。
- Reasoning 静态回放配置为 `reasoning-replay: never|tool_calls|all|native_items`；Chat 型号另有可选/强制历史契约时，用 `reasoning-history` 与可选厂商字段将用户 intent 和完整回放绑定。
- 严格校验客户端身份的中转站才配置 Provider 级 `client-emulation: codex|claude-code`；
  `client-version` 可省略。Codex 仅用于 OpenAI Chat/Responses，Claude Code 仅用于 Anthropic；
  协议不匹配在启动阶段失败。普通兼容站不启用。

> 最高优先级 YAML 一旦声明 `harnex.providers`，就完整接管 concrete Provider Map；低优先级端点、
> 同名字段与模型列表都不会渗入。命令行/环境变量仍可在拥有者之上按字段覆盖。删除、改名或禁用时检查
> `router.default-provider`、summarizer、MoA/delegate 引用。

#### 4.6.2 上线矩阵

| 场景 | `type` | 上线前必须验证 |
| --- | --- | --- |
| OpenAI Responses | `openai-responses` | semantic SSE、完整 output item 工具回放、incomplete/refusal、附件、缓存 usage |
| Anthropic 原生 Messages | `anthropic` | named SSE、`tool_use`、thinking/signature 回放、cache_control、图片/PDF |
| Google Gemini Interactions | `gemini` | step SSE、完整 thought/signature/内置工具 step 回放、function call/result、Google Search、图片/音频/视频/PDF |
| 国产模型/中转/本地 OpenAI 兼容端点 | `openai-compatible` | 标准 SSE、tool_calls 闭环、thinking 回放规则、特殊 finish reason、附件 shape、usage/cache 字段 |

“OpenAI-compatible”只表示可以共享 Chat Completions 基线，不表示厂商扩展完全相同。上线国产模型时：

1. 从厂商当前模型目录复制**精确 ID**，不要长期使用手册里的静态别名。DeepSeek 的 `deepseek-chat` / `deepseek-reasoner` 按[官方 V4 公告](https://api-docs.deepseek.com/news/news260424/)计划于 2026-07-24 15:59 UTC 退役，当前应迁移到 `deepseek-v4-flash` / `deepseek-v4-pro`。Kimi K2.7/K3、Grok 4.5 和 Gemini 当前型号可直接选用内置 `moonshot-kimi-chat` / `xai-responses-grok45` / `gemini-interactions` profile，再填入自己的 Key。
2. 用最小三轮契约测试验证：用户问题 → 模型 tool call → Harnex tool result → 模型最终文本。对 thinking 模型再确认 reasoning/thought 内容的回传要求；Kimi K2.7/K3 需按官方契约回放 `reasoning_content`，Grok Responses 与 Gemini Interactions 则回放完整原生 output item/step。
3. 图片/文件必须为精确模型声明输入模态并实测。未声明时保留 `file_read`/OCR 降级，不要假设网关会忽略未知 content part。
4. OpenAI 专有 cache key/显式 breakpoint 只发给官方明确支持的端点。国产厂商的 cache hit/miss usage 名称各异，应以响应指标验收。
5. 将 429、5xx、529、network、timeout、首 token 超时纳入 failover；`parse`/`cancelled` 和已输出文本/思考后的错误不自动切换，以免重复回答。

当前可复用国产 profiles：

| Profile | 推荐放置 | 重要限制 |
| --- | --- | --- |
| `deepseek-v4` | DeepSeek 专用 provider | 仅 V4 当前 ID；reasoning 仅工具轮回放；厂商自动前缀缓存，不发 OpenAI cache key |
| `moonshot-kimi-chat` | Moonshot 官方 Chat 端点 | K2.7/K3 由型号规则自动区分；统一使用 `max_completion_tokens`，分别采用 32768/131072 默认上限；多步工具 reasoning 全量回放、稳定 cache key |
| `xai-responses-grok45` | xAI Grok 4.5 官方 Responses 端点 | 完整 output/encrypted reasoning 回放、`low/medium/high` effort、稳定 cache key 与原生搜索 |
| `gemini-interactions` | Google Gemini 官方 Interactions 端点 | 完整 step/thought signature 回放；function tools、Google Search 与声明后的 image/audio/video/PDF |
| `dashscope-qwen-chat` | DashScope 兼容模式官方端点 | Qwen 3.5–3.8 由型号规则自动区分 thinking/effort/历史保留；`features.reasoning-history:auto` 使用安全默认，需要跨轮保留时才选 `preserve` |
| `zhipu-glm-chat` | 智谱官方 Chat 端点 | GLM 5/5.1/5.2 共用 `clear_thinking:false`；5.2 单独获得 effort 白名单；reasoning 全量回放 |
| `openai-compatible-chat-safe` | 未知兼容端点、exact Ark endpoint ID、本地模型 | 只声明安全 Chat/SSE/function-tools 基线；**未实现/不宣称 Ark Context caching**，也不自动开启 reasoning replay |

专用 provider 设置 `profile: deepseek-v4`。普通中转只选协议 profile 并填写 endpoint/key/model；
官方 ID 被改名时优先用 `models[].capability-model`。只有 OpenRouter/自建聚合等单 endpoint 真正混合
多家 wire 契约时才用 `models[].profile` 精确覆盖。Profile 名不要带点号。

## 5. 构建与发布（维护者）

> 适用对象：维护者打 `.tgz` 自己保留、发到 npm registry 给终端用户用、或推到私服 / GitHub Packages。终端用户跳过本节。

### 5.1 一键脚本（推荐）

源码依赖验证使用 npm 10.9.4。首次在根目录安装工具依赖时执行 `npx --yes npm@10.9.4 ci --ignore-scripts --omit=optional`。
平台 CLI 包尚未发布时，npm 12 的 `npm ci` 可能因可选包缺失而拒绝当前锁文件；本地原生构建不需要下载这些 CLI 包。

工程根目录有 [scripts/build/build.mjs](../scripts/build/build.mjs)，**不用再手动跳进 backend / frontend 各打一次**：

```bash
# 在工程根目录
npm run build              # 全流程: mvn package + vite build + npm pack 校验 + 生成 .tgz
npm run pack:dry           # 仅预览将打入 .tgz 的文件
npm run release            # 全流程 + npm publish --access public
npm run release:patch      # 自动 npm version patch 升版本后发布
npm run release:minor      # 同上，minor

# 直接调底层脚本支持更多开关
node scripts/build/build.mjs --clean              # 先清 target/ 与 frontend/dist 与旧 .tgz
node scripts/build/build.mjs --skip-frontend      # 跳过前端（仅 cli 模式发版可用）
node scripts/build/build.mjs --publish --tag beta # 发到 beta dist-tag
```

脚本流水线：构建 jar → 构建前端 dist → `npm pack --dry-run` 校验产物里**确实包含了 jar**（防止漏打）→ 生成 `.tgz` 或 `npm publish`。任一步失败立即退出，给出原因。

**首次发版前的一次性准备**：

```bash
npm adduser              # 或 npm login
npm whoami               # 确认登录
npm view harnex   # 404 = 包名可用；显示信息 = 已被占（需改 scoped 名）
```

### 5.2 .tgz 包内容

| 必含 | 说明 |

**未打入**：源码 (`src/`)、`node_modules/`、`Dockerfile`、`docker-compose.yml`、内部设计文档（详见 [.npmignore](../.npmignore)）。


### 5.6 macOS 签名、公证与更新

适用版本：1.0.0；最低系统：macOS 13。Harnex 采用 Developer ID 直接分发，不进入 Mac App Store，
因为产品需要启动内置 JVM、MCP 和用户批准的工作区命令，不适合 App Sandbox。

#### 1. 产物与架构

分别在原生 runner 构建，不制作携带双份 JRE 的 Universal App：

| Runner | Runtime target | 用户产物 | Updater key |
|---|---|---|---|
| Apple Silicon | `darwin-arm64` | aarch64 DMG、VSIX、portable、optional npm CLI | `darwin-aarch64` |
| Intel | `darwin-x64` | x64 DMG、VSIX、portable、optional npm CLI | `darwin-x86_64` |

公共 Tauri 配置位于 `src-tauri/tauri.conf.json`；平台差异分别位于
`tauri.windows.conf.json` 与 `tauri.macos.conf.json`。Mac 配置只生成 `app,dmg`，启用 hardened runtime、
`icon.icns` 和 `minimumSystemVersion=13.0`。

#### 2. 不可改变的签名顺序

```text
Rust CLI + jlink JRE
  → 对每个 Mach-O/dylib codesign
  → 生成 runtime-bundle.json + SHA256SUMS
  → Tauri 复制 resources
  → 签名外层 Harnex.app
  → DMG
  → notarize + staple
  → codesign/spctl/真实启动验收
```

禁止在 Runtime 哈希生成后重新签名其中的 CLI/JRE，否则桌面、VS Code companion 和 portable consumer
都会按设计 fail closed。开发构建使用 ad-hoc identity `-`；正式构建必须使用 Developer ID。
复制 jlink JRE 时会解引用模块间共享许可证等符号链接，生成独立普通文件，再签名并计算哈希；最终
Runtime Bundle 仍禁止符号链接，删除临时 jlink 镜像后产物仍可独立校验。
Developer ID 重签会为 JRE executable 显式应用 `JreEntitlements.plist`（JIT、unsigned executable memory、
library validation exception），共享库不携带 executable entitlement；release 验收会反查 `java` 与
`jspawnhelper` 的最终签名 entitlement。

#### 3. 签名配置

正式 macOS 构建需在本机 Keychain 中安装 Developer ID 证书，并设置 `APPLE_SIGNING_IDENTITY`。
公证使用 App Store Connect API 凭据，或 `APPLE_ID`、`APPLE_PASSWORD`、`APPLE_TEAM_ID`。
更新签名使用 `TAURI_SIGNING_PRIVATE_KEY` 和可选的 `TAURI_SIGNING_PRIVATE_KEY_PASSWORD`；
应用内只配置 HTTPS 更新端点及 `HARNEX_UPDATE_PUBKEY` 公钥。
私钥与账号凭据由构建环境提供。具体检查以 `scripts/build/desktop.mjs` 为准。

#### 4. 本地构建

```bash
# 工具链体检：Rust/Tauri/Maven/jlink/Xcode CLT；正式模式再要求 notarytool
npm run build:desktop:check

# 当前 CPU 的 ad-hoc .app + .dmg
npm run build:desktop

# 设置上述 Apple/Tauri 环境变量后执行正式链路
npm run build:desktop:macos:release
```

`scripts/build/desktop.mjs --target` 必须与 `uname -m` 匹配。跨 CPU 构建会直接拒绝，避免把错误架构的 JRE
装进看似有效的 App。

#### 5. 手动运行自动化验收

在对应 Mac 架构上构建后端、前端、扩展与原生 CLI/Tauri，验证 Runtime Bundle。
安装本机构建的安装包，分别检查实际启动、运行域就绪、退出清理、签名、公证和 Gatekeeper 状态；独立自动验收脚本不随公开源码分发。
不同架构应分别验证，结果记录在发行说明中。

#### 6. 人工发布验收

- 在未装开发证书的新用户账户下载 DMG，拖入 Applications 后正常双击启动；
- `codesign --verify --deep --strict --verbose=2 /Applications/Harnex.app`；
- `spctl --assess --type execute --verbose=2 /Applications/Harnex.app`；
- Apple Silicon/Intel 各验证一次冷启动、切换工作区、Cmd-Q、Dock reopen、睡眠唤醒；
- 验证 Desktop/Documents/iCloud Drive/外置卷的 TCC 提示；
- 验证中文/日文 IME Enter、`⌘⇧F`、截图粘贴、拖放；
- 验证 Homebrew `git/node/npx/docker/ssh/tesseract`；
- 设置 `http.proxy=system` 验证系统/PAC 代理；
- 保存/显示/删除 Provider，确认 Keychain 项与 `keychain-providers.json` 索引同步；
- 并发保存/删除多个 Provider，确认索引没有丢更新；锁定 Keychain 后删除必须向 UI 报错，不能假成功；
- 安装 Darwin companion，确认 VS Code 集成终端 exact attach；
- 更新应用制品前备份用户配置、个人与项目数据；同版本重启须保持 Catalog、会话和 Keychain。未交付阶段不承诺旧格式迁移。

#### 7. 常见失败

启动冒烟在失败时会输出 App stdout/stderr、Domain state、desktop-shell.log 和 JVM stdout/stderr 的尾部，
再清理临时目录。`desktop Runtime manifest was not published` 只表示未到 READY；请根据这些日志判断是
资源定位、JVM 启动还是就绪探测失败，不能仅据此延长等待时间。

| 现象 | 检查 |
|---|---|
| App 被报告 damaged | Developer ID、notarization/staple、内嵌 Mach-O 是否全部签名 |
| Runtime Bundle hash mismatch | 查看错误中的 extra/missing/changed 文件列表；changed 指向 Mach-O 时检查是否在生成清单后又执行了 codesign。App 内顶层 `resources/ui/` 属于独立 SPA，Node 与 Rust 校验器均排除其哈希，但仍拒绝其中的符号链接 |
| Finder 启动找不到 npx/git | `fix-path-env` 是否在 `main()` 最早阶段执行；检查 shell profile |
| Provider Key 重启后为空 | Keychain 项、索引文件、`${HARNEX_KEYCHAIN_PROVIDER_*:}` 引用是否一致 |
| Quit 后仍有 Java/MCP | JVM 是否以独立 process group 启动；SIGTERM→SIGKILL 是否针对负 PGID |
| 更新检查失败 | endpoint HTTPS、minisign 公钥、`latest.json` 双平台键与 `.sig` 内容 |

Windows 主机只能验证公共 Rust/Java/TypeScript 和发行契约；Apple Objective-C framework、Keychain、
codesign、公证、WKWebView 与 TCC 的最终结论必须来自上述 Mac 原生 CI/人工验收。

## 6. Docker Compose 部署

### 6.1 从源码启动与访问

默认通过 GitHub 源码部署，在用户机器上构建镜像。宿主机只需 Git、支持 Linux 容器的 Docker 和 Docker Compose **2.24+**，无需安装 Maven、JDK、Python、Node/npm 或 Harnex CLI。首次构建需要联网下载基础镜像、系统软件包、Maven 和 npm 依赖。

```bash
git clone https://github.com/debug2048/Harnex.git
cd Harnex
docker compose up -d --build
docker compose ps
```

Compose 自动加载 `docker-compose.override.yml`，直接从源码构建两个服务；不需要预先下载 Harnex 镜像或 GitHub Release 发布包。后端在 Maven/JDK 17 构建阶段编译出 JAR，再复制到运行镜像；前端在 Node.js 24 构建阶段生成网页文件，再复制到 Nginx 镜像。前端构建使用仓库根目录作为上下文，包含 `frontend` 与共享的 `packages/protocol`，依赖按 lockfile 安装。

启动前无需创建 `.env`、填写模型密钥或选择宿主机项目。服务就绪后，在部署机器打开 **http://localhost:18081**，点击“配置模型”或进入“设置 → 模型”，添加模型服务并保存。模型设置会应用到后续任务，并保存到用户配置卷；不需要为了填写模型密钥而重建容器。设置中的“诊断”可查看实际工作区、存储和工具环境，启动故障使用 `docker compose logs -f backend` 排查。

端口默认只绑定部署机器的 `127.0.0.1`。如果浏览器在另一台电脑上，在那台电脑执行并保持 SSH 连接：

```bash
ssh -N -L 18080:127.0.0.1:18081 user@server
```

再打开 **http://localhost:18080**。通过域名提供访问时，在服务前配置带身份认证的 HTTPS 反向代理，并在 `.env` 设置浏览器的精确来源，例如 `HARNEX_WEB_ORIGIN=https://harnex.example.com`；代理需保留原始 Host。当前 GUI 没有账号登录流程。

Docker Web 提供“会话”和“Agent”：普通会话独立于项目，Agent 固定使用 `/workspace`，无需选择目录或配置 SSH 项目。两者共享模型设置，历史记录各自保存。后台管理进程启动即就绪，首次进入对应模式时才启动 Java Runtime；切换页面不会停止另一个模式中的任务。两个模式均使用后会保留两个 JVM，`.env` 中 `HARNEX_SUPERVISOR_JAVA_XMS=64m`、`HARNEX_SUPERVISOR_JAVA_XMX=512m` 按每个 JVM 生效，实际容器内存还包括 JVM 非堆内存与工具进程。健康检查表示管理服务可用；各 Runtime 的启动进度或失败由页面显示。

### 6.2 默认工作区、可选项目挂载与升级

默认工作区是 `/workspace`，通过 `HARNEX_SUPERVISOR_WORKSPACE` 固定，并自动创建 Docker 管理的持久化卷。工作文件与应用目录 `/app` 分开。命令在后端容器内执行，运行底座为 Ubuntu 24.04（glibc）和 Temurin 17 JRE。

| 默认运行工具 | 用途 |
| --- | --- |
| Java 17 JRE | 运行 Harnex 后端 |
| Python 3.12、pip、venv | Python 脚本与项目依赖；`python`、`python3` 均可用 |
| Node.js 24 LTS、npm、npx | JavaScript 脚本、前端项目、Node MCP 服务；从官方 Node 镜像复制到运行阶段 |
| `/bin/sh`、Bash、Git、ripgrep | 命令、Bash 脚本、代码管理与搜索 |
| curl、wget、jq、zip/unzip、CA 证书 | HTTP、JSON、归档与 HTTPS |
| Tesseract 与英文／简体中文语言包 | OCR 回退 |

`bash` 工具仍通过 `/bin/sh -c` 执行 POSIX 命令；需要 Bash 语法时显式执行 `bash script.sh`。Maven/JDK 是后端的构建依赖，最终运行镜像提供 JRE；需要编译 Java、Go、Rust 或使用浏览器的项目，可按需扩展运行镜像。

Python 第三方包安装到项目虚拟环境，保留 Ubuntu 系统 Python 的受管理保护。以下命令在容器的项目工作区内执行：

```bash
cd /workspace
python -m venv .venv
.venv/bin/python -m pip install -r requirements.txt
.venv/bin/python your_script.py
```

Node 项目可在工作区运行 `npm ci`、`npm run build` 或 `npx`。虚拟环境和项目内的 `node_modules` 随工作区卷保留；安装第三方依赖时需要相应软件源可达。Node 镜像固定 24 LTS 主版本，需要拉取新的基础镜像补丁时先执行 `docker compose build --pull`；升级语言主版本时应重新创建项目依赖环境。

Compose 与 backend Dockerfile 使用一致的持久化路径：

| 命名卷 | 容器路径 | 内容 |
| --- | --- | --- |
| `HARNEX-workspace` | `/workspace` | 项目文件、任务输出、`.harnex/data` 中的档案与日志、`.harnex/skills` 中的项目 Skills |
| `HARNEX-user` | `/root/.harnex` | 用户配置、用户 Skills、认证及个人数据 |

用户配置文件为 `/root/.harnex/agent-config.yml`，用户 Skills 为 `/root/.harnex/skills`，个人会话数据为 `/root/.harnex/personal`。项目档案随项目挂载保留；用户配置和个人会话独立于项目挂载。此布局按全新部署设计，不迁移旧版独立的 data/skills 卷。修改环境变量或挂载后需重新创建容器，`restart` 不更新已有容器环境。

需要直接操作宿主机已有项目时，在 `.env` 中加入现有目录的绝对路径（保留已有设置）：

```dotenv
HARNEX_WORKSPACE_HOST=/srv/my-project
```

再显式加载可选的工作区挂载模板：

```bash
docker compose -f docker-compose.yml -f docker-compose.override.yml \
  -f docker-compose.workspace.yml up -d --build
```

该模板只替换 `/workspace` 的挂载，其他数据卷继续保留；目录不存在时拒绝启动，避免误建空目录。容器中的修改会直接写回宿主机项目。切换挂载不会复制默认工作区中的文件；后续启动、升级和停止应继续使用同样的三个 `-f` 参数。浏览器只能访问容器可见的工作区，不能直接打开未挂载的宿主机目录。

不提供旧 bind-mount 数据自动迁移，切勿用 `docker compose down -v` 作为普通升级步骤；该参数明确删除卷。

后端默认映射 `8088`，前端默认映射 `18081`，可通过 `.env` 中 `HARNEX_BACKEND_PORT` / `HARNEX_FRONTEND_PORT` 覆盖。已有 `.env` 若仍设置 `HARNEX_FRONTEND_PORT=8080`，更新源码后也会沿用该值；改为 `18081` 或删除该行即可使用新默认值。仅调整前端端口时，可复用已有镜像执行：

```bash
docker compose up -d --no-deps --no-build --pull never frontend
```

Runtime 日志分别写入项目和个人数据目录中的 `diagnostics/logs/`，随对应卷持久化，Compose 默认按日切片 + 5 MB 单文件 + 14 天保留 + 1 GB total cap。管理进程及子进程输出保存在用户目录下的 Runtime Domain 日志中。排查启动问题可先运行 `docker compose logs backend`，或在设置中查看诊断。

源码部署升级：更新到目标 Git 版本后，在同一部署目录运行 `docker compose up -d --build`，重新构建并保留数据卷。使用宿主机项目挂载时仍需带上上述三个 `-f` 参数。跨不兼容版本升级前应备份数据和配置。

停止服务：
```bash
docker compose down                          # 保留工作文件、会话、配置卷与镜像
```

### 6.3 `harnex doctor`（A1）

npm 发行版的诊断命令。Docker 部署使用 `docker compose ps`、日志和 Web 设置中的“诊断”，无需在宿主机安装此命令。`harnex doctor` 读取本机 `agent-config.yml` + 环境变量，对以下条目逐项给出红/黄/绿：

- Java 17+ 是否在 PATH
- 后端 jar 是否已 build
- `harnex serve` 的监听端口（默认 18081）是否被占用，以及占用方是否为本进程
- `agent-config.yml` 中 `providers[].api-key` 是否全部为 `${ENV}` 引用（**不允许裸字符串**，A3）
- 至少一个 provider 的 key 解析后非空
- `HARNEX_AUTH_ENABLED` 与 `HARNEX_AUTH_TOKENS` 是否一致
- `data/` 目录是否可写

```bash
node bin/harnex.mjs doctor          # 本仓库
harnex doctor                        # 全局安装后
```

退出码：所有 FAIL 解决前为 `1`，可直接接入 CI / smoke-test 脚本。

### 6.4 `harnex init --wizard`（C3）

`harnex init` 默认仍写出一份 `AGENTS.md`（CI/脚本场景兼容）。新增 `--wizard` / `-w`
进入 5 题向导，生成本地 `.env`：

1. 团队/部署名称（写入 .env 注释，便于多机器辨识）
2. 主用 IM 平台（`feishu` / `dingtalk` / `wecom` / `webhook` / `none`）
3. 主 LLM provider 的 env-var 名（默认 `OPENAI_API_KEY`，可改 `FALLBACK_API_KEY` 等）
4. 宿主绑定地址（默认 `127.0.0.1`）
5. 命令执行环境（`host` / `docker`）

向导会询问所选模型环境变量的值，但不会生成 Provider 定义；选择其他变量名后仍需在模型设置或 YAML 中引用。它生成 `HARNEX_AUTH_ENABLED=false`，不生成 Bearer Token，远程访问需自行配置认证边界。SSH 通过远端工作区连接，不是此向导的命令环境选项。

向导完成后提示 `docker compose up -d --build` 与 `harnex doctor`。当前模板还会写入旧的 `HARNEX_LOG_DIR=/app/data/logs`；使用本文 Compose 布局时应删除这一行，以采用随个人／项目数据卷保存的默认日志路径。无需部署定制时可直接按 §6.1 启动。

### 6.5 Alertmanager 告警入站（B3）

`POST /api/gateway/alertmanager` 接收 Prometheus Alertmanager v4 标准 payload，
HMAC-SHA256 签名（与 WebhookController 同一套 ts/nonce/sig 模式）。
配置步骤：

1. `agent-config.yml` 中 `harnex.gateway.alertmanagerSecret: ${HARNEX_ALERTMANAGER_SECRET:}`（默认已存在）
2. `.env` 设置 `HARNEX_ALERTMANAGER_SECRET=<你的随机长字符串>`
3. Alertmanager 侧 `receivers` 增加：
   ```yaml
   receivers:
     - name: harnex
       webhook_configs:
         - url: https://harnex.example.com/api/gateway/alertmanager
           http_config:
             # Alertmanager 不直接支持 X-HARNEX-* 头，建议在前置 nginx/lua 注入
             # X-HARNEX-Timestamp / X-HARNEX-Nonce / X-HARNEX-Signature 三个头
             # 然后转发；或参考下方 sample 用 sidecar 转换。
   ```
4. 授权的告警进入对应会话，Agent 按实际模型、工具集与网关权限处理摘要。仓库不预置 `ops-k8s-inspect`／`ops-log-query` 技能，也不保证固定的 `[ROLLBACK]` 回复字段；诊断步骤与输出格式需在已安装技能或任务指令中明确。

> 其他告警平台（Datadog / Grafana / OpsGenie / 自研脚本）请将 payload 规范化后改投 `POST /api/gateway/inbound` ，以复用现有入站接口。

### 6.6 MCP 集成 — Prometheus + GitHub（B2）

`agent-config.yml` 中 `harnex.mcp.servers` 已预置两条注释样例（一等公民支持范围）。
启用任一条即可：

```yaml
harnex:
  mcp:
    servers:
      - name: prometheus
        transport: stdio
        command: npx
        args: ["-y", "@modelcontextprotocol/server-prometheus"]
        env:
          PROMETHEUS_URL: ${PROMETHEUS_URL:http://prometheus:9090}
      - name: github
        transport: stdio
        command: npx
        args: ["-y", "@modelcontextprotocol/server-github"]
        env:
          GITHUB_PERSONAL_ACCESS_TOKEN: ${GITHUB_TOKEN:}
```

`.env.example` 已添加 `PROMETHEUS_URL` / `PROMETHEUS_BEARER_TOKEN` / `GITHUB_TOKEN` 占位。
启动后这些 MCP 工具会以 `mcp__prometheus__*` / `mcp__github__*` 命名空间出现在**默认仅 `act` preset** 中（由 `harnex.mcp.servers[].expose-to-presets` 控制，默认 `[act]`；如需让只读会话也能调用，明示设为 `[read, inspect, act]`）。MCP 连接和工具暴露范围由设置页及示例 YAML 配置。

### 6.7 执行环境、按需隔离与 SSH

普通开发使用 Runtime 所在机器的工具链，不额外创建沙箱。SSH 工作区中的主机就是远端服务器。
只有用户配置要求隔离，或任务明确需要并通过 `bash.sandbox` 请求时，才使用原生沙箱；Docker 由用户选择执行环境，不由模型随意切换。

审批与隔离独立：选择容器/沙箱不会自动批准命令，后台运行也不会把尚未授权的操作转为允许。
自动 Git 检查禁用 fsmonitor、外部 diff 和 textconv 回调，避免快照/文件浏览在命令隔离之外执行仓库程序；用户显式执行的 Shell 命令保留自己的 Git 行为。
子 Agent 继承父任务权限，不能通过委派深度扩大权限。自动化任务的 `allowMutations` 是显式授权，取消该选项会同步收紧其复用线程。

#### 支持范围

| 能力 | Windows | macOS | Linux |
|---|---|---|---|
| 本机 GUI/TUI 与主机命令 | 支持；Git Bash 优先，保留 CMD 输出兼容 | 支持 | 支持 |
| SSH 连接客户端 | 系统 OpenSSH | 系统 OpenSSH | 系统 OpenSSH |
| SSH Runtime 服务端 | 本轮不支持 | 本轮不支持 | Java 17+、setsid、sha256sum |
| 可选原生命令隔离 | 本轮不启用，不会创建系统账号或修改防火墙 | 固定版本 SRT + Seatbelt | 固定版本 SRT + bubblewrap/seccomp |
| Docker 命令环境 | 需要可访问的 Linux Docker daemon | 同左 | 同左 |

不支持某项原生隔离时，普通主机模式仍可使用；请求该隔离的命令会在启动用户命令前报错。
`installed` 表示找到了隔离运行器，不等同于通过了内核权限验收。运行器或 IPC 依赖缺失、存在降级警告、内核/AppArmor 拒绝启动时，命令均不会降级执行。

按需原生隔离使用 `@anthropic-ai/sandbox-runtime@0.0.75`（SRT），不自行拼装平台安全策略。只有需要此功能的机器才安装：

```text
npm install -g @anthropic-ai/sandbox-runtime@0.0.75
```

需要 Node 20.11+ 和 rg；Linux 还需要 bubblewrap、socat 及系统允许的用户命名空间。Harnex 不会自动安装这些依赖。
原生隔离当前固定为离线，阻断 Unix 套接字及网络，且不继承任意凭据或 SSH Agent 环境；需要联网隔离时由用户明确配置 Docker。
运行器、Node 和 Harnex Runtime 必须位于工作区及额外可写目录之外，避免隔离任务改写自身的执行边界。

#### 配置

在运行目标机器的用户配置 `~/.harnex/agent-config.yml` 中配置，或使用 GUI「安全与权限 → 命令执行环境」。执行设置按新任务快照生效；正在执行的任务沿用原快照。连接与凭据类变更按保存结果提示重连。

```yaml
harnex:
  execution:
    environment: host          # host | docker
    sandbox-mode: none         # none | read-only | workspace-write
    sandbox-network: deny      # deny | allow，只影响隔离命令和容器
    sandbox-runtime: ""        # 可选：上述 SRT 包目录的绝对路径；留空发现全局 srt
    writable-roots: []          # 原生沙箱额外写入目录；绝对路径，需预先存在
    image: debian:stable-slim   # Docker 用户选择的工具链镜像
    memory: 512m
    cpus: "1"
    pids-limit: 256
```

普通主机命令、模型服务连接和 SSH 控制连接不受 `sandbox-network` 限制。
主机模式没有 OS 隔离；文件工具仍受路径访问与写保护规则约束。可选运行器隔离命令及子进程的文件、网络和 IPC，并屏蔽 Runtime 私有目录与凭据目录；它不把整个 JVM 或远程 MCP 服务放入沙箱。

单次工具调用可请求更窄的隔离：

```json
{"command":"./inspect-untrusted-input.sh","sandbox":"read-only"}
```

可选值为 `read-only` 或 `workspace-write`。省略时沿用用户配置；请求不能关闭配置强制的隔离。不要为日常文件读写或普通开发任务无差别加入此参数。

旧 `harnex.sandbox.*`、`HARNEX_SANDBOX_BACKEND` 和工具参数 `sync_workdir` 已移除，会明确报错。不存在 SSH/Docker 失败后回退主机的路径。

#### 远端项目部署

远端服务端目前支持 Linux x64/arm64，需要 `setsid`、`sha256sum`；优先使用 Java 17+，自动准备 JRE 时还需 `tar`。连接宿主下载并校验 Temurin 17，JAR／rg 按摘要缓存，既不安装系统包也不复制项目。模型配置、项目工具链与运行数据均在远端。远端 HTTP 只监听 loopback 并启用令牌，经 SSH 隧道访问。

GUI 与终端连接步骤、认证和恢复见[用户手册](06_用户手册.md#ssh-workspaces)。请在实际 SSH 服务端验证连接、命令执行及文件访问。

Compose 部署整个 Harnex；其中 `environment: host` 指在后端容器内执行。
Compose 的直连 GUI 操作该 Runtime 的固定工作区；SSH 连接管理入口由桌面宿主或 Web Supervisor 提供。
命令级 Docker 则按用户选择的镜像创建临时容器，把项目挂到 `/work`，并限制根文件系统、资源和网络。项目内的 Runtime 私有数据目录会被遮蔽。
Docker CLI 必须能访问 Linux daemon，daemon 的绑定挂载必须对应 Runtime 所见的实际文件系统。容器化 Runtime 加宿主 Docker socket、远程 Docker context 等组合需要额外部署设计，本轮不作为完整开发环境支持。
命令级隔离由 `execution.image` 选择工具链镜像，默认的 `debian:stable-slim` 不包含 Node、Maven 等开发工具；需按项目自行准备。Compose 后端预装的 Python/Node 不会自动进入这些临时容器；当前不实现完整 Dev Container 生命周期。

## 7. 配置说明

### 7.1 Spring 与存储配置

`application.yml` 管理端口、日志、认证等 Spring 配置；`agent-config.yml` 管理 Harnex 业务配置。目录在日志初始化之前统一解析，不再先写到工作目录的 `data/logs`。最小业务默认值：

```yaml
harnex:
  data-dir: .harnex/data
  skills-dir: .harnex/skills
  max-iterations: 200
  ordinary-max-iterations: 64
```

相对路径以实际项目根解析；PERSONAL 固定使用用户根的 personal。宿主登记的显式 dataDir／启动参数优先。模板见[agent-config.example.yml](../agent-config.example.yml)，用户配置声明 providers 时整体替换低优先级端点表，需列全要保留的提供商。

### 7.2 `agent-config.yml`（业务配置与生效边界）

Provider、路由、摘要、安全与路径策略、工具集、Hooks、搜索、图片和执行设置可用于新任务；当前任务保留原快照。HTTP／MCP 连接和相关凭据变更可能需要重连，端口、目录等启动配置仍需重启。具体以设置保存结果与[用户手册 §9.0](06_用户手册.md#90-配置怎么读取怎么改最重要先读这一节)为准。

```yaml
harnex:
  providers:
    primary:
      profile: openai-chat
      base-url: ${OPENAI_BASE_URL:https://api.openai.com/v1}
      api-key: ${OPENAI_API_KEY:}
      default-model: ${OPENAI_DEFAULT_MODEL:gpt-4o-mini}
    fallback:
      profile: deepseek-v4
      base-url: ${FALLBACK_BASE_URL:https://api.deepseek.com/v1}
      api-key: ${FALLBACK_API_KEY:}
      default-model: ${FALLBACK_DEFAULT_MODEL:deepseek-v4-flash}

  router:
    default-provider: primary
    failover-on: ["429", "500", "502", "503", "504", "529", "timeout", "network", "stream_ttft_timeout"]

  toolsets:
    presets:
      read:    [file_read, glob, grep, web_fetch]
      inspect: [file_read, glob, grep, web_fetch, bash]
      act:     [bash, file_read, file_write, file_edit, glob, grep, web_fetch, delegate]
    default-set: [act]

  budget:
    per-tool-chars: 8000
    per-turn-chars: 30000
    preview-chars: 1200

  approval:
    mode: default            # bypass | default | strict
    dangerous-patterns:
      - "rm\\s+-rf\\s+/"
      - "mkfs\\."

  execution:
    environment: host
    sandbox-mode: none
    sandbox-network: deny

  moa:
    enabled: false

  cron:
    enabled: true
```

> 上面是最小结构示例。生产配置应以仓库当前的 `agent-config.example.yml` 为字段基线；模型目录使用厂商控制台返回的精确 ID，避免复制过时静态型号。

## 8. 持久化 / 备份

| 位置 | 备份内容 |
| --- | --- |
| 项目 `.harnex/data` 或显式 dataDir | 会话档案、Run／Goal／Snapshot、上传、资产、用量账本、项目记忆与设置 |
| 项目 `.harnex/skills` | 可随 Git 共享的项目技能，与运行数据分别保存 |
| `<userDataDir>/personal` | 普通会话、图片、附件和用量 |
| 用户根 | 配置、用户技能／USER.md、认证账户、Catalog 和 SSH 连接配置；凭据按敏感资料保护 |

备份时以设置 → 诊断列出的实际用户目录和项目数据目录为准。`indexes` 可重建，`diagnostics` 是诊断；`usage-ledger`、`assets` 和 `conversations` 是业务数据，不能当缓存清理。宿主日志与后端日志分别位于运行域和 dataDir。

Node 启动器提供 `harnex backup --personal`，或项目备份 `harnex backup --workspace <项目>`，并支持 `--data <专用数据目录>`、`--out <输出目录>`；`--personal` 不能与项目／data 选择同时使用。默认项目目录和 Catalog 显式绑定使用同一解析规则。备份是 Node 工具命令，native binary 没有实现该子命令；原生用户可在停止写入后备份上述目录。

先停止／排空所有使用该项目共享根的写 Runtime，再复制完整项目数据根，包含 `runtime-stores/`，确保共享档案、资产与各宿主的 Run、用量、快照和回执一致。只备份诊断页的执行 dataDir 会遗漏独立 sharedDataDir 中的档案与原件。恢复到专用目录并保持共享根与宿主子目录结构，不能将运行目录直接设为项目根、用户根或 `.harnex` 容器。Runtime 自动建立 `<dataDir>/.gitignore` 的 `*` 防误提交规则，项目技能仍可提交；已跟踪文件或 `git add -f` 不受该规则保护。

Windows 要将个人会话与缓存移出 C 盘，在所有宿主启动前设置 `HARNEX_USER_DATA_DIR=D:/HarnexUserData`；这只改变后续读取位置，不自动搬迁现有资料。项目默认随所在磁盘保存，已登记的显式路径优先。

- 升级：拉取新 jar / 镜像，滚动重启；先核对数据格式；未交付阶段不提供旧配置／旧记录兼容，使用明确的新目录验证，不自动转换或清空既有资料

- 安装与升级方式见 [Docker 部署说明](../scripts/deploy/README.md)。
- **Agent 正在对话的请求** 会被 graceful drain（默认 30s）

## 10. 监控 / 可观测

- **日志**：Logback 文本日志默认输出到 `<dataDir>/diagnostics/logs/harnex.log`；`HARNEX_LOG_DIR` 可覆盖目录。
- **指标**：显式开启 `/actuator/prometheus` 后可抓取 `harnex_chat_requests_total`、`harnex_chat_errors_total`、`harnex_tool_calls_total`、`harnex_tool_duration_seconds_*`、`harnex_provider_failovers_total` 等。当前注册没有上述指标的逐工具、逐线程或 `from/to` 标签；清单以 `HarnexMetrics` 和实际抓取结果为准。
- **访问**：默认仅开放 health/info，需设置 `management.endpoints.web.exposure.include=health,info,metrics,prometheus`，并满足认证边界。Compose 的公开端口由 Supervisor 托管，抓取 Runtime 指标还需明确转发到对应个人／项目 Runtime，不能把管理服务健康检查当作业务指标。
- **链路**：当前仓库未集成 OpenTelemetry exporter；仅设置 `OTEL_EXPORTER_OTLP_ENDPOINT` 不会启用链路导出。后续接入需单独配置和验收。

## 11. 安全基线

1. 默认仅绑定 `127.0.0.1` 且本地用户级 GUI 免登录；只有越过 loopback 暴露时才启用
   `harnex.auth.enabled=true`，或把 WebUI 放在可信认证反向代理后，Backend API 不直接暴露
2. Approval 默认 `default` 模式；命中危险命令规则时先 DENY，其余调用按任务权限与审批模式决定 ALLOW／ASK
3. 文件工具（file_read/file_write/file_edit/glob/grep）的可达范围由 `WorkspacePathResolver` 的 GREEN/YELLOW/RED 分区约束（工程内放行、工程外按需、敏感/私有路径拒绝）
4. `web_fetch` 默认 SSRF 黑名单：`127.0.0.0/8`、`10.0.0.0/8`、`169.254.0.0/16`
5. 公共资产导入默认每个文件最多 64 MiB；Spring multipart 的单文件／请求上限为 200MB／220MB，不能覆盖资产层限制。Web 客户端还会采用配置中更小的上传上限，反向代理可能更早拒绝。Compose 的 `frontend/nginx.conf` 未显式设置 `client_max_body_size`，大文件部署需另行配置并验收代理限制。运行数据整体没有 2GB 硬配额
6. API Key 按用户配置或平台 Keychain 保存；API 默认脱敏，前端不持久化明文
7. CORS 默认只允许同源；开发期用 `spring.web.cors.allowed-origins`
8. 出网代理凭据脱敏：所有日志与 `tool_results` 经 `SecretRedactor` 扫描，URL 中的
   `user:pass@host` 形式会被替换为 `[REDACTED]@host`（见下节 §11a）

## 11a. 出网代理 / Egress Proxy

> 设计目的：开发机/办公网通常走企业代理，但 `127.0.0.1` 上的本地中转（如 CLIProxyAPI、
> sing-box）需要直连。沿用 VSCode 的单 URL 体验，避免再发明另一套配置 schema。

### 11a.1 配置字段（agent-config.yml）

```yaml
harnex:
  http:
    # 全局出网代理；空 / off / direct / none → 不走代理
    proxy: "http://user:pass@proxy.corp.lan:8080"
    # on   = 永远使用上面配置的 proxy
    # off  = 强制直连（忽略 proxy 字段）
    # fallback = 先 TCP 探测 baseUrl 直连，3s 内连得通则 DIRECT，否则用代理（默认）
    proxy-support: fallback
    # 直连白名单（任一命中即不走代理；支持 glob *）
    # 内置免配置 bypass：loopback、RFC1918、169.254/16、.local/.internal/.corp、IPv6 ULA
    proxy-bypass:
      - "*.deepseek.com"
      - "10.*"
  providers:
    anthropic:
      profile: anthropic-messages
      api-key: ${ANTHROPIC_API_KEY:}
      # per-provider override，优先级高于全局 harnex.http.proxy
      proxy: http://override.lan:1234
    local-cliproxy:
      profile: openai-compatible-chat-safe
      base-url: http://127.0.0.1:7999
      api-key: anything
      default-model: <本地服务实际模型 ID>
      proxy: off                # 永远直连，即使全局开了代理
```

### 11a.2 配置来源优先级（Spring 标准 + POSIX env 兼容）

从高到低：

1. `--harnex.http.proxy=...`（CLI 启动参数）
2. `SPRING_APPLICATION_JSON`
3. `-Dharnex.http.proxy=...`（JVM 系统属性）
4. `HARNEX_HTTP_PROXY` env（Spring 标准绑定）
5. **`HTTPS_PROXY` / `HTTP_PROXY` / `ALL_PROXY` env**（POSIX 事实标准，与 curl/npm/git/pip/go 共享）
6. `agent-config.yml` 的 `harnex.http.proxy`（macOS 桌面可显式填 `system` 使用系统/PAC 代理）
7. 默认（空 = 直连）

> 第 5 条是为了与企业网用户的既有习惯对齐 —— `export HTTPS_PROXY=...` 之后
> harnex 与 npm/git 自动一致；不需要再重复设 `HARNEX_HTTP_PROXY`。

`NO_PROXY` env（curl 子集语法：`.suffix` → `*.suffix`、`host:port` 丢端口）
会与 `harnex.http.proxy-bypass` **合并**，不是覆盖。

> VSCode 插件 / 包装脚本可通过 `--harnex.http.proxy=$(代理URL)` 在启动时透传，
> 不需要改 YAML 也不依赖 env。

### 11a.3 安全

- HTTP CONNECT 鉴权失败（407）后只重试一次，避免无限循环。
- OkHttp 强制使用 `NoDefaultProxySelector`，**不会**意外读取 JVM 的
  `-Dhttp.proxyHost` 或操作系统代理；唯一来源就是上面的配置。
- `harnex doctor` 会以脱敏形式（`***:***@host:port`）打印当前生效的全局代理与
  每个 provider 的覆盖值，便于运维核对。
- 凡进入日志、`tool_results`、审计流水的字符串都会过 `SecretRedactor`，
  URL 中的 `user:pass@` 段会被替换成 `[REDACTED]@`。

### 11a.4 验证

```bash
harnex doctor
# [  OK  ] http.proxy (global)           http://***:***@proxy.corp.lan:8080 support=fallback bypass=*.deepseek.com
# [  OK  ] provider 'anthropic' proxy    http://override.lan:1234
# [  OK  ] provider 'local-cliproxy' proxy off — forced DIRECT regardless of global
```

启动日志里也会出现一行 `Provider 'xxx' http: proxy=... (source=...)`，
便于在 SSH/Pod 里 grep 排查。

## 12. 生产建议

- 按当前单用户 Runtime 边界部署；保护配置、个人目录和完整项目数据根，并演练同版本恢复。
- 每个执行 dataDir 仅有一个写 Runtime。桌面／IDE 的独立执行子目录与共享档案事务不等于跨机器 HA；不要让多个副本共写同一执行目录或 Lucene 索引。
- 使用带认证的 HTTPS 反向代理，配置 SSE 转发与上传限制；容量按实际模型、工具、JVM 和任务负载测试，不承诺固定并发数。
- SQL 历史后端、跨机器协调、K8s／HA 和 Helm Chart 尚未实现。需要这些能力时先设计并实现相应存储与恢复支持，不能仅添加 PostgreSQL、共享 NFS 或粘性会话配置获得。

## 13. 常见问题

| 现象 | 排查 |
|------|------|
| 启动报 `Failed to bind` | 端口占用；调整 `server.port` |
| SSE 很快断开 | 反向代理需 `proxy_buffering off; proxy_read_timeout 900s;` |
| `401 Unauthorized` | API Key 未注入；检查环境变量 / `agent-config.yml` |
| 工具输出乱码 | Windows 控制台默认 GBK；设 `-Dfile.encoding=UTF-8` |
| Lucene 锁异常 | 先确认所属 Runtime 已停止且没有另一写入者，再检查 `<dataDir>/indexes`；不要删除活进程的锁 |

## 15. 与 CLIProxyAPI 集成

> CLIProxyAPI 把若干厂商命令行/Web 登录态转换成 OpenAI/Anthropic 风格 API。只有它对所选模型实际暴露了 Harnex 所需的 Chat/SSE/tool-calls 基线时，才可作为 `openai-compatible` 上游；thinking、附件、缓存等扩展仍需逐模型验证。

### 15.1 拓扑

```
+--------------+        +-------------+        +----------------+
| Harnex       |  --->  | CLIProxyAPI |  --->  | Claude / Codex |
|              |        |  (本地 / VM) |        | / Gemini Web   |
+--------------+        +-------------+        +----------------+
  协议适配层               OAuth / Key 池       (各厂商 CLI / Web)
```

### 15.2 部署步骤

1. 按 CLIProxyAPI 当前官方 README 在与 Harnex **同一安全域内**部署实例。端口只绑定 loopback、同一 Docker network 或内网 Service，不直接暴露公网；按上游说明完成 OAuth / API key 录入。

2. 在 Harnex 的用户级 `agent-config.yml` 配置 Provider。下面是仅使用 CLIProxyAPI 的完整端点表；已有其他端点时需在同一 `providers` Map 中保留它们，并保持默认／摘要／MoA 引用有效：
   ```yaml
   harnex:
     providers:
       cliproxy:
         profile: openai-compatible-chat-safe
         base-url: http://cliproxy:8317/v1   # Docker Compose 同 network；外部部署用真实 host
         api-key: ${CLIPROXY_KEY:}
         default-model: <网关当前返回且已通过工具闭环验证的模型 ID>
         models:
           - { id: <exact-model-id>, label: "Model via CLIProxy", tier: medium, input-modalities: [text] }
     router:
       default-provider: cliproxy
   ```

3. （可选）把摘要绑定到同一端点的另一模型；这仍共享 `cliproxy` 的连接和凭据。需要独立额度时另建 Provider。vision/附件始终跟随当前 Chat 模型：
   ```yaml
   harnex:
     summarizer:
       enabled: true
       provider: cliproxy
       model: <cheap-summary-model>
   ```

### 15.3 安全要点

- CLIProxyAPI 内嵌的 OAuth token / 各厂商 cookie **比单纯的 API key 更敏感**——它们是会话级凭证，
  泄漏后无法仅靠"换 key"撤销。**严禁把 CLIProxyAPI 端口对外**，建议：
  - 同 docker network 内访问（`-p 127.0.0.1:8317` 而非 `-p 8317`），或
  - 走 VPC 内 Service / Unix socket。
- 如果 Harnex Runtime 会越过 loopback 暴露，必须启用 `HARNEX_AUTH_ENABLED=true` 或放在可信认证代理后；CLIProxyAPI 自己**不**替代 Harnex 的访问边界。
- CLIProxyAPI 升级 OAuth 库时可能导致厂商一侧 cookie 失效，触发 401 / 403；Harnex 会按路由健康策略处理，但运维仍应告警并重新授权。
- 不要因为网关目录显示“视觉/推理模型”就自动声明附件或 reasoning 能力；必须用该网关端点实测，而不是套用官方直连能力。

### 15.4 何时不用 CLIProxyAPI

- 已经有官方 API key（Anthropic / OpenAI / Gemini）→ 直接配对应协议更稳，省一跳。
- 客户合规要求“所有 LLM 流量走自有 BYOK”→ CLIProxyAPI 的 OAuth 池不符合这个口径。
- 阶段 2 的形态 2 自研 `harnex-gateway`（P-16）落地后，这条路径可被替代。
